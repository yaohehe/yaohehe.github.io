Tokenizer 实测：一个汉字被切成几个 token

TokenizertiktokenLLM

TL;DR：官方帮助页那条「1 token 约等于 4 个字符」是英语的经验值，用中文技术文实测会低估 3.4 倍。更麻烦的是字节级 BPE 的后果：一个汉字可能被切成 3 个字节碎片，逐个 token 解码会永久丢字（47 字符变 55 字符、16 个替换符），而整个过程不报任何错。

我把站内 23 篇中文原创技术文和 40 篇英文原创技术文全部过了一遍 tiktoken 0.14.0，下面每一个数字都来自本机跑出来的结果，脚本可复现。本文不含任何联盟推广链接。

官方口径其实写得很清楚，只是没人往下读

OpenAI 帮助中心那篇讲 token 的文章里，三句话是连在一起的，逐字原文是：

  • 「1 token is approximately 4 characters.」
  • 「1 token is approximately three-quarters of a word.」
  • 「These are estimates, not exact counts. Sentence and paragraph lengths vary, and other languages can have different relationships between characters, words, and tokens.」

第三句就是全部答案：4 字符是个只针对英语的粗略估计，而且官方明说不同语言里字符、词、token 三者的关系不一样。但工程里流传的版本通常只有第一句，于是中文项目的额度估算从第一天起就偏了。

我实际测试的结果：英文技术文的中位数是 4.13 字符/token（与官方那条经验值几乎重合）；中文技术文是 0.841 token/字符，也就是一个 token 只覆盖 1.19 个汉字。按 4 字符/token 去估中文，等于把 token 数算成实际的 30%，低估 3.4 倍。

五个 encoding 的词表规模差了一倍

tiktoken 里能直接取到的公开 encoding 及本机实测的词表大小：

encodingn_vocab特殊 token 数典型用途

最后一行值得单独看一眼：o200k_harmony 有 1,091 个特殊 token，把常见几个列出来就知道它不是给普通对话用的，里面塞满了 <|channel|>、<|message|>、<|constrain|>、<|call|> 这类结构符号。如果你的计数脚本对 allowed_special 用了宽松策略，碰上这个 encoding 会把一堆控制符当成普通文本数进去。

换 encoding 到底省了多少：中文 22.8%，英文几乎为零

同一批语料换 encoding 重跑，结论比直觉更值得记：

  • 中文 23 篇：cl100k_base 中位 0.841 token/字符 → o200k_base 中位 0.649 token/字符，省 22.8%
  • 英文 40 篇：cl100k_base 中位 1.531 token/词 → o200k_base 中位 1.534 token/词，差 0.2%，在噪声内

也就是说，词表从 10 万翻到 20 万，买到的几乎全是非拉丁文字的字形合并能力，英文散文的压缩率一点没变。单句对照更直观：同一段 47 字的中文，cl100k_base 切出 49 个 token，o200k_base 切出 32 个。

这条对选型有直接后果：如果你的负载以英文为主，换到 o200k 系模型不会因为「词表更大」而便宜；如果负载是中文，光换 encoding 这一项就能省两成。

字节级 BPE 的三个后果

BPE 最底层的单位是字节，不是字符。一个汉字在 UTF-8 里占 3 个字节，而词表里不一定恰好有「这个汉字」的整体词条。当没有时，它就被拆成 2 到 3 个字节碎片，每个碎片一个 token。

后果一，计数会超出直觉：一段 47 字的中文，最差情况下要 49 个 token。

后果二，逐 token 解码会永久丢字。这是本文最值得带走的一条。把同一段中文的每个 token 单独 decode 再拼起来：

toks = enc.encode_ordinary(text)          # 47 个汉字 -> 49 个 token
joined = "".join(enc.decode([t]) for t in toks)
# 原文 47 字符 -> 拼接结果 55 字符，含 16 个 U+FFFD 替换符，joined != text

16 个替换符意味着 16 个汉字位置被 � 顶掉，而且没有任何异常。想让它报错必须显式指定：

enc.decode([toks[1]], errors="strict")
# UnicodeDecodeError: 'utf-8' codec can't decode bytes in position 0-1: unexpected end of data

后果三，前缀解码也不安全。改成每次解码 toks[:i] 的累计结果，最终结果是对的，但中间仍有 2/32 步会闪出替换符，因为那一步的最后一块正好落在字符中间。真正稳的写法是把末尾不完整的字节扣住不输出，等下个 token 补齐再吐。这条和流式输出是同一个问题，我在 LangGraph 流式三种入口的实测里踩过一次：token 级流式接前端时，中文一定会出现方块，原因不在框架，在解码边界。

数字、标识符和缩进是 token 黑洞

同一段文本里，最容易失控的不是正文而是结构化字段：

样本字符数token 数每字符 token
UUID 3f2b9c1e-7a4d-4f88-9b21-0c5e6d7a8b9036330.92
JSON 订单对象83400.48
时间戳 2026-11-011060.60
时间 06:10:46850.63

UUID 是极端案例：36 个字符吃掉 33 个 token，几乎一比一。日志、trace_id、订单号密集的 prompt，按字符数估额度会错到离谱。

数字还有个反直觉的地方。不加分隔符的 1284500 是 3 个 token，加上千分位写成 1,284,500 变成 5 个 token，因为逗号各自占一个。为了可读性加的格式，在 token 账上是净支出。

缩进也是。同一段 Python，4 空格缩进 18 个 token，Tab 缩进 16 个 token，差 11.1%。这个差距在大批量代码语料上会放大。

特殊 token 默认是直接抛错的

把 <|endoftext|> 当普通文本喂进去，tiktoken 会拒绝：

ValueError: Encountered text corresponding to disallowed special token '<|endoftext|>'.
If you want this text to be encoded as a special token, pass it to `allowed_special`
To disable this check for all special tokens, pass `disallowed_special=()`.

三条路的结果完全不同，我逐个跑了：

写法结果
默认抛 ValueError
disallowed_special=()9 个 token（当普通文本）
allowed_special="all"4 个 token（那个标记被压成 1 个控制符）
encode_ordinary()9 个 token（等价于第二条）

allowed_special="all" 少算 5 个 token 只是表面，真正的问题是语义：用户输入里只要出现 <| 开头的字面量，就会被当成控制符注入。计数脚本和生产请求必须用两套策略，别图省事写成同一个。

模型名到 encoding 的映射会「猜」

encoding_for_model 不是查表就完事，它还有一层前缀匹配。源码注释自己承认了这点：

Note that this can match on non-existent models (e.g., gpt-3.5-turbo-FAKE)

本机实测：gpt-3.5-turbo-FAKE 返回 cl100k_base，不报错。更需要注意的是 gpt-oss- 前缀映射到 o200k_harmony，而 OpenAI 模型页现在把 gpt-4o 标成了 Deprecated。写成 gpt-4o 硬编码的项目，等模型下线那天会拿到一个「能跑但算错」的结果。查不到时它倒是老实：

KeyError: 'Could not automatically map my-finetune-model to a tokeniser.
Please use `tiktoken.get_encoding` to explicitly get the tokeniser you expect.'

换算成窗口和钱

官方模型页给 gpt-4o 的规格是「128,000 context window」和「16,384 max output tokens」。按实测比率换算，128,000 个 token 大约能放：

  • cl100k_base：122,775 个汉字
  • o200k_base：188,000 个汉字

同一句意思分别用中文和英文写（英文 297 字符 / 56 token，中文 105 字），中英 token 比是 1.88 倍（cl100k）、1.34 倍（o200k）。这个比值和使用 Prometheus 分位数口径时遇到的情况很像：口径没对齐，后面所有结论都是错的。

按官方标准档单价（截至发稿，美元/百万 token）算 100 万汉字的输入成本：gpt-4o 是 $2.50、gpt-4.1 是 $2.00、gpt-5 是 $1.25、gpt-4o-mini 是 $0.15。于是：

encoding100 万汉字约等于多少 tokengpt-4o 输入成本
cl100k_base1,043,000$2.61
o200k_base681,000$1.70
按 4 字符/token 估算250,000$0.63（错 4.17 倍）

最后一行就是「估算器给了一个让人安心的数字」的典型：$0.63 和 $2.61 之间的差额，不会在账单来之前被任何人发现。这套「默认值看起来合理、实际语义变了」的坑，和 pandas 3.1 写时复制里那五处静默失效的赋值是同一类。

踩坑录：五个真实报错

报错一，默认拒绝特殊 token。 ValueError: Encountered text corresponding to disallowed special token '<|endoftext|>'。这是保护，不是 bug。修法是按用途分开：计数用 encode_ordinary()，生产用显式白名单。

报错二，模型名映射失败。 KeyError: 'Could not automatically map ... to a tokeniser.'。修法是别依赖自动映射，直接用 tiktoken.get_encoding("o200k_base") 写死 encoding，把模型名和 encoding 的对应关系放进配置文件，模型升级时人工确认一次。

报错三，严格解码暴露字节切断。 UnicodeDecodeError: 'utf-8' codec can't decode bytes in position 0-1: unexpected end of data。这条不是要你改 errors=，而是要你意识到「这个 token 单独拿出来不是合法 UTF-8」。

报错四（最危险，因为它不报错），逐 token 解码丢字。 47 字符变 55 字符、16 个替换符、退出码 0。判据只能是「拼接结果是否等于原文」，不能看有没有异常。

报错五，特殊 token 数量失控。 换成 o200k_harmony 后特殊 token 从 2 个涨到 1,091 个，计数脚本如果对特殊 token 一律放行，数字会莫名其妙偏小。

本文的边界

本文所有 token 数都是本机 encoding 计算值，不是 API 返回的 usage。API 侧还会叠加消息包装（角色标记、分隔符）的开销，那部分我没有 API key，未实测，因此不作为数字写入。另外未覆盖：Claude 与 Gemini 的词表、o200k_harmony 的对话模板细节、图片与音频的 token 折算。价格取自官方定价页标准档，截至发稿 2026 年 11 月 1 日，会变。

可以直接抄走的五条

1. 中文按 0.65-0.85 token/字符 估，不要用 4 字符/token；英文继续用 4.1 字符/token 是安全的。

2. 计数和编码用 encode_ordinary()，永远不要在计数路径上开 allowed_special="all"。

3. 流式输出必须按 UTF-8 边界缓冲，不要逐 token decode 再拼。

4. UUID、时间戳、JSON 字段密集的 prompt 单独计数，它们比正文贵一倍以上。

5. 把「模型名到 encoding」写成显式配置，别信 encoding_for_model 的前缀匹配。
