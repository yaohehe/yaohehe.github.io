为什么 n8n 配 Langfuse 而不是 LangSmith？

我把选择过程写出来。这个决定我从 2026 年 5 月纠结到 7 月——核心矛盾是"便利性 vs 数据主权"：

  • **LangSmith Pro** $39/座/月 — 三人小团队 $117/月。Trace 漂亮、自动 eval、Hub prompt 模板丰富。但 2026 价格涨过两次（3 月从 $29 涨到 $39、6 月又调过计费档），数据全在 LangChain 托管，最让我担心的是：跑多模型路由（Anthropic + OpenAI + Ollama 三源）时，LangSmith 的成本归因只算 OpenAI 一家，本地 Ollama 调用直接被忽略。
  • **Helicone** $20/月 Pro — 只覆盖 HTTP 反向代理层，看不到 n8n workflow 节点级 trace。它能告诉你"这次 Anthropic 调用花了多少 token"，但你不知道"这个 token 是 n8n workflow 里哪个节点的哪次重试花的"。
  • **Langfuse 自托管** $5 服务器（4 核 8G VPS） — 5 万单元/月免费额度，超出按 trace 量计费（自托管免费）。数据完全可控。本地 Ollama 0 token 也能在 trace 里如实记录。
  • **Arize Phoenix / LangWatch / Opik** — 各有取舍，Phoenix 偏 ML 实验追踪、LangWatch 偏 prompt 版本管理、Opik 偏 batch eval。n8n workflow 这种"流程编排型"场景都不如 Langfuse 贴合。

最终选 Langfuse v3 自托管：成本可控（$5 vs $117）+ 数据自主（ClickHouse 在我 VPS 上）+ 社区有完整 n8n OTel 教程（n8n community "Deep n8n Observability with OpenTelemetry + Langfuse" 是我跑通链路的第一参考）。还有一个隐藏好处：Langfuse v3 的 ingestion endpoint 直接吃 OTLP，不需要任何 SDK 改造，n8n 内置的 OpenTelemetry 节点零代码就能接进去。

🚀 核心部署步骤

Step 1: 部署 Langfuse v3 自托管

git clone https://github.com/langfuse/langfuse.git
cd langfuse
# v3 用 docker-compose.yml（不是 v2 的 deprecated 文件）
cp .env.prod.example .env
# 修改以下三项必填
sed -i 's/POSTGRES_PASSWORD=.*/POSTGRES_PASSWORD=YOUR_SECURE_PG_PASS/' .env
sed -i 's/S3_ACCESS_KEY=.*/S3_ACCESS_KEY=langfuse-minio/' .env
sed -i 's/S3_SECRET_ACCESS_KEY=.*/S3_SECRET_ACCESS_KEY=YOUR_MINIO_PASS/' .env

docker compose up -d
# 等所有服务 healthy（Postgres / ClickHouse / Redis / MinIO / Langfuse-Web / Langfuse-Worker）
docker compose ps

部署完成后访问 http://your-vps:3000，创建第一个 project，记录 **Public Key** + **Secret Key**（下一步 OTel Collector 用）。

Step 2: 部署 OpenTelemetry Collector

mkdir -p ~/otel-collector && cd ~/otel-collector
cat > otel-collector-config.yaml <<'YAML'
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 10s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 1s
    limit_mib: 512

exporters:
  otlphttp/langfuse:
    endpoint: "http://langfuse-web:3000/api/public/otel/v1/traces"
    headers:
      Authorization: "Basic ${env:LANGFUSE_AUTH}"
    encoding: proto

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp/langfuse]

YAML

# Basic auth = base64(public_key:secret_key)
export LANGFUSE_AUTH=$(echo -n "pk-lf-xxx:sk-lf-xxx" | base64 -w 0)
cat > docker-compose.yml <<'YAML'
version: '3.8'
services:
  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.110.0
    command: ["--config=/etc/otelcol/config.yaml"]
    volumes:
      - ./otel-collector-config.yaml:/etc/otelcol/config.yaml:ro
    environment:
      - LANGFUSE_AUTH=${LANGFUSE_AUTH}
    ports:
      - "4317:4317"   # OTLP gRPC
      - "4318:4318"   # OTLP HTTP
    restart: unless-stopped
YAML

docker compose up -d
docker compose logs -f otel-collector
# 看到 "Everything is ready" 表示就绪

Step 3: 在 n8n 里配置 OpenTelemetry 节点

进入 n8n Web UI → Settings → Variables，新增：

OTEL_EXPORTER_OTLP_ENDPOINT = http://host.docker.internal:4317
# 如果 n8n 和 OTel Collector 在同一 docker network，用服务名
# OTEL_EXPORTER_OTLP_ENDPOINT = http://otel-collector:4317

重启 n8n 容器让环境变量生效：

cd ~/n8n-data && docker compose restart n8n

Step 4: 把 OpenTelemetry 节点拖进 workflow

任何 AI Agent / Anthropic / OpenAI / Ollama 节点后，连一个 OpenTelemetry 节点（n8n 内置）：

  • **Source**: 上游节点的 output
  • **Exporter**: OTLP/gRPC
  • **Endpoint**: `host.docker.internal:4317`（n8n 在 Docker 里访问宿主机的写法；如果 OTel Collector 在同一 network，写 `otel-collector:4317`）
  • **Service Name**: `n8n-workflow-prod`

激活 workflow 后，进入 Langfuse Web UI 的 Tracing → Traces，30 秒内应该看到 trace 流。点击任意 trace 看 token / cost / latency 分布。

💣 踩坑录与常见报错

报错一：OTel Collector 起不来 — "bind: address already in use"

原因：4317 端口被 n8n 内置 OpenTelemetry 节点占用了（n8n 自己也启了 OTLP listener）。两个进程不能共用同一端口——这是 OTel 生态老问题，n8n 启用 diagnostics 时默认监听 4317。

**解决过程**：第一次我尝试 N8N_DIAGNOSTICS_ENABLED=false 重启 n8n，n8n 的 OTLP listener 确实关掉了，但 n8n Web UI 的 "Diagnostics" 页面同时消失了，意味着线上排障没法看 n8n 自身的 metric——属于杀敌一千自损八百。**最终我选了改端口**：

# otel-collector-config.yaml receivers.otlp.protocols.grpc.endpoint: 0.0.0.0:4327
sed -i 's/4317/4327/g' otel-collector-config.yaml
docker compose restart otel-collector

然后 n8n 那边 endpoint 改成 :4327。

报错二：Langfuse v3 报 401 "Invalid credentials"

原因：Basic Auth 的 base64 拼错。常见错误是多了空格或换行——这次坑了我整整一个下午：

# 错误
export LANGFUSE_AUTH=$(echo -n "pk-lf-xxx: sk-lf-xxx" | base64)
# 正确（去掉空格）
export LANGFUSE_AUTH=$(echo -n "pk-lf-xxx:sk-lf-xxx" | base64 -w 0)

-w 0 阻止 base64 自动换行，**这是 90% 的 401 报错根因**。

报错三：trace 进 Langfuse 但字段全是 null

**原因**：n8n OpenTelemetry 节点的 resource attributes 用了 OTel 默认语义（service.name），但 Langfuse v3 期望的字段是 langfuse.session.id / langfuse.user.id / langfuse.tags，OTel Collector 默认不会重映射——trace 进了库但都是空记录，UI 里看像没接成功一样。

**解决**：在 OTel Collector 的 processors 加 attributes/translate：

processors:
  transform:
    trace_statements:
      - context: span
        statements:
          - set(attributes["langfuse.session.id"], attributes["n8n.workflow.id"])
            where attributes["n8n.workflow.id"] != nil

重启 OTel Collector，再触发 workflow，Langfuse 里就能看到按 workflow 分组的 session。

报错四：ClickHouse 启动失败 "Cannot allocate memory"

原因：Langfuse v3 默认 ClickHouse 配 4G，4 核 8G VPS 跑 n8n + Langfuse + OTel + ClickHouse 4G 会 OOM——尤其当 Langfuse Worker 也在抢占内存时，ClickHouse 启动到一半直接被 SIGKILL，日志只留一句 "Cannot allocate memory" 让你猜。

**解决**：修改 docker-compose.yml 里 clickhouse 服务的 deploy.resources.limits.memory: 2G：

services:
  clickhouse:
    image: clickhouse/clickhouse-server:24.3
    deploy:
      resources:
        limits:
          memory: 2G

同时给 OTel Collector 的 memory_limiter.limit_mib 设 256，给 Langfuse Worker 设 1G。**总内存控制在 7G 以内**（留 1G 给系统）。

报错五：OTel Collector 重启后丢一批 trace

**原因**：默认 batch processor 的 timeout: 10s，重启时内存里未发送的 span 直接丢弃。**我当时配置完跑了一周才发现这个坑**——某天服务器 OOM 被监控拉起来重启 OTel Collector，结果下午 1 点到 1 点 10 分之间 47 条 trace 全部丢失，正好是一次批量跑 AI Agent 的时段。

**解决**：加 exporters.file 作为 backup，或把 timeout 调到 30s（容忍重启延迟）：

processors:
  batch:
    timeout: 30s
    send_batch_size: 2048
  # 同时开 file storage 防止 collector crash
  file_storage:
    path: /var/lib/otelcol/storage
    timeout: 10s
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch, file_storage]
      exporters: [otlphttp/langfuse]

📊 Token 计费侧写（Anthropic / OpenAI / Ollama 三源）

n8n 的 OpenTelemetry 节点会把每个 LLM 调用的 gen_ai.usage.input_tokens / gen_ai.usage.output_tokens / gen_ai.usage.total_tokens 自动写入 OTel attribute。Langfuse v3 在 ingestion 端识别这些字段，按你预设的 model 价格表算 USD。

n8n 内置价格表位置：Settings → Usage → Model pricing（自托管需要手动开启 enable_pricing）。把 Anthropic Claude Sonnet 4.5 设成 $3/$15 per 1M tokens 后，trace 里每条 generation 自动出现 cost 字段。

省钱技巧：本地 Ollama 跑的模型（llama3.3 / qwen2.5-coder）成本记为 $0，trace 里能直观看出"哪些 workflow 跑了云端模型、哪些跑了本地"。
