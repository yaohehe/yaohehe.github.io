TLS 证书链验证：verify 的六种失败与一次静默降级

TLS证书链Python

同一张证书，交给不同工具会得到不同答案。Python 的 ssl 抛 unable to get local issuer certificate，openssl verify 打印 error 20，而 requests 只丢一条警告就把 200 返回给你。

这三种结果背后是同一套验证逻辑的四个开关，差别只在默认值。我在本机搭了一条三层的证书链（根 → 中间 → 叶），把能想到的错法逐个跑了一遍。下面每条报错都是原样复制的，实验环境写在第四节。

TL;DR：

  • 缺中间证书是最常见的失败，报错固定是 unable to get local issuer certificate；要补的是签发者那一张，把根证书再发一遍没用
  • 证书只写 CN 不写 SAN 时，Python 和 openssl verify 都会放行；通配符 *.a.test 匹配不到 x.y.a.test
  • ssl.SSLContext(ssl.PROTOCOL_TLS) 的默认是 verify_mode=0（不验）、check_hostname=False，拿它当客户端等于「握手成功、证书一张不验」
  • create_default_context(cafile=…) 是替换不是叠加：给一个 cafile，Windows 上默认的 221 张立刻变 1 张

验证其实只做四件事

很多人把「证书验证」当成一个开关，实际上它是四道互相独立的检查，任何一道不通过都会独立失败，报错文本也各不相同。

第一道是链：叶证书的签名能不能一路验到你信任的那个根。第二道是名字：你连的域名是否出现在证书的 SAN 里。第三道是用途：证书的 extendedKeyUsage 里有没有 serverAuth。第四道是时间：当前时刻是否落在 notBefore 与 notAfter 之间。

这四道检查里，只有第一道需要「链上缺东西」，其余三道都是单张证书内部的事。分清这一点很有用：报错说 unable to get local issuer，问题一定在链上，跟域名、用途、时间都无关。

实验台：三层 CA 与一条真链

环境是 Windows 11 10.0.26300、CPython 3.13.14、OpenSSL 3.5.7（Python 内置同版本）、requests 2.31.0、urllib3 2.5.0。用 openssl 命令行生成了三张证书：自签的根 CA（pathlen:1）、由根签发的中间 CA（pathlen:0）、由中间签发的叶证书（SAN 为 DNS:localhost,IP:127.0.0.1）。

openssl req -x509 -newkey rsa:2048 -nodes -keyout root.key -out root.pem -days 3650 \
  -subj "/CN=Lab Root CA" -addext "basicConstraints=critical,CA:TRUE,pathlen:1"
openssl req -new -newkey rsa:2048 -nodes -keyout inter.key -out inter.csr -subj "/CN=Lab Intermediate CA"
openssl x509 -req -in inter.csr -CA root.pem -CAkey root.key -CAcreateserial -out inter.pem \
  -days 1825 -extfile inter.ext

服务端用 ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER) 起在 127.0.0.1 的随机端口，load_cert_chain() 传哪个文件就发哪几张证书；客户端统一用 ssl.create_default_context(cafile=…)。这样「发什么」和「信什么」两个变量都能单独调。

第一种失败：签发者不在链上

服务端只发叶证书，客户端只信根证书，握手立刻断在验证阶段：

ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
unable to get local issuer certificate (_ssl.c:1032)

把中间证书拼进客户端信任的文件（cat root.pem inter.pem > bundle.pem）之后，同样的服务端、同样的请求，直接返回 200。另一条路是让服务端把中间证书一起发出来（load_cert_chain("leaf.pem" + inter.pem)），客户端仍只信根，也能通过。

命令行给的是同一个诊断，只是编号不同：

$ openssl verify -CAfile root.pem leaf.pem
error 20 at 0 depth lookup: unable to get local issuer certificate
$ openssl verify -CAfile root.pem -untrusted inter.pem leaf.pem
leaf.pem: OK

-untrusted 就是「这张不是根，但它可能在链中间」——它补的正是缺失的第 0 层签发者。

多发一张根证书并不能修好它

一个常见误解是「链不完整就多塞一张」，于是有人把叶证书和根证书拼在一起发出去，中间证书仍然缺席。实测结果和什么都不做一样：

certificate verify failed: unable to get local issuer certificate (_ssl.c:1032)

反过来，把三张全发出去（叶 → 中间 → 根）是能过的。也就是说 OpenSSL 容忍链里多一张根证书，但不接受链里少一张中间证书。这两件事不对称，别用「多发点总没错」的思路排错。

只有 CN 没有 SAN，脚本会放行

这条反直觉。我另签了一张只有 CN=localhost、完全没有 subjectAltName 的叶证书，Python 客户端连 localhost 时通过了；openssl verify -verify_hostname localhost 也给 OK。

把主机名换掉就立刻失败：

$ openssl verify -CAfile bundle.pem -verify_hostname other.test leaf2.pem
error 62 at 0 depth lookup: hostname mismatch

说明 CN 确实被当成了名字来源。这里有一个容易踩的坑：OpenSSL 的 man page 写 X509_check_host() 默认「只对 subjectAltName 匹配，不看 subject DN」，而 Python 和 openssl verify -verify_hostname 走的是 X509_VERIFY_PARAM_set1_host() 这条入口，实测会回退到 CN。两条入口口径不同，读文档时要看清说的是哪一个函数。

实践含义是：脚本能过，不代表浏览器认。SAN 缺失在现代浏览器里是硬性要求，这条属于浏览器实现，本文没有实测，需要做兼容性判断请查对应浏览器文档。

通配符只吃一级

证书 SAN 写 DNS:*.local.test 时，连 x.local.test 通过，连 a.b.local.test 失败：

certificate verify failed: Hostname mismatch, certificate is not valid for
'a.b.local.test'. (_ssl.c:1032)

OpenSSL 文档的原话是「wildcards … match only in the left-most label」（默认）。同一个证书还允许 w*.local.test、*w.local.test 这种带前后缀的部分通配，要放开跨级必须显式加 X509_CHECK_FLAG_MULTI_LABEL_WILDCARDS。写在证书里的一行 * 和你以为的范围，往往差一个层级。

用途写错与时间写错，是两条不同的报错

把叶证书的 extendedKeyUsage 从 serverAuth 改成 clientAuth，服务端照样能起，客户端连上去报：

certificate verify failed: unsuitable certificate purpose (_ssl.c:1032)

时间问题则分两种，方向相反。我签了一张 notBefore 在 2020 年、notAfter 在 2021 年的证书：

certificate verify failed: certificate has expired (_ssl.c:1032)

把 notBefore 挪到 2030 年，同样的链换成：

certificate verify failed: certificate is not yet valid (_ssl.c:1032)

两条报错对应两个完全不同的排查方向：前者要续期，后者通常是本机时钟跑快了，或者容器里的时间没同步。看到 not yet valid 先去查时钟，别去查证书——这一点和时钟语义那篇里 monotonic 与系统时间的差别是两回事。

最危险的一条：PROTOCOL_TLS 默认不验

前三节都是「验证失败」，这一节是「根本没有验证」。

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS)
print(ctx.verify_mode, ctx.check_hostname)   # 0 False

verify_mode=0 就是 CERT_NONE。用这个 context 当客户端去连那张只发叶证书、客户端什么都不信的服务端，结果是 OK：握手成功，拿到响应，一张证书都没验。没有任何警告，也没有异常。

对照一下默认值：

常量verify_modecheck_hostname
PROTOCOL_TLS0（CERT_NONE）False
PROTOCOL_TLS_CLIENT2（CERT_REQUIRED）True
PROTOCOL_TLS_SERVER0（CERT_NONE）False

PROTOCOL_TLS 自 3.10 起已弃用（会发 DeprecationWarning），但它仍然是 SSLContext() 不传参数时的默认值。老代码里那句 ssl.SSLContext(ssl.PROTOCOL_TLS) 不会报错、不会警告到日志里，只是从此不再验证任何证书。

verify_mode 与 check_hostname 的顺序不对称

想手动关掉验证时，顺序会咬人。默认 context 直接改 verify_mode 会被拦：

ValueError: Cannot set verify_mode to CERT_NONE when check_hostname is enabled.

先关 check_hostname 再改 verify_mode 就可以。反过来把 check_hostname 重新打开时不报错也不提示，verify_mode 会被静默抬回 2：

c = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
c.check_hostname = False
c.verify_mode = ssl.CERT_NONE     # 0
c.check_hostname = True           # 无异常
print(c.verify_mode)              # 2

也就是说「关掉验证再打开」不是幂等的：你以为只是切回主机名校验，实际把整条链的验证也一起恢复了。写测试用的宽松 context 时，这一段值得单独写一个断言。

cafile 是替换，不是叠加

create_default_context(cafile=…) 只加载你给的那一个文件，不保留系统默认的信任集：

ssl.create_default_context().cert_store_stats()               # {'x509': 221, 'crl': 0, 'x509_ca': 219}
ssl.create_default_context(cafile="root.pem").cert_store_stats()  # {'x509': 1, 'crl': 0, 'x509_ca': 1}

要在保留默认的前提下追加，得自己调 load_verify_locations()：

ctx = ssl.create_default_context()
ctx.load_default_certs()
ctx.load_verify_locations("root.pem")
print(ctx.cert_store_stats()["x509"])   # 226

221 加 1 得 226 而不是 222，是因为加载路径里本来就存在重复的证书，OpenSSL 按主体去重。这个差值本身不重要，重要的是：为了信任一张内网 CA 而传 cafile，会把公网那 221 张一起丢掉，于是下一句访问外部 HTTPS 的请求才报错，而你还在查内网那张证书。

requests 的 verify 参数走的是同一套逻辑，两个答案都实测到了：

[verify=False]        status 200  警告: InsecureRequestWarning
[verify=root.pem]     SSLError    （缺中间证书）
[verify=bundle.pem]   status 200

verify=False 只是把警告发出来，请求照样成功。这是HTTP 缓存那篇里提过的同一种失败形态：失败被降级成提示，退出码仍是 0。批量任务里这种写法最危险，因为它不会让任何一条命令变红。

Windows 上那 221 张证书从哪来

如果去看 ssl.get_default_verify_paths()，你会得到一个指向 C:\Program Files\Common Files\SSL\cert.pem 的路径——而那个文件在这台机器上不存在。如果据此判断「没有默认证书」，就判断错了：

ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
ctx.cert_store_stats()["x509"]        # 0
ctx.load_default_certs()
ctx.cert_store_stats()["x509"]        # 221
len(ssl.enum_certificates("ROOT"))    # 226
len(ssl.enum_certificates("CA"))      # 33

Python 文档对 load_default_certs() 写得很直白：「On Windows it loads CA certs from the CA and ROOT system stores.」所以 221 张来自 Windows 的证书存储，不是那个 cert.pem 文件。而 create_default_context() 在 cafile / capath / cadata 三个参数都为 None 时会调用它，于是默认就有了 221 张。

顺带一个数量对比：requests 依赖的 certifi 包在这台机器上是 146 张。两套信任集不是同一个集合，也不保证同步——同一张证书可能在 certifi 里、不在系统库里，或者反过来。换用哪个，取决于你希望跟谁保持一致。

排错清单：六条报错对应六个位置

下面六条都按「报错原文 → 它在说什么 → 先查哪里」写，顺序按现场出现频率排。

一、unable to get local issuer certificate

链的问题，不是名字的问题。先看服务端到底发了几张：openssl s_client -connect host:443 -showcerts 里数 BEGIN CERTIFICATE 的行数。实测我的服务端发 2 张（叶 + 中间）时，同一条命令给出 Verify return code: 20 (unable to get local issuer certificate)——因为它默认不信任我本地那个根，这正好说明这条错误码跟「你是谁」无关，只跟「链到不到达一个被信任的锚点」有关。

二、Hostname mismatch, certificate is not valid for 'xxx'

名字不匹配。检查 SAN 里到底有哪些值，别只看 CN。注意通配符只吃最左一级，*.a.test 覆盖不了 x.y.a.test。

三、certificate has expired

看 notAfter。过期证书在握手阶段就被拒，抓包只能看到 alert。

四、certificate is not yet valid

看 notBefore，同时看本机时间。这是唯一一条「大概率不是证书的错」的报错。

五、unsuitable certificate purpose

看 extendedKeyUsage。给客户端签的证书拿去当服务端证书，签名和链都没问题，用途这一道过不去。

六、[SSL: CERTIFICATE_VERIFY_FAILED] ... (_ssl.c:1032) 但完全不知道哪一项错

把 verify_mode 打印出来。如果它是 0，前面五条都不用查，你压根没有在验证。这类故障不会出现在日志里，只会出现在「为什么生产环境的证书换了也没人发现」这种复盘里。

三条命令先把链看清楚

排 TLS 问题时，先跑命令再看代码，省时间。

openssl s_client -connect example.com:443 -showcerts -servername example.com
openssl x509 -in leaf.pem -noout -subject -issuer -dates -ext subjectAltName
openssl verify -CAfile root.pem -untrusted inter.pem -verify_hostname example.com leaf.pem

第一条看服务端实际发了什么，第二条看单张证书的四个字段，第三条在本地把「链 + 名字」一次验完，不用起服务。-servername 别省，它决定服务端给你哪张证书。

另外提醒一句：ssl.match_hostname() 这个函数在 3.13 上已经不存在了（hasattr(ssl, "match_hostname") 实测为 False）。文档记载从 3.7 起主机名匹配改由 OpenSSL 在握手阶段完成，那个纯 Python 的实现随之退场。网上大量「自定义 hostname 校验」的代码片段还在调用它，迁移到 3.12 之后会直接 AttributeError。

常见问题

Q：我把根证书装进系统信任库了，为什么 Python 还报错？

因为 create_default_context(cafile=…) 一旦传了参数就不读系统库。要么不传参数让它读系统库，要么用 load_verify_locations() 叠加。

Q：客户端信任文件里放根证书还是放中间证书？

放根（信任锚），中间证书负责把叶接上去。两者都放最省事，代价是中间证书轮换时你要跟着换文件。

Q：为什么 verify=False 的请求还能成功？

因为在 TLS 层它把 verify_mode 降成了 CERT_NONE，相当于是「不验证但继续」。requests 只会发一条 InsecureRequestWarning，状态码照旧。pip 构建产物那篇里「装成功了但跑的是旧代码」是同一种形态：成功信号与真实状态脱钩。

Q：内网自签证书怎么让 Python 认？

把自签 CA 作为信任锚传给 cafile，并确认证书的 SAN 里有你要连的域名（IP 连接则要有 IP SAN）。只写 CN 在 Python 里能过，但你同时还要面对浏览器和其他客户端。

Q：这和 TCP 连接失败有什么区别？

TLS 验证失败时 TCP 已经连上了，三次握手成功、端口是通的。判活那一层的问题看TCP 那篇，证书的问题都在握手阶段，两者的报错层次完全不同。
