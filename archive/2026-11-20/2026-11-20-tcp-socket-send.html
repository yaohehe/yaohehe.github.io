TCP socket 判活八条：send 说成功，连接其实已经断了

TCPsocket传输层

我实际在本机跑了一遍 TCP 连接判活的实验：一个回环服务端、一个客户端，逐个制造「对端已经走了」的场面，然后看 Python 到底报什么。环境是 Windows 11 build 26300、CPython 3.13.14，全部连 127.0.0.1，不经过任何路由器。

结论不体面：send 返回成功几乎证明不了任何事，报什么错还取决于你把超时设成几秒。下面八条都能在三四十行代码里复现，脚本我在文末给出。

TL;DR：判活的顺序是「先看 recv 拿到空串还是异常，再考虑写探测」，而不是反过来。

  • 对端已关闭时，第一次 send() 依然返回发送字节数，第二次才抛 ConnectionAbortedError（10053）
  • 对端带着未读数据关闭，recv() 抛 ConnectionResetError（10054），不是返回空串
  • shutdown(SHUT_WR) 只是半关闭：对端收到空串，你还能继续读；此后 send() 抛 10058
  • 连一个没人监听的端口，超时设 1 到 2 秒时你拿到的是 TimeoutError，不是 ConnectionRefusedError
  • SO_REUSEADDR 在 Windows 上会让端口可被第二个进程抢绑，行为与 Linux 相反
  • SO_KEEPALIVE 出厂关闭，Windows 默认要 2 小时才发现死连接
  • settimeout(0) 不是「零超时」，是切到非阻塞模式，报 10035
  • 流没有消息边界，两次 send() 会被一次 recv() 读走

一、send 返回 1，连接其实已经断了

服务端 accept 之后立刻 close，一个字节都不读。客户端第一次 send(b"x") 返回 1，第二次 send(b"y") 抛 ConnectionAbortedError，winerror 10053。

原因是 send() 只承诺「数据交给了内核发送缓冲」，不承诺「对端收到了」。第一次写与对端关闭在时间上错了半个来回，数据先落进缓冲；第二次写时本机已经知道这条连接废了，于是中止。

Python 官方文档在 sendall() 条目下写得很直白：出错时「there is no way to determine how much data, if any, was successfully sent」。send() 连这句都不给。微软的错误码表把 10053 定义为「An established connection was aborted by the software in your host computer」——注意是「your host」，也就是本机主动放弃，而不是对端拒绝。

所以判活不能靠写。要么写完之后等一个回执，要么走下一节的读。

二、recv 返回空串和抛 10054 是两件事

两个对照实验：

  • 服务端 accept 后先 sendall(b"bye") 再 close，客户端 recv 依次得到 b'bye' 与 b''，全程 0.0001 秒
  • 服务端 accept 后不读、直接 close，客户端 recv 抛 ConnectionResetError 10054

同样是「对端关了」，一个有礼貌（FIN），一个没礼貌（RST）。区别在于关闭时接收缓冲里还有没有未读数据。

RFC 9293 第 3.5.2 节给的一般规则是「reset (RST) is sent whenever a segment arrives that apparently is not intended for the current connection」，并且紧接着强调「A reset must not be sent if it is not clear that this is the case」——协议栈不会无缘无故发 RST，出现了就说明它认为这条连接上还有不该在的东西。

这条对代码结构影响很大。如果你的读循环写成 while True 里 data = sock.recv(4096)、空串就 break，碰到 RST 时是异常退出而不是 break；如果外层 except 只捕 OSError 打了个日志，你会在监控上看不出「对端是正常收尾还是被打断」。

三、shutdown 是半关闭，close 是拆整条

shutdown(SHUT_WR) 之后：对端 recv 拿到 b''（收到 FIN），而本端还能继续读——实测读回了对端在 FIN 之后补发的 b'resp-after-fin'。这条正是「请求-响应」协议里最该用的收尾顺序：先关写方向告诉对方「我说完了」，再读完剩下的响应，最后 close。

但半关闭之后继续写会立刻失败：send() 抛 BrokenPipeError，winerror 10058，官方定义是「A request to send or receive data was disallowed because the socket had already been shut down in that direction with a previous shutdown call」。重复调用 shutdown(SHUT_WR) 则静默成功，不报错。

还有一个更反直觉的：shutdown(SHUT_RD) 之后不是「读到空串」，而是 recv 和 send 双双抛 10053。也就是说这个调用在本机把连接搞得比自己预想的更糟。

微软那篇讲优雅关闭的文档把 close 的行为说清楚了：closesocket 会隐式触发一次关闭序列，默认是「graceful shutdown, immediate return」——「the application has no way of knowing when (or whether) the graceful shutdown sequence actually completes」。想让对端确实收全，就得显式 shutdown，不能指望 close。

四、连接被拒要两秒才到，于是错误类型取决于你的超时

这是本篇最值得带走的一条。

create_connection(("127.0.0.1", 未监听端口), timeout=2) 抛的是 TimeoutError，不是 ConnectionRefusedError。把同样的调用换成 timeout=25，2.05 秒时抛 ConnectionRefusedError（10061），IPv6 回环 ::1 也是 2.04 秒。

也就是说：在 2 秒以内，本机拿不到「积极拒绝」这个答案。真实原因是回环上的 SYN 也要走一次重传计时，拒绝报文到达在 2 秒量级。

后果很实际：你写了 except ConnectionRefusedError 打「服务没起来」，而实际超时设的是 1 秒或 2 秒，那么这条分支永远不会命中，日志里全是 TimeoutError，然后你去查网络、查防火墙，其实只是服务没起。

判据改成两条：一是超时至少留 3 秒再判「拒绝」；二是 TimeoutError 与 ConnectionRefusedError 分开处理，别合并成一个「连不上」。

五、SO_REUSEADDR 在 Windows 上是反的

Linux 上的肌肉记忆是：服务重启时端口还在 TIME_WAIT，绑不上，加 SO_REUSEADDR 就好。Windows 上这套会出事。

实测四种组合，端口都是 127.0.0.1 上已经被第一个 socket 监听的那个：

第二个 socket 的选项结果
什么都不设OSError 10048，地址已被占用
只自己设 SO_REUSEADDRPermissionError 10013
两个 socket 都设 SO_REUSEADDR绑定成功
第一个设 SO_EXCLUSIVEADDRUSE，第二个设 SO_REUSEADDRPermissionError 10013

第二种最坑：只给「后来者」加选项，反而从 10048 变成 10013（权限不足），错误码换了，原因却是同一个。微软 bind 文档解释 10048 的原话是「a process on the computer is already bound to the same fully qualified address and the socket has not been marked to allow address reuse with SO_REUSEADDR」——注意条件挂在「已经在用的那个 socket 有没有被标记为允许复用」上。

两边都设会绑定成功，但连接仍然被第一个 accept 接走（实测连续两次 accept，命中第一个）。这不是「共享端口」，这是先绑的人让位规则不明确。

微软 SO_EXCLUSIVEADDRUSE 页面的原话说得更直接：这个选项「prevents other sockets from being forcibly bound to the same address and port, a practice enabled by the SO_REUSEADDR socket option」，而且「Such reuse can be executed by malicious applications to disrupt the application」。

所以 Windows 上的服务端该设的是 SO_EXCLUSIVEADDRUSE（常量值 -5，Python 里 socket.SO_EXCLUSIVEADDRUSE 可用），而不是照抄 Linux 的 SO_REUSEADDR。

另外补一条对照：主动关闭连接之后，同一个端口立刻重绑，设与不设 SO_REUSEADDR 都成功——Windows 并不像 Linux 那样因为 TIME_WAIT 卡住重绑。所以「Linux 上必须加的那行，Windows 上加了反而危险」。

六、SO_KEEPALIVE 出厂关闭，默认两小时才发现

新 socket 的三个默认值：SO_KEEPALIVE 为 0、TCP_NODELAY 为 0、收发缓冲各 65536 字节。

微软 SO_KEEPALIVE 页写明「The SO_KEEPALIVE option for a socket is disabled (set to FALSE) by default」，并且「For TCP, the default keep-alive timeout is 2 hours and the keep-alive interval is 1 second」。

两小时。一条 NAT 超时、对端断电、网线被拔的长连接，在默认配置下你要等两小时才会收到错误。如果你的服务是「订阅推送」「长轮询」「WebSocket 上游」，这等于没有判活。

好消息是 Windows 上这三个旋钮现在能直接设：实测 TCP_KEEPIDLE、TCP_KEEPINTVL、TCP_KEEPCNT 都设成 30，读回来都是 30。Python 文档的 changelog 也记录了支持时间：3.6.5 起 Windows 支持 TCP_KEEPCNT，3.7 起支持 TCP_KEEPIDLE 与 TCP_KEEPINTVL。

设之前先 SO_KEEPALIVE 置 1，否则那三个参数没有作用对象。

七、settimeout(0) 不是「零超时」

settimeout(0) 之后 recv() 抛 BlockingIOError，winerror 10035。这不是超时，是「现在没数据」——官方文档原话：「If zero is given, the socket is put in non-blocking mode」；并且非阻塞模式下的错误「is unfortunately system-dependent」。

settimeout(0.3) 才是超时模式：实测 0.303 秒后抛 TimeoutError，没有 errno 也没有 winerror，消息就是 timed out。

顺手一个坑：TimeoutError 是 OSError 的子类。你的 except OSError 会把超时、重置、拒绝一气吞掉，日志里只剩一句「网络错误」。

三种模式的分工，官方文档说法是：阻塞模式一直等到完成或系统返回错误；非阻塞模式「cannot be completed immediately」就失败；超时模式在指定时间内没完成就抛超时异常。选错一个，行为就完全不同。

八、流没有消息边界

客户端连续两次 sendall，各 100 字节；服务端一次 recv(1000) 拿到 200 字节，第一个是 b'A'、最后一个是 b'B'。反向也成立：recv(1) 三次拿到 b'h'、b'e'、b'l'。

TCP 是字节流，send 的次数与 recv 的次数没有任何对应关系。所有「客户端一条一条发，服务端一条一条收」的代码，都是在赌数据别粘在一起——而 Nagle 默认就是开的（TCP_NODELAY 为 0），它专门帮你粘。

还有一个量级感：非阻塞模式下一直 send 到阻塞为止，本机吸收了 458,752 字节才报 10035，占我准备的 64 MB 的 0.68%。也就是说「写成功」这件事在缓冲还没满的时候几乎必然发生，跟对端在不在没有关系。

Troubleshooting：七个报错原文与改法

  • ConnectionAbortedError: [WinError 10053] —— 本机中止。通常出现在对端已关闭后继续写。改法：写之前先读一次，或对写操作做「写-回执」配对
  • ConnectionResetError: [WinError 10054] —— 对端 RST。常见于对端带未读数据关闭、进程被杀。改法：把 RST 与正常 EOF 分开处理，别都当「连接结束」
  • BrokenPipeError: [WinError 10058] —— 该方向已 shutdown。改法：检查是不是在 shutdown(SHUT_WR) 之后还有写操作
  • OSError: [WinError 10048] —— 地址被占用。改法：先确认上一个进程真的退出了；Windows 上不要靠 SO_REUSEADDR 绕过
  • PermissionError: [WinError 10013] —— 绑定被拒。Windows 上常见原因是对端 socket 已用 SO_EXCLUSIVEADDRUSE，或你自己加了 SO_REUSEADDR 去抢一个被独占的端口
  • BlockingIOError: [WinError 10035] —— 非阻塞模式没数据。改法：换成非零超时，或配合 select
  • TimeoutError: timed out —— 超时模式到点了。若目标是判「服务没起来」，把超时提到 3 秒以上，才可能拿到 10061

一份可以直接抄的判活顺序

import socket

def peer_state(sock, timeout=3.0):
    sock.settimeout(timeout)
    try:
        data = sock.recv(1, socket.MSG_PEEK)
    except TimeoutError:
        return "alive_silent"
    except ConnectionResetError:
        return "reset"
    except OSError:
        return "broken"
    if data == b"":
        return "closed_by_peer"
    return "alive_with_data"

要点是用 MSG_PEEK 只看不取，不破坏后续读；recv 返回空串是 FIN，抛 10054 是 RST，超时才是「还活着但没说话」。写完这段再考虑要不要发心跳——顺序反过来就会踩第一节的坑。

本文的边界

  • 只测 Windows 11 build 26300 与 CPython 3.13.14，Linux 与 macOS 未测；SO_REUSEADDR 与 10013 的结论明确不适用于 Linux
  • 只跑回环，没有跨路由、丢包、NAT 超时与中间设备，真实网络的 RST 来源会更杂
  • keepalive 的 2 小时探测没有等（等不起），引用的是微软文档口径
  • 没有涉及 TLS、HTTP 层；HTTP 缓存与 ETag 的静默分歧我在另一篇里单独测过，可以配合看：HTTP 缓存语义
  • 跨进程的端口与文件互斥是另一个层，见文件锁与跨进程互斥

判活这件事，本质是「你相信哪一层」。内核缓冲、协议栈状态、对端应用，三层各有各的答案，而 send 返回的那个数字只代表最里面那一层。顺带说一句，同一类「返回值不等于结果」的坑在构建链上也有，比如 pip install 报成功却跑旧代码。

FAQ

Q：本地测一直正常，线上偶尔 10054，是代码问题吗？

更可能是中间设备。10054 表示收到了 RST，而 RST 不只由对端应用产生：负载均衡的空闲超时、NAT 表项过期都可能让一侧收到 RST。判断办法是看 RST 出现的时间间隔是否稳定——固定在第 N 分钟出现，基本就是中间设备的空闲回收。

Q：sendall() 成功，是不是就代表对端收到了？

不是。它只保证数据全部交给了内核发送缓冲。官方文档写的是「continues to send data from bytes until either all data has been sent or an error occurs」，这里的 sent 指本机送出，不含对端确认。要确认真实送达，只能等应用层回执。

Q：Windows 上到底该设 SO_REUSEADDR 还是 SO_EXCLUSIVEADDRUSE？

服务端设 SO_EXCLUSIVEADDRUSE。实测第二个进程只要两边都开 SO_REUSEADDR 就能绑上同一个端口，这既是调试时的干扰源，也是被劫持的入口。

Q：keepalive 调到 30 秒会不会把好好的连接断掉？

TCP_KEEPCNT 决定探测几次才判死，三项一起设才完整。只把 TCP_KEEPIDLE 调小、TCP_KEEPCNT 保持默认，探测会持续更久而不是更快失败。另外 keepalive 由内核发空包，某些中间设备会把它当异常流量，这一点要结合自己的链路验证。
