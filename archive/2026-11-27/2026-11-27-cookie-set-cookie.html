Cookie 作用域：一个 Set-Cookie 要过的六道关

cookieHTTP 语义调试排查

为了复现一个「登录明明成功了，下一个请求还是游客」的问题，我在本机起了两个 HTTP 服务，一个占 8101，一个占 8102。同一份代码、同一个 CookieJar 对象：8101 上设的会话 cookie，8102 的请求里照样带着；换成路径，/app/v1/other 带，/app/v1x 不带。

这两件事都不算 bug，它们是 RFC 6265 写明的行为。可排错文章很少把它们摆在一起讲，于是「cookie 丢了」最后总是归结成一句「清一下浏览器缓存」。

本文只回答一个问题：服务端发了 Set-Cookie 之后，下一次请求到底会不会带上它。

数字全部来自本机实测：Windows 11 10.0.26300、CPython 3.13.14、标准库 http.cookiejar（2,123 行）、requests 2.31.0。被测对象是标准库与 requests，不是浏览器；凡涉及浏览器的地方一律引官方文档原文并单独标注。本文不含任何联盟推广链接。

判据只有一份：请求前要过四道筛选

RFC 6265 §5.4 规定，生成 Cookie 头之前，先从存储里挑出满足全部条件的记录：host-only 的必须与请求主机完全相同，其余走 domain-match；请求路径要 path-match；secure-only 为真时请求必须是安全协议；http-only 只在非 HTTP API 场景下排除。选中之后再排序，路径长的在前，等长时创建早的在前，最后拼成 name=value; name=value 的唯一一个请求头。

标准库把这套规矩做成了一个策略对象。DefaultCookiePolicy 有 13 个构造参数，其中三个默认值决定了后面大半的行为：strict_domain=False、strict_ns_domain=DomainLiberal（等于 0，所有 Netscape 域严格性开关全关）、strict_ns_set_path=False。

换句话说，「标准库比浏览器松」不是形容词，是这三行默认值。

第一关：Domain 不写，作用域反而更大

先看 jar 里存了什么。请求 http://127.0.0.1:8101/set 时下发两种 cookie，一种不带 Domain，一种写 Domain=127.0.0.1。读回来是两条记录：

  • 不带的：domain 为 127.0.0.1，domain_specified=False，即 host-only
  • 带 Domain 的：domain 变成 .127.0.0.1，前面被加了一个点，domain_specified=True

按 RFC 6265 §5.4，host-only 的 cookie 只有「请求主机与 cookie 的 domain 完全相同」才会被发出，这是比 Domain 写法更严的一档。但标准库默认策略不这么判。

我用伪造的 Request 对象直接调 policy.return_ok()，绕开 DNS 与网络，只测匹配逻辑本身。4 个主机 × 2 种策略共 8 个组合，结果分成两栏：

请求主机DomainLiberal（默认）DomainStrictNonDomain
example.com发发
sub.example.com发不发
a.b.example.com发不发
notexample.com不发不发

只要把 strict_ns_domain 从默认的 0 改成 DomainStrictNonDomain，行为立刻和 RFC 对齐。默认值这一栏，源码自己的注释写得很直白（Lib/http/cookiejar.py 第 1171 行）：strict check of non-domain cookies: Mozilla does this, MSIE5 doesn't。

官方文档对 DomainStrictNonDomain 的解释是：没有显式写 domain 属性的 cookie，只能返回给设置它的那个域。也就是说这个开关是存在的，只是默认关着。

这里的杀伤力在共享域名上：多租户系统里 A 客户在 a.example.com 设了一个没写 Domain 的会话 cookie，默认策略下它会不会被发到 b.example.com，取决于你用哪个客户端。浏览器不会，标准库会。

第二关：端口根本不在作用域里

8101 上设的 cookie，在 8102 的请求里完整带上，两条都在。这不是标准库偷懒，是 RFC 6265 的属性表里压根没有端口这一项——§5.4 的筛选条件只有域名、路径、协议三项，RFC 2965 时代的 Port 属性已被删除。

于是本机最常见的两种翻车都从这里来：localhost:3000 与 localhost:8080 互相覆盖同名 session；前端 dev server 代理到后端时，两边 cookie 互相污染。

一个不需要改代码的办法：127.0.0.1 与 localhost 是两个不同的 host，cookie 不互通。想彻底隔离，用 host 区分而不是用端口区分。

第三关：Path 不写时，默认是上一级目录

在 /app/v1/settings 上设一条不带 Path 的 cookie，jar 里存的 path 是 /app/v1，不是 /。

RFC 6265 §5.1.4 的算法写得很清楚：取请求 URI 的路径，去掉最右边那个 / 之后的所有内容。所以「上一层目录」才是默认值，/ 是很多人想当然的答案。

拿这个 path 去请求五个地址，实测结果：

请求路径带不带
/app/v1/other带
/app/v1带
/app/v1x不带
/app/v2/x不带
/不带

显式写 Path=/foo 时边界更清楚：/foo 带、/foo/bar 带、/foobar 不带、/foo2 不带。path-match 要求「前缀匹配」并且「多出来的第一个字符必须是 /」，/foobar 多出来的是 b，所以不匹配。

有一处文档口径值得记一笔：MDN 的例子说 https://example.com/docs/Web/HTTP/index.html 的默认 path 是 /docs/Web/HTTP/，带尾斜杠；RFC 算法给出的是不带尾斜杠的 /docs/Web/HTTP。两种写法 path-match 出来的集合相同，实测标准库跟的是 RFC 那一版。

真实的翻车场景是 SPA：登录接口在 /api/login，前端路由在 /。不带 Path 时 cookie 的作用域只有 /api，前端页面里的 document.cookie 一个字都看不到，但接口请求一切正常——于是问题被描述成「前端拿不到登录态」，其实是服务端少写了一行。

第四关：Secure 的 cookie 存得进、发不出

用 http 下发一条带 Secure 的 cookie，标准库照收不误：jar 里 secure 为 True，discard=True、expires=None。然后同一个 jar 再发 http 请求，这条 cookie 一次都不会出现。

既没有异常，也没有日志。它就在 jar 里躺着，等着某个 https 请求来取。

浏览器在这件事上更严格。MDN 的 Set-Cookie 页原文写着：Insecure sites (http:) cannot set cookies with the Secure attribute. 也就是说 http 页面下发的 Secure cookie 会被整条忽略，连存都不存。标准库存下来但永不发出，浏览器直接丢掉——两种实现，同一个结果，两种排查路径。

顺带一个容易误解的点：RFC 6265 §4.1.2.5 自己就说了，Secure 只保护机密性，不保护完整性，主动攻击者可以从非安全通道覆写 Secure cookie。把它当成「不可篡改」是过度解读。

第五关：同一个名字可以同时存在几份

cookie 的唯一键是「名字 + 域名 + 路径」，三者任一不同就是两条记录。所以 sid 完全可以在 / 和 /app 各存一份：

  • jar 里两条：sid=root（path /）与 sid=app（path /app）
  • 请求 /app/x 时发出的头是 sid=app; sid=root，长 path 在前
  • dict_from_cookiejar() 只给你 {'sid': 'app'}，另一份被静默丢掉
  • CookieJar 对象直接下标会报 TypeError: 'CookieJar' object is not subscriptable，因为它没有实现 __getitem__

这个顺序是 RFC 推荐的（SHOULD，不是 MUST）：路径长的在前，等长时创建早的在前。历史上有服务端依赖过这个顺序，所以它至今被当作事实标准。

服务端读第一个值，就等于读到了 path 更长、更具体的那个。如果应用在 / 上写登出逻辑、把 sid 清成空，/app 上的那份还活着，下一次进 /app 就又被认回来——「退出登录后刷新一下又登进去了」通常就是这条。

同一次响应里发两个同名同 path 的 Set-Cookie 则是另一种结果：只有后一个活下来，jar 里仍然只有 1 条。

第六关：过期解析，两位数年份会把你送回未来

先确认优先级。同时下发 Max-Age=3600 和 Expires=Thu, 01 Jan 1970 00:00:00 GMT，RFC 6265 §4.1.2.2 原文是 the Max-Age attribute has precedence，实测 jar 里存活，expires 变成当前时间加 3600 秒。Max-Age=0 则是立刻删除，MDN 的说法是「零或负数立即过期」。

真正麻烦的是解析失败。下面几种写法都不是全部合法，结果分两类：

  • Expires=garbage、Expires=Thu, 32 Jan 2030 00:00:00 GMT：解析失败，expires=None、discard=True，静默退化成会话 cookie
  • Expires=Thu, 01 Jan 1970 00:00:00 GMT：正常解析成过去时间，删除生效
  • Expires=Thu, 01 Jan 70 00:00:00 GMT：两位数年份，解析成功，但结果不是 1970

最后一条是本文最反直觉的发现。cookiejar 的 http2time() 文档字符串写着：年份只有两位时，选择「让这个年份最接近当前日期」的那个世纪。实测今天（2026-11-27）的边界落在 76 与 77 之间：

  • 70 解析成 2070-01-01
  • 76 解析成 2076-01-01
  • 77 解析成 1977-01-01

而 RFC 6265 §5.1.1 的规则是死的：70 到 99 加 1900，0 到 69 加 2000。按 RFC，70 应该解析成 1970，cookie 立即过期。按标准库，它活到 2070。

100 个两位数年份取值里有 7 个（70 到 76）和 RFC 不同，也就是 7% 的取值会在「用过期时间删 cookie」这个经典手法上失效。老代码里 Expires=Thu, 01 Jan 70 00:00:00 GMT 是常见的删除写法，实测跑完这条之后，jar 里那条 cookie 的 expires 变成 3155760000，删除失败，而且不报错。

更要紧的是这个边界会漂移：它是按「离当前日期最近」算的，随着年份推移，分歧区间会整体后移。今天测出来的结论，过几年就不成立。

没有公共后缀表，cookie 会发给别人的子域

浏览器拒绝把公共后缀当 Domain。MDN 原文：Domain cannot be a public suffix such as com, co.uk, or github.io，越界的 cookie 会被直接忽略。

标准库没有这张表。我在源码里搜 publicsuffix 与 public_suffix，命中 0 次。实测结果：

  • 从 user.github.io 下发 Domain=.github.io，set_ok 返回 True
  • 这条 cookie 对 other.github.io 返回 True
  • 对 evil.github.io 也返回 True
  • 从 shop.example.co.uk 下发 Domain=.co.uk，set_ok 同样返回 True

也就是说，在共享域托管（*.github.io、*.herokuapp.com、*.netlify.app 这类）上跑脚本时，一个租户的 cookie 可以被发到另一个租户的站点。浏览器挡住了这条，脚本没有。

需要挡住时，要么在策略里挂 blocked_domains，要么在发送前自己核一遍域名后缀，别指望库替你做。

SameSite 与 __Host-：标准库一个字都不认

同样在源码里数：samesite 命中 0 次、SameSite 0 次、__Host- 0 次、__Secure- 0 次。

实际行为对得上：

  • 下发 SameSite=Strict 的 cookie，它只落在 Cookie 对象的 _rest 字典里（{'SameSite': 'Strict'}），请求时没有任何额外判断
  • 带 Referer: https://evil.example/ 与 Sec-Fetch-Site: cross-site 的请求，这个 cookie 照发
  • 下发 __Host-h=1（既无 Secure，也没有 Path=/）被接受，并正常回发
  • 下发 __Secure-s=1（没有 Secure 属性）也被接受，并正常回发

而 MDN 对 __Host- 的要求是三条同时满足：必须 Secure、必须由 HTTPS 页面设置、不得带 Domain 且 Path 必须为 /。代码里用前缀做「这个 cookie 绑死在当前主机」的假设，在浏览器里成立，在脚本里不成立。

对写爬虫、写接口测试、写 SSO 联调脚本的人来说，这条意味着：你在浏览器里验证过的 CSRF 防护，换成脚本跑同一套流程，防护层根本不存在。

排错：五个真实报错与两条静默改写

下面五条都是这次实测中撞出来的原始报错，附上各自的原因。

一、直接调策略对象时抛 AttributeError: 'DefaultCookiePolicy' object has no attribute '_now'

return_ok() 内部会调 cookie.is_expired(self._now)，而 _now 是 CookieJar 在构造时注入给策略的。单独 new 一个策略来测匹配逻辑，必须自己补 policy._now = lambda: 0，否则第一行就抛。

二、TypeError: 'CookieJar' object is not subscriptable

标准库的 Jar 不支持 jar['sid']。要按名字取，得用 requests 的 RequestsCookieJar，或者自己遍历。

三、CookieConflictError: There are multiple cookies with name, 'sid'

用 requests 的 Session 时，同名 cookie 有两份（不同 path），ss.cookies['sid'] 就会抛这个。要么指定 domain 与 path，要么改用 dict_from_cookiejar()——但后者会静默丢掉一份，只在调试时可靠。

四、UnicodeEncodeError: 'latin-1' codec can't encode characters in position 3-4

jar 里存了一个非 ASCII 值（比如中文），发请求时 http.client 用 latin-1 编码请求头，整条请求直接失败。这个报错发生在发送阶段，不在解析阶段，堆栈里看不到 cookie 字样，很容易误判成 URL 编码问题。解决办法是在写入时就做百分号编码，别把原始 UTF-8 塞进 cookie 值。

五、LoadError: '...' does not look like a Netscape format cookies file

MozillaCookieJar.load() 读到一个不是 Netscape 格式的文件时抛这个。文件头必须是 # Netscape HTTP Cookie File，自己拼 cookie 文件时最容易漏这一行。

另外两条静默改写，不报错但会改数据：

  • 值里带分号：Set-Cookie: v=a;b; Path=/ 实际存进去的是 v=a，分号被当成属性分隔符，后半截静默消失
  • 名字里带空格：Set-Cookie: bad name=1 被接受，请求头里原样发出 bad name=1，服务端多数解析器会把它当成垃圾丢弃

三十行脚本：把作用域一次看清

排查「cookie 为什么不发」时，先把 jar 摊开，再逐条对照请求路径算一遍，比猜快得多。

import urllib.request
import http.cookiejar as cj

policy = cj.DefaultCookiePolicy(
    strict_ns_domain=cj.DefaultCookiePolicy.DomainStrictNonDomain,
)
jar = cj.CookieJar(policy)
jar._policy._now = jar._now = 0  # 只看结构时固定时间，避免过期项被偷偷剔掉

def dump(jar):
    for c in jar:
        print(f"{c.name}={c.value}  domain={c.domain} host_only={not c.domain_specified} "
              f"path={c.path} secure={c.secure} expires={c.expires} rest={c._rest}")

def will_send(jar, url):
    req = urllib.request.Request(url)
    return [c.name for c in jar if jar._policy.return_ok(c, req)]

先把 dump(jar) 的输出贴出来，再对可疑 URL 调 will_send()。两行输出就能回答三个问题：cookie 在不在 jar 里、作用域算出来是哪一层、以及它为什么被判为不该发。

常见问题

Q：本机开发为什么两个端口会互相覆盖 session？

因为 cookie 作用域里没有端口这一维。RFC 6265 §5.4 的筛选条件只有域名、路径、协议。想隔离，用不同 host（127.0.0.1 与 localhost）而不是不同端口。

Q：服务端设了 cookie，浏览器开发者工具里也能看到，为什么接口请求还是没带上？

先看两条：Path 是不是落在了接口所在的目录之外，Secure 是不是在 http 下发的。前者表现为「页面能看到、请求不带」，后者表现为「存进去了但一次都不发」。两者都不报错。

Q：为什么用 Expires=Thu, 01 Jan 70 00:00:00 GMT 删不掉 cookie？

标准库按「离当前日期最近的世纪」解释两位数年份，70 被解释成 2070 而不是 1970。删 cookie 用 Max-Age=0，或者写完整的四位年份。

Q：把 Domain=.example.com 写成 Domain=example.com 有区别吗？

在标准库与浏览器里都没有实质区别，前导点会被忽略。真正有区别的是写与不写，即 domain 属性存在与否，那决定了 host-only 与 domain cookie 两档作用域。

结论：作用域是四个属性算出来的

把六道关收拢成一句话：cookie 会被发到哪个请求，由「域名属性 + 路径 + Secure + 过期时间」四样东西共同决定，再加上一条同名冲突时的排序规则。服务端写了什么，不等于客户端会照做——中间隔着一层策略默认值。

这次实测里，标准库与 RFC 或 MDN 不一致的地方有五处：host-only 默认发子域、没有公共后缀表、认两位年份用最近世纪、http 下收下 Secure cookie、完全不认 SameSite 与 cookie 前缀。每一处单独看都是小事，叠在一次登录链路上就是「明明设了却没带上」。

相邻的几层语义，站内已经写过了：响应头能活多久看 HTTP 缓存与 ETag，连接还在不在看 TCP 判活，证书链验了哪几件事看 TLS 证书验证。cookie 这一层比它们都靠后：它假设前两层都通了，然后决定这次请求要不要带上凭证。

如果只从本文带走一条，就这条：DefaultCookiePolicy() 的默认值不是「安全默认」，而是「兼容 2000 年代的浏览器」。用它做接口测试可以，用它模拟真实用户不行。
