URL 拆开再拼回去：urllib.parse 的七处静默改写

PythonURL 解析Web 开发

上周排查一个收录问题：站点的 sitemap 里出现了两条「不同」的分页链接，一条带尾斜杠、一条不带，Google 把两条都收了，canonical 却只有一个。生成器里只有一行 urljoin(base, page)，看上去人畜无害。

我把这一行单独拎出来跑了六十多条用例。结论是：urllib.parse 从不抛异常地告诉你「我改了一个字符」，它只是安静地给出一个看起来一样、实际不一样的字符串。而这个问题最难的地方不在解析，在于解析和序列化是两个函数，中间任何一个默认值都会动手。

下面七处都是我在 CPython 3.13.14、Windows 11 10.0.26300 上实际跑出来的输出，原样贴结果，不推断。凡是与 RFC 3986 有出入的地方，我把两边原文都列出来，你自己判断该信谁。

一、尾斜杠：base 的最后一段会被吃掉

这是最常见的一处。urljoin 的路径合并规则不是「拼字符串」，而是「把相对路径接在 base 除最后一段之外的部分后面」。本机实测：

urljoin('http://a/b/c/d', 'e')   -> http://a/b/c/e
urljoin('http://a/b/c/d/', 'e')  -> http://a/b/c/d/e
urljoin('http://a/b', 'c')       -> http://a/c
urljoin('http://a/', 'c')        -> http://a/c

http://a/b 拼 c 得到 http://a/c，b 那一段直接没了。原因写在 RFC 3986 5.2.3 里，原文是「appended to all but the last segment of the base URI's path」——除非 base 以斜杠结尾，否则最后一段被当作「文件」，只能被替换。

所以凡是把「目录」当 base 用，必须自己补尾斜杠。反过来，如果 base 是 http://a/b/c/d;p?q 这种带查询串的地址，?y 这种只有查询的引用会保留原路径，只换查询部分：

urljoin('http://a/b/c/d;p?q', '?y')  -> http://a/b/c/d;p?y
urljoin('http://a/b/c/d;p?q', '#s')  -> http://a/b/c/d;p?q#s
urljoin('http://a/b/c/d;p?q', '')    -> http://a/b/c/d;p?q

上点号也一样按规则走，而且不会越过根：urljoin('http://a/b/c/d;p?q', '../../../g') 得到 http://a/g，退到根就停。RFC 3986 5.4.2 的异常示例我逐条对拍了十九条，Python 只在 http:g 这一条上与严格解析器不同，下一节说。

二、换站：两个字符就能把请求发到别人家

urljoin 的第二条规则比第一条危险得多：引用以 // 开头时，主机被整体替换。

urljoin('https://shop.example.com/cart', '//evil.test/x')      -> https://evil.test/x
urljoin('https://shop.example.com/cart', 'https://evil.test/x') -> https://evil.test/x

官方文档对这一条写得很直白：「Because an absolute URL may be passed as the url parameter, it is generally not secure to use urljoin with an attacker-controlled url.」——前半句是事实，后半句是我们最容易漏掉的判据：只要 urljoin 的第二个参数来自用户输入（回跳地址、头像链接、Webhook 回调），这个函数就是一个开放重定向。

还有一条更隐蔽的：相对引用的第一段只要含冒号，就被当成 scheme。

urljoin('http://h/d/e', 'a:b')     -> a:b
urljoin('http://h/d/e', './a:b')   -> http://h/d/a:b
urljoin('http://h/d/e', 'a%3Ab')   -> http://h/d/a%3Ab

a:b 被当成「scheme 为 a、路径为 b」的绝对地址原样返回，浏览器拿到它就会去找 a 这个协议。RFC 3986 5.4.2 对这一点有明确说明：严格解析器把 http:g 解析成 http:g，只有向后兼容的解析器才把它当相对引用展开成 http://a/b/c/g。Python 属于后者——本机实测 urljoin('http://a/b/c/d;p?q', 'http:g') 返回 http://a/b/c/g。

另外，带凭据的 base 会把凭据一路带下去：urljoin('https://user:pw@a.test/x/y', '../z') 得 https://user:pw@a.test/z。如果日志里打印的是 join 之后的结果，密码就跟着进了日志。这一条与我此前实测的 Cookie 作用域六道关 属于同一类问题：字符串层面看起来正常的地址，到了协议层已经换了对象。

三、空问号与空井号：往返一圈就没了

urlsplit 与 urlunparse 的往返不是恒等变换。本机实测：

urlsplit('http://h/p?').geturl()   -> http://h/p
urlsplit('http://h/p#').geturl()   -> http://h/p
urlsplit('http://h/p?&').geturl()  -> http://h/p?&
urlunparse(('http','h','/p','','','')) -> http://h/p

末尾那个空 ? 和空 # 消失了，但 ?& 这种「有内容」的查询串能活下来。原因是 urlunparse 只判断分量是否为空字符串，空字符串就不写分隔符。

这里有一处文档与 RFC 的分歧，值得单独记一笔。Python 文档在 urlunparse 条目下写的是：「This may result in a slightly different, but equivalent URL, if the URL that was parsed originally had unnecessary delimiters (for example, a ? with an empty query; the RFC states that these are equivalent).」

而我去查 RFC 3986 5.3 的原文，方向是反的：「Note that we are careful to preserve the distinction between a component that is undefined, meaning that its separator was not present in the reference, and a component that is empty, meaning that the separator was present」。5.3 要求区分「未定义」与「为空」，重组时该写回 ? 就要写回。

对做 URL 去重、缓存键、canonical 的人来说这不是学术问题：/p 与 /p? 在你眼里是不是同一个资源，决定了两个缓存条目还是一个。上游显然也意识到了，3.15 的文档里 urlunparse 多了一个 keep_empty 参数，urlsplit 多了 missing_as_none；本机 3.13.14 两个参数都还没有（urlunparse 的签名仍是 urlunparse(components)）。升级到 3.15 之后这一段行为会变，写死假设的代码要复查。

顺带一个同族改写：urlsplit(url, allow_fragments=False) 不会报错，它把井号后面的东西整个塞进 query。实测 urlsplit('http://a/p?x=1#f', allow_fragments=False) 得到 query='x=1#f'、fragment=''。用这个参数时要记得，# 之后的内容已经混进查询串了。

四、分号：urlparse 只从最后一段切

urlparse 比 urlsplit 多的那个 params 分量，来自已废弃的 RFC 1738 / 1808。Python 文档直说「urlsplit() should generally be used instead of urlparse()」，但老代码里 urlparse 到处都是，而它的切法很挑位置：

urlparse('http://a/b/c;d')   -> path='/b/c'      params='d'
urlparse('http://a/b;c/d')   -> path='/b;c/d'    params=''
urlparse('http://a/b;c;d')   -> path='/b'        params='c;d'
urlparse('http://a/b/c;d/e') -> path='/b/c;d/e'  params=''

只有最后一段里的分号才会被切成 params；中间段的分号留在 path 里；最后一段有两个分号时，第一个之后全算 params。也就是说 .path 这个属性在 urlparse 下可能比你写的少一截——如果你用 parsed.path 去比对路由表，/b/c;d 会比不上。

urlsplit 完全不做这件事，path 原样保留 /b;c/d。要在两者之间选，判据很简单：要不要 params。不要就用 urlsplit，因为少一个可变分量，少一处惊喜。

五、查询串的三个默认值：空值、分号、加号

parse_qs 的签名里有一串默认值，每一个都会改变结果：

parse_qs('a=1&b=&c=&d')                         -> {'a': ['1']}
parse_qs('a=1&b=&c=&d', keep_blank_values=True) -> {'a': ['1'], 'b': [''], 'c': [''], 'd': ['']}
parse_qs('a=1;b=2')                             -> {'a': ['1;b=2']}
parse_qs('a=1;b=2', separator=';')              -> {'a': ['1'], 'b': ['2']}
parse_qs('a=1&junk', strict_parsing=True)       -> ValueError: bad query field: 'junk'
parse_qs('a=1&b=2&c=3', max_num_fields=2)       -> ValueError: Max number of fields exceeded

三件事：

第一，keep_blank_values 默认 False，带 = 但没值的参数会被整条丢掉。做表单回填、埋点校验、OAuth 回调参数核对时，这等于丢数据。文档原话：「The default false value indicates that blank values are to be ignored and treated as if they were not included.」

第二，分号自 3.10 起不再是分隔符。文档版本注记写得很清楚：「Python versions earlier than Python 3.10 allowed using both ; and & as query parameter separator.」所以 a=1;b=2 现在是一个键，值是 1;b=2。老系统迁移过来，参数会静默合体。

第三，+ 与 %20 是两套解码：parse_qs('q=a+b') 与 parse_qs('q=a%20b') 都给 a b，但 unquote('a+b') 返回 a+b，只有 unquote_plus('a+b') 才返回 a b。手动解码查询串时用错函数，加号就变成字面加号。

还有一个不会报错的：parse_qs('q=100%') 返回 {'q': ['100%']}，%zz、%2 也原样留着。unquote 对不成对的百分号是「放过」而不是「报错」，只有能凑成字节、但字节解不成 UTF-8 时才替换。所以「解析没报错」不等于「数据干净」。

六、编码：quote 与 quote_plus 只差一个默认参数

quote 的默认 safe='/'，quote_plus 的默认 safe=''。差这一个字符，斜杠的处理就完全不同：

quote('a b/c?d=e&f+g%h#i')       -> a%20b/c%3Fd%3De%26f%2Bg%25h%23i
quote_plus('a b/c?d=e&f+g%h#i')  -> a+b%2Fc%3Fd%3De%26f%2Bg%25h%23i
quote('/a b')                    -> /a%20b
quote_plus('/a b')               -> %2Fa+b

quote 是给路径用的，所以放过 /、把空格编成 %20；quote_plus 是给表单值用的，所以 / 也编成 %2F、空格变成 +。urlencode 默认走的是后者，文档原话：「By default, quote_plus() is used to quote the values」；想换成 %20 就传 quote_via=quote。

二次编码是这类问题里最难看出来的一种：quote(quote('a b')) 得到 a%2520b，解一次回到 a%20b，再解一次才是 a b。本机实测一个具体的双解码场景：parse_qs(unquote('q=a%252Bb')) 返回 {'q': ['a+b']}——经过两次解码，原本被编码的加号变成了真正的加号，再进一次解码就会变成空格。签名字符串、回调参数被这样啃掉一个字符，报错会出现在离现场很远的地方。

urlencode 还有两处会把类型悄悄变成字符串：

urlencode({'a': [1, 2]})              -> a=%5B1%2C+2%5D
urlencode({'a': [1, 2]}, doseq=True)  -> a=1&a=2
urlencode({'a': None})                -> a=None
urlencode({'a': True, 'b': 0})        -> a=True&b=0

不传 doseq=True 时，列表会被 str() 成 [1, 2] 再编码，服务端收到的是字面量 [1, 2]。None 变成 None、True 变成 True，没有任何警告——布尔值与整数在 Python 里不是字符串，但 urlencode 不打算替你判断。

七、主机名：三种口径与一次 NFKC 拦截

同一个 URL，netloc、hostname、username 三个属性给三种口径：

urlsplit('HTTP://User:PW@Example.COM:8080/Path?Q=1')
  scheme='http'  netloc='User:PW@Example.COM:8080'
  hostname='example.com'  username='User'  path='/Path'

scheme 被小写，netloc 原样保留大小写，hostname 又变成小写，路径与查询串一律不动。拿 netloc 做白名单比对（if host in ALLOWED），大小写混写的域名就会漏判；拿 hostname 比对，ex%61mple.com 这种百分号编码的主机又不会被解开——文档写着「Percent-encoded sequences are not decoded」，实测 hostname 返回的就是 ex%61mple.com 原串。

urlsplit 也不做校验。文档给了明确警告：「urlsplit() does not perform validation.」实测 urlsplit('http://a b/p') 不报错，hostname 就是 a b；IPv6 要去掉方括号：urlsplit('http://[::1]:8080/p').hostname 是 ::1。

真正会拦下来的只有两类，都是解析或访问属性时才抛：

urlsplit('http://exam／ple.com/p')  # 全角斜杠 U+FF0F
  -> ValueError: netloc 'exam／ple.com' contains invalid characters under NFKC normalization
urlsplit('http://℀.test/p')          # U+2100，NFKC 展开成 a/c
  -> ValueError: netloc '℀.test' contains invalid characters under NFKC normalization

规则来自 _checknetloc()：对非 ASCII 的 netloc 做 NFKC 归一，若归一后出现了 /?#@: 就拒绝。理由是 IDNA 按 NFKC 等价处理主机名，一个「看起来像点、归一后是斜杠」的字符能骗过肉眼白名单。但这道网并不密：我实测 U+2044（分数斜杠）在 NFKC 下不展开，http://a⁄b/p 照样通过。

中文域名不会自动转 punycode。'münchen.de'.encode('idna') 得 b'xn--mnchen-3ya.de'，这一步要自己做；不做的话错误会出现在比你预想晚得多的地方，见排错录第 5 条。

八、控制字符与非 ASCII：删掉的、留着的、炸掉的

urlsplit 会静默删除 URL 里任意位置的 \t、\r、\n（3.10 起），并剥掉开头的 C0 控制字符与空格（3.12 起）。本机实测：

urlsplit('http://h/p\r\nX: y').path  -> '/pX: y'
urlsplit('http://h/p\x00').path      -> '/p\x00'
urlsplit('  http://h/p').netloc      -> 'h'

回车换行被删掉，\x00 留着。这两条对安全侧都不是小事：前者意味着「用 urlsplit 清洗过的 URL 不会再带 CRLF」，后者意味着 NUL 会一路带到应用层，os.path 与数据库各自有各自的解读。

非 ASCII 的问题不在 urllib.parse 里，它在 socket 口上等着。本机实测：

HTTPConnection('127.0.0.1', 9).putrequest('GET', '/订单?q=中')
  -> UnicodeEncodeError: 'ascii' codec can't encode characters in position 5-6
HTTPConnection('127.0.0.1', 9).putrequest('GET', '/订单/a b?q=中')
  -> InvalidURL: URL can't contain control characters. '/订单/a b?q=中' (found at least ' ')
HTTPConnection('127.0.0.1', 9).putrequest('GET', '/%E8%AE%A2%E5%8D%95')
  -> 通过

请求行只接受 ASCII，所以路径必须先 quote。注意第二条的报错文案在说「control characters」，实际触发原因是那个空格——文案与根因不一致，是本轮我花时间最多的一处误导。发送顺序上，如果你要处理的是「连上了但对面不回应」，那是另一层，我在 TCP socket 判活 里实测过四组超时与半关闭行为。

还有一条容易被忽略：urlsplit 不解码路径里的 %2F。urlsplit('http://h/a%2Fb').path 返回 /a%2Fb，你按 / 切段得到一段 a%2Fb，而某些服务端会把 %2F 解成真正的分隔符。切段逻辑与服务端解码口径不一致，就是路径穿越的入口。

排错录：六个真实报错

1. ValueError: not enough values to unpack (expected 7, got 6)

parts = urlsplit('http://h/p')   # 5 分量
urlunparse(parts)                # 炸

urlunparse 要六元组（scheme, netloc, path, params, query, fragment），urlsplit 只给五个。修法：改用 urlunsplit(...) 或直接 SplitResult.geturl()。别指望 urlunparse 自动对齐——它内部就是一次六元组解包，所以报错文案说的是「解包得到 6 个值」。

2. ValueError: Invalid IPv6 URL

urlsplit('http://[::1/p')

方括号没闭合。异常抛在 urlsplit 里而不是访问 hostname 时，源码 _check_bracketed_netloc() 会先检查「方括号前不允许有内容、方括号与端口之间只能是冒号」。IPv4 加方括号同样会被拒：An IPv4 address cannot be in brackets。

3. ValueError: Port out of range 0-65535 与 ValueError: Port could not be cast to integer value as 'abc'

urlsplit('http://a:99999/p').port
urlsplit('http://a:abc/p').port

两条都在读 .port 属性时才抛，urlsplit 本身不报错。所以「解析成功」不能作为端口合法的依据；校验端口必须显式读一次 .port。3.6 之前越界返回 None，现在是抛异常，老代码 if p.port: 的判断方式会直接崩。

4. UnicodeEncodeError: 'ascii' codec can't encode characters in position 5-6

路径里有中文且没编码。修法只有一条：进 putrequest / urlopen 之前 quote(path)，且编码只做一次（见第六节的 %2520）。

5. UnicodeEncodeError: 'latin-1' codec can't encode characters in position 0-1

c = HTTPConnection('例子.测试', 9, timeout=1)
c.putrequest('GET', '/')
c.putheader('Host', '例子.测试')
c.endheaders()

Host 头按 latin-1 编码，中文域名必须先 encode('idna').decode('ascii')。这类问题的现场通常出现在 DNS 或 TLS 之后（对照 TLS 证书链验证的六种失败，主机名不匹配也在同一层），但根因在上游的字符串没转。

6. TypeError: Cannot mix str and non-str arguments

urljoin('http://a/b', b'/c')

urljoin 两边必须同类型。urlsplit(b'...') 是支持的，返回 SplitResultBytes，所有分量都是 bytes；但只要混一个 str 就抛。修法是入口处统一转 str，别指望函数替你猜。

另外还有一条不算报错但同样要记：quote(b'\xff', encoding='utf-8') 抛 TypeError: quote() doesn't support 'encoding' for bytes——bytes 输入不接受 encoding，因为它已经是字节，没什么可编的。

一套可复用的判据

把上面七处收成六条，写进代码注释比写进文档管用：

  • base 是目录就补尾斜杠，否则最后一段必丢。
  • urljoin 的第二参数不可信时不要用它，先用 urlsplit 取 hostname 与 scheme 比对，再决定要不要拼。
  • 往返要逐字比对，不要用「看起来一样」判断。geturl() 与原串做 ==，是唯一成本够低的检查。
  • 查询串解析显式传 keep_blank_values=True，并显式选定分隔符，不要依赖默认值。
  • 编码只做一次，编码前后各断言一次「不含 %」或「不含非 ASCII」。
  • 校验主机用 hostname 且先 lower()，同时对 netloc 的大小写混写做一次归一，别让两套口径各管一半。

关于第 3 条，还有个配套的工程习惯：把 URL 当主键存库之前，先跑一遍「解析 → 重拼 → 比对」，不一致就把两串都记下来。这个动作和我在 HTTP 缓存那篇 里给缓存键做归一化是同一套思路：先让键稳定，再谈命中。

常见问题

Q：既然 Python 文档说空问号往返之后是「equivalent」，那我还需要保留它吗？

取决于你把它当资源标识还是当字符串。作为资源标识，/p 与 /p? 在多数服务端指向同一份内容，可以归一；作为缓存键或去重键，就必须保留原样，因为下游可能有系统按字节比较。RFC 3986 5.3 要求区分「未定义」与「为空」，我倾向按 RFC 走，等到 3.15 的 keep_empty 可用再简化。

Q：urljoin 会不会被 //evil.test 这种引用绕过？我加了 host 白名单。

白名单加在校验阶段就有用，加在拼接之后没用。实测 urljoin('https://shop.example.com/cart', '//evil.test/x') 直接返回 https://evil.test/x，主机被整体替换。正确顺序是：先解析引用、取出它的 scheme 与 hostname，为空才允许拼；不为空就按绝对地址走拒绝逻辑。

Q：parse_qs 返回的键值都是列表，为什么不做成单值？

因为同一个参数可以出现多次（a=1&a=2 实测返回 {'a': ['1', '2']}），字典只能存列表。要单值就自己取 [0]，但要清楚这等于主动丢掉后面的值，而不是「取到唯一值」。

Q：中文路径报 ascii 编码错，我改成 encode('utf-8') 为什么还是错？

putrequest 要的是已经百分号编码的 ASCII 字符串，不是 UTF-8 字节。正确做法是 quote('/订单') 得到 /%E8%AE%A2%E5%8D%95，再交给它。直接传 bytes 会走到另一条类型判断上。

结论

urllib.parse 的问题不是「有 bug」，而是它有一整套合理的默认值，而你的场景未必是它默认的那个：默认 base 是文件、默认查询串不要空值、默认分隔符只有 &、默认给表单值用 quote_plus、默认主机名不做 IDNA、默认 URL 里没有非 ASCII。

这七处改写里，只有两处会走到异常，其余五处（5/7，约 71%）都是静默的。所以判据不能是「跑通了」，只能是「拼回来的字符串和我写下去的那个逐字相同」。我实际跑了六十多条用例之后，最有用的一条经验反而是最笨的那条：任何 URL 在落库、拼装、发请求之前，先做一次 geturl() == original 的断言。它抓不到所有问题，但它能在问题离开你的机器之前抓住大部分。
