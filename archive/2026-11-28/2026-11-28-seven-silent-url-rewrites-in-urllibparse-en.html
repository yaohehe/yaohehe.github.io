Seven silent URL rewrites in urllib.parse, measured

PythonURL parsingWeb development

Last week a crawl report showed two "different" pagination URLs in our sitemap: one with a trailing slash, one without. Google had indexed both, while the canonical tag pointed at only one. The generator contained a single call, urljoin(base, page), which looks harmless enough.

I pulled that one call out and ran it against more than sixty cases. The finding: urllib.parse never raises an exception to tell you it changed a character. It quietly returns a string that looks the same and is not. The hard part is not parsing. It is that splitting and serialising are two different functions, and every default between them gets a vote.

Everything below was produced on CPython 3.13.14 on Windows 11 10.0.26300. I paste the output as it came out. Where Python and RFC 3986 disagree, I quote both sides so you can decide which one your code should follow.

Not one row in that table raises. The six failures that do raise are in the troubleshooting section near the end, and they are the easy half of the problem, precisely because they are loud.

One: the trailing slash eats the last segment

This is the most common surprise. urljoin does not concatenate strings. It appends the relative path to everything in the base except the last segment. Measured here:

urljoin('http://a/b/c/d', 'e')   -> http://a/b/c/e
urljoin('http://a/b/c/d/', 'e')  -> http://a/b/c/d/e
urljoin('http://a/b', 'c')       -> http://a/c
urljoin('http://a/', 'c')        -> http://a/c

http://a/b plus c gives http://a/c. The b segment is gone. RFC 3986 5.2.3 spells out the rule: the reference path is "appended to all but the last segment of the base URI's path". Unless the base ends in a slash, its last segment is treated as a file and gets replaced.

So whenever the base is a directory, add the slash yourself. The inverse case behaves sanely: a query-only reference keeps the path and swaps only the query.

urljoin('http://a/b/c/d;p?q', '?y')  -> http://a/b/c/d;p?y
urljoin('http://a/b/c/d;p?q', '#s')  -> http://a/b/c/d;p?q#s
urljoin('http://a/b/c/d;p?q', '')    -> http://a/b/c/d;p?q

Dot segments follow the same rules and never climb above the root: urljoin('http://a/b/c/d;p?q', '../../../g') returns http://a/g. I checked all nineteen abnormal examples in RFC 3986 5.4.2. Python matches them except http:g, which the next section covers.

Two: two characters are enough to change the host

The second rule in urljoin is far more dangerous than the first. When the reference begins with //, the host is replaced wholesale.

urljoin('https://shop.example.com/cart', '//evil.test/x')      -> https://evil.test/x
urljoin('https://shop.example.com/cart', 'https://evil.test/x') -> https://evil.test/x

The documentation is blunt about it: "Because an absolute URL may be passed as the url parameter, it is generally not secure to use urljoin with an attacker-controlled url." That sentence is the whole argument. If the second argument comes from user input, a return-to URL, an avatar field, a webhook callback, then this function is an open redirect with extra steps.

There is a quieter variant. A relative reference whose first segment contains a colon is read as a scheme.

urljoin('http://h/d/e', 'a:b')     -> a:b
urljoin('http://h/d/e', './a:b')   -> http://h/d/a:b
urljoin('http://h/d/e', 'a%3Ab')   -> http://h/d/a%3Ab

a:b is returned as-is, as an absolute URI with scheme a. A browser handed that string will go looking for a protocol named a. RFC 3986 5.4.2 describes both behaviours: strict parsers keep http:g as http:g, and only backward-compatible parsers expand it to http://a/b/c/g. Python is the second kind. Measured: urljoin('http://a/b/c/d;p?q', 'http:g') returns http://a/b/c/g.

Credentials ride along too. urljoin('https://user:pw@a.test/x/y', '../z') returns https://user:pw@a.test/z. If your logs print the joined result, the password is now in the logs. This belongs to the same family as the six gates a Set-Cookie has to pass: a string that looks fine at the text layer has already become a different object at the protocol layer.

Three: an empty question mark does not survive the round trip

urlsplit followed by urlunparse is not an identity transform.

urlsplit('http://h/p?').geturl()   -> http://h/p
urlsplit('http://h/p#').geturl()   -> http://h/p
urlsplit('http://h/p?&').geturl()  -> http://h/p?&
urlunparse(('http','h','/p','','','')) -> http://h/p

The trailing ? and # vanish. A query of ?& survives, because it has content. urlunparse only checks whether a component is an empty string, and an empty string writes no separator.

Here the documentation and the RFC point in opposite directions, which is worth recording. The urlunparse entry says: "This may result in a slightly different, but equivalent URL, if the URL that was parsed originally had unnecessary delimiters (for example, a ? with an empty query; the RFC states that these are equivalent)."

RFC 3986 5.3 says something else: "Note that we are careful to preserve the distinction between a component that is undefined, meaning that its separator was not present in the reference, and a component that is empty, meaning that the separator was present". The RFC asks you to keep the difference; the Python documentation calls it equivalent.

For anyone doing URL deduplication, cache keys or canonicals, this is not academic. Whether /p and /p? are the same resource decides whether you keep one cache entry or two. Upstream clearly noticed. The 3.15 docs add a keep_empty parameter to urlunparse and missing_as_none to urlsplit. On the 3.13.14 install I tested, neither exists; the signature is still urlunparse(components). If you upgrade to 3.15, revisit any code that assumed the current behaviour.

One related rewrite: urlsplit(url, allow_fragments=False) does not raise. It shoves everything after the hash into the query. Measured, urlsplit('http://a/p?x=1#f', allow_fragments=False) gives query='x=1#f' and fragment=''.

Four: urlparse only splits semicolons in the last segment

The extra params component in urlparse comes from the obsolete RFC 1738 and 1808. The docs say plainly that "urlsplit() should generally be used instead of urlparse()", but old code is full of urlparse, and its splitting depends on position.

urlparse('http://a/b/c;d')   -> path='/b/c'      params='d'
urlparse('http://a/b;c/d')   -> path='/b;c/d'    params=''
urlparse('http://a/b;c;d')   -> path='/b'        params='c;d'
urlparse('http://a/b/c;d/e') -> path='/b/c;d/e'  params=''

Only a semicolon in the final segment becomes params. Semicolons in earlier segments stay in the path. With two semicolons in the last segment, everything after the first one counts as params. So .path can be shorter than what you wrote. If you compare parsed.path against a route table, /b/c;d will not match a route for /b/c;d.

urlsplit does none of this; the path stays /b;c/d. The choice is simple: do you want params or not. If not, use urlsplit and remove a variable from the equation.

Five: three query-string defaults

The parse_qs signature is a list of defaults, and each one changes the answer.

parse_qs('a=1&b=&c=&d')                         -> {'a': ['1']}
parse_qs('a=1&b=&c=&d', keep_blank_values=True) -> {'a': ['1'], 'b': [''], 'c': [''], 'd': ['']}
parse_qs('a=1;b=2')                             -> {'a': ['1;b=2']}
parse_qs('a=1;b=2', separator=';')              -> {'a': ['1'], 'b': ['2']}
parse_qs('a=1&junk', strict_parsing=True)       -> ValueError: bad query field: 'junk'
parse_qs('a=1&b=2&c=3', max_num_fields=2)       -> ValueError: Max number of fields exceeded

Three things to note.

First, keep_blank_values defaults to False, so a parameter with = and no value is dropped entirely. The docs: "The default false value indicates that blank values are to be ignored and treated as if they were not included." For form round-trips, analytics validation or OAuth callback checks, that is data loss with a clean exit code.

Second, the semicolon stopped being a separator in 3.10. The version note reads: "Python versions earlier than Python 3.10 allowed using both ; and & as query parameter separator." So a=1;b=2 is now one key whose value is 1;b=2. Migrate an old system and its parameters merge silently.

Third, + and %20 are two different decoders. Both parse_qs('q=a+b') and parse_qs('q=a%20b') yield a b, but unquote('a+b') returns a+b, and only unquote_plus('a+b') returns a b. Pick the wrong one when decoding by hand and plus signs become literal plus signs.

And one that never complains: parse_qs('q=100%') returns {'q': ['100%']}. So do %zz and %2; they pass through untouched. unquote lets unmatched percent signs through rather than raising; it only substitutes when the bytes assemble but fail to decode as UTF-8. A clean parse is not the same as clean data.

Six: quote and quote_plus differ by one default

quote defaults to safe='/', quote_plus to safe=''. One character of difference and slashes are handled differently.

quote('a b/c?d=e&f+g%h#i')       -> a%20b/c%3Fd%3De%26f%2Bg%25h%23i
quote_plus('a b/c?d=e&f+g%h#i')  -> a+b%2Fc%3Fd%3De%26f%2Bg%25h%23i
quote('/a b')                    -> /a%20b
quote_plus('/a b')               -> %2Fa+b

quote is for paths, so it protects / and turns spaces into %20. quote_plus is for form values, so it encodes / as %2F and spaces as +. urlencode uses the second by default: "By default, quote_plus() is used to quote the values". Pass quote_via=quote to get %20 instead.

Double encoding is the hardest kind to spot. quote(quote('a b')) returns a%2520b; one decode gives back a%20b, and only the second decode yields a b. Measured example of a double decode going wrong: parse_qs(unquote('q=a%252Bb')) returns {'q': ['a+b']}. After two passes an encoded plus has become a real plus, and one more pass would turn it into a space. Signature strings and callback parameters lose a character this way, and the error surfaces far from the scene.

urlencode also stringifies types without asking:

urlencode({'a': [1, 2]})              -> a=%5B1%2C+2%5D
urlencode({'a': [1, 2]}, doseq=True)  -> a=1&a=2
urlencode({'a': None})                -> a=None
urlencode({'a': True, 'b': 0})        -> a=True&b=0

Without doseq=True, a list is run through str() and encoded as the literal [1, 2]. None becomes None and True becomes True, with no warning. Booleans and integers are not strings in Python, and urlencode does not intend to decide that for you.

Seven: three notions of the host, and one NFKC check

For a single URL, netloc, hostname and username give three different answers.

urlsplit('HTTP://User:PW@Example.COM:8080/Path?Q=1')
  scheme='http'  netloc='User:PW@Example.COM:8080'
  hostname='example.com'  username='User'  path='/Path'

The scheme is lowercased, netloc keeps its original case, hostname is lowercased, and the path and query are untouched. An allowlist built on netloc (if host in ALLOWED) will miss a mixed-case domain. An allowlist built on hostname will not decode a percent-encoded host: the docs state "Percent-encoded sequences are not decoded", and hostname returns ex%61mple.com exactly as typed.

urlsplit does not validate either. The docs carry an explicit warning: "urlsplit() does not perform validation." Measured, urlsplit('http://a b/p') raises nothing and hostname is a b. IPv6 brackets are stripped: urlsplit('http://[::1]:8080/p').hostname is ::1.

Only two classes get rejected, and both raise during parsing or attribute access.

urlsplit('http://exam／ple.com/p')  # fullwidth solidus U+FF0F
  -> ValueError: netloc 'exam／ple.com' contains invalid characters under NFKC normalization
urlsplit('http://℀.test/p')          # U+2100, NFKC expands to a/c
  -> ValueError: netloc '℀.test' contains invalid characters under NFKC normalization

The check lives in _checknetloc(): normalise a non-ASCII netloc with NFKC, reject it if /?#@: appears afterwards. The reasoning holds, since IDNA compares hostnames by NFKC, so a character that looks like a dot but normalises to a slash can slip past a visual allowlist. But the net is not tight. U+2044, the fraction slash, does not expand under NFKC here, and http://a⁄b/p passes.

Chinese and other IDN hostnames are not converted for you. 'münchen.de'.encode('idna') gives b'xn--mnchen-3ya.de'; that step is yours. Skip it and the failure shows up much later, as error 5 in the next section.

Eight: control characters and non-ASCII, deleted, kept and thrown

urlsplit silently deletes \t, \r and \n anywhere in the URL (since 3.10) and strips leading C0 controls and spaces (since 3.12).

urlsplit('http://h/p\r\nX: y').path  -> '/pX: y'
urlsplit('http://h/p\x00').path      -> '/p\x00'
urlsplit('  http://h/p').netloc      -> 'h'

Carriage returns and newlines are gone; \x00 stays. Both matter on the security side. The first means a URL that passed through urlsplit cannot carry CRLF any more. The second means a NUL byte travels to your application layer, where os.path and the database each read it their own way.

Non-ASCII is not a urllib.parse problem. It waits at the socket.

HTTPConnection('127.0.0.1', 9).putrequest('GET', '/订单?q=中')
  -> UnicodeEncodeError: 'ascii' codec can't encode characters in position 5-6
HTTPConnection('127.0.0.1', 9).putrequest('GET', '/订单/a b?q=中')
  -> InvalidURL: URL can't contain control characters. '/订单/a b?q=中' (found at least ' ')
HTTPConnection('127.0.0.1', 9).putrequest('GET', '/%E8%AE%A2%E5%8D%95')
  -> accepted

The request line is ASCII only, so the path has to be quoted first. Note the second message: it complains about control characters, while the actual trigger is the space. That mismatch between message and cause cost me the most time in this round. If your problem is a connection that opens but never answers, that is a different layer; I measured four timeout and half-close cases in TCP socket liveness.

One more thing worth knowing: urlsplit does not decode %2F in the path. urlsplit('http://h/a%2Fb').path returns /a%2Fb, so splitting on / gives you one segment named a%2Fb, while some servers decode it into a real separator. When your splitting logic and the server's decoding disagree, that gap is a path traversal.

Troubleshooting: six errors I reproduced

1. ValueError: not enough values to unpack (expected 7, got 6)

parts = urlsplit('http://h/p')   # 5 components
urlunparse(parts)                # raises

urlunparse wants six items (scheme, netloc, path, params, query, fragment); urlsplit gives five. Use urlunsplit(...) or SplitResult.geturl() instead. The function cannot align them for you; internally it unpacks six values, hence the wording about unpacking six.

2. ValueError: Invalid IPv6 URL

urlsplit('http://[::1/p')

An unclosed bracket. The error comes out of urlsplit, not from reading hostname, because _check_bracketed_netloc() rejects content before the bracket and anything other than a colon between bracket and port. An IPv4 address in brackets is rejected too: An IPv4 address cannot be in brackets.

3. ValueError: Port out of range 0-65535 and ValueError: Port could not be cast to integer value as 'abc'

urlsplit('http://a:99999/p').port
urlsplit('http://a:abc/p').port

Both raise only when .port is read. urlsplit itself is happy. A successful parse is therefore not evidence that the port is valid; validate by reading .port on purpose. Before 3.6 an out-of-range port returned None. Code written as if p.port: will now crash rather than take the false branch.

4. UnicodeEncodeError: 'ascii' codec can't encode characters in position 5-6

A non-ASCII path that was never quoted. Quote it once, before putrequest or urlopen, and only once, otherwise you get the %2520 case from section six.

5. UnicodeEncodeError: 'latin-1' codec can't encode characters in position 0-1

c = HTTPConnection('例子.测试', 9, timeout=1)
c.putrequest('GET', '/')
c.putheader('Host', '例子.测试')
c.endheaders()

The Host header is encoded as latin-1, so an IDN must first become punycode via encode('idna').decode('ascii'). The symptom usually appears after DNS or TLS, on the same layer as the six TLS chain failures, but the cause is a string upstream that was never converted.

6. TypeError: Cannot mix str and non-str arguments

urljoin('http://a/b', b'/c')

Both arguments must be the same type. urlsplit(b'...') is supported and returns a SplitResultBytes whose components are bytes, but a single mixed argument raises. Normalise to str at the boundary rather than hoping the function guesses.

One more that is not an exception but still worth recording: quote(b'\xff', encoding='utf-8') raises TypeError: quote() doesn't support 'encoding' for bytes. Bytes are already bytes; there is nothing left to encode.

A checklist you can reuse

Six rules, worth more in a code comment than in a wiki:

  • If the base is a directory, add the trailing slash. Otherwise the last segment is lost.
  • Do not use urljoin when the second argument is untrusted. Split the reference first, compare scheme and hostname, then decide.
  • Compare round trips character by character. geturl() == original is the cheapest check that actually works.
  • Pass keep_blank_values=True explicitly when parsing queries, and choose the separator explicitly too.
  • Encode exactly once, and assert "no percent signs" or "no non-ASCII" on both sides of that step.
  • Validate hosts on hostname, lowercased, and normalise the case of netloc as well, so the two notions cannot disagree.

There is a habit that goes with rule three: before storing a URL as a primary key, run parse, rebuild and compare. If the strings differ, keep both. It is the same idea I used when normalising cache keys in the HTTP cache and ETag piece: make the key stable before you talk about hits.

FAQ

Q: The docs call an empty query "equivalent" after a round trip. Should I still preserve it?

It depends whether you treat the URL as a resource identifier or as a string. As an identifier, /p and /p? usually resolve to the same content and you can normalise. As a cache key or deduplication key, preserve it, because some downstream system will compare bytes. RFC 3986 5.3 asks you to keep "undefined" and "empty" apart, and I would follow the RFC until keep_empty in 3.15 is available to you.

Q: I have a host allowlist. Does that stop a //evil.test reference?

An allowlist helps if it runs before the join. After the join it is too late. Measured, urljoin('https://shop.example.com/cart', '//evil.test/x') returns https://evil.test/x with the host replaced. The correct order is to split the reference, inspect its scheme and hostname, and only join when both are empty.

Q: Why does parse_qs return lists instead of single values?

Because a parameter can repeat: a=1&a=2 returns {'a': ['1', '2']} here. A dict of lists is the only shape that keeps both. Taking [0] is fine, as long as you know it discards the rest rather than proving uniqueness.

Q: My Chinese path throws an ascii error. encode('utf-8') did not help. Why?

putrequest wants a percent-encoded ASCII string, not UTF-8 bytes. quote('/订单') gives /%E8%AE%A2%E5%8D%95, which it accepts. Passing bytes takes a different branch of the type checks.

Conclusion

The problem with urllib.parse is not a bug. It is that the module ships a complete set of sensible defaults, and your situation is probably not the situation those defaults were chosen for: base treated as a file, blank query values discarded, & as the only separator, quote_plus for form values, no IDNA on hostnames, no non-ASCII anywhere in the URL.

Of the seven rewrites, only two ever reach an exception. The other five (five of seven, 71%) are silent. So the acceptance criterion cannot be "it ran". It has to be "the string I got back is character-for-character the string I put in". After sixty-odd cases, the most useful lesson was also the dumbest: assert geturl() == original before a URL is stored, joined or sent. It will not catch everything, but it catches most problems before they leave your machine.
