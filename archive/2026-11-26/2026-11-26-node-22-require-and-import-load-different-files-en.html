Node 22 module resolution: require() vs import()

nodejsesmmodule-resolution

TL;DR: Node 22.7 and 22.12 each flipped one default. The first made SyntaxError: Cannot use import statement outside a module stop appearing for .js files, the second let require() load ES modules. Once those errors went quiet, the real question became which file and which instance you actually got. I ran 40 subprocess cases on Node 22.22.2: 18 exited 1, 22 exited 0, and several of the zero-exit runs handed back the wrong module. Every error below is copied from my terminal, with the command that reproduces it.

Two dividing lines: what 22.7 and 22.12 each changed

Pin the version facts first, because every "why does this not fail on my machine" further down traces back to these two releases.

Node v22.7.0 (2024-08-22) says, verbatim: Module syntax detection is now enabled by default. The release note defines ambiguous files as .js or extensionless files whose nearest parent package.json has no "type" field. Node first tries to parse them as CommonJS, and if that fails on ES module syntax, runs them again as an ES module. --no-experimental-detect-module turns it off.

Node v22.12.0 (2024-12-03, LTS "Jod") says: require(esm) is now enabled by default. Three more sentences in the same block matter. Node.js will no longer throw ERR_REQUIRE_ESM. It can, however, throw ERR_REQUIRE_ASYNC_MODULE when the graph contains top-level await. And on success the returned object is either an ES module namespace object similar to what import() returns, or what gets exported as "module.exports". The block also names two switches: --no-experimental-require-module and process.features.require_module.

On this machine node -p "process.features.require_module" prints true, on v22.22.2 with V8 12.4.254.21-node.39, Windows 11 10.0.26300.

Resolution layer: import adds no extension and does not read index

The resolver feature list in the docs is blunt: No default extensions, No folder mains. CommonJS has spent decades doing exactly those two things.

The same directory layout therefore produces two outcomes. require('./util') exits 0. import './util' prints:

Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'D:\lab\cases\e-import-noext\util'
imported from D:\lab\cases\e-import-noext\main.js
Did you mean to import "./util.js"?

That "Did you mean" line comes from Node, not from me. Directory imports are just as strict: import './lib' raises ERR_UNSUPPORTED_DIR_IMPORT with Did you mean to import "./lib/index.js"?.

There is no flag and no compatibility window for this. When moving from CJS to ESM, adding extensions to relative imports is a precondition, not a style preference. Before you start, measure the size of the job by filtering out the relative imports that lack an extension:

grep -rnE "from '[^']*'" --include=*.js --include=*.mjs src | grep -vE "\.(js|mjs|cjs|json)'"

I verified this two-stage filter on three test files: the import of ./a.js was dropped and only ./b and ./dir survived. The second one is a directory import, so it still needs /index.js appended before it resolves.

Format layer: who decides whether a .js file is CJS or ESM

The order is measurable, and the packages docs describe the same layers.

First, the extension. Verbatim: Regardless of the value of the "type" field, .mjs files are always treated as ES modules and .cjs files are always treated as CommonJS.

Second, the type field of the nearest parent package.json. Verbatim: The "type" field defines the module format that Node.js uses for all .js files that have that package.json file as their nearest parent.

Third comes syntax detection, fourth the CommonJS default.

I tested the boundary of layer two: a root package.json with "type": "module" and a sub/package.json with "type": "commonjs". The sub/main.js using require('./dep.cjs') exits 0. The nearest manifest wins; the parent declaration does not reach past a child declaration.

Once a file lands in ESM, the name require simply does not exist:

ReferenceError: require is not defined in ES module scope, you can use import instead
This file is being treated as an ES module because it has a '.js' file extension
and 'D:\lab\cases\e-require-undefined\package.json' contains "type": "module".
To treat it as a CommonJS script, rename it to use the '.cjs' file extension.

The message carries all three facts you need: which file, which manifest caused it, and how to opt out. If you must stay in ESM and still load synchronously, use createRequire(import.meta.url) rather than bolting a require onto the global object.

Syntax detection turned an old error into a silent pass

This is the easiest place to misjudge Node 22. The exact same file, one line of import fs from 'node:fs' with no package.json anywhere, exits 0 on 22.22.2 and prints normally. Add --no-experimental-detect-module and the familiar error returns:

SyntaxError: Cannot use import statement outside a module

A .cjs file containing import also exits 1, but with an extra line first: Warning: Failed to load the ES module: ...main.cjs. Make sure to set "type": "module" in the nearest package.json file or use the .mjs extension. Detection only applies to ambiguous files; .cjs is a declaration, not a guess.

The dangerous case is an ambiguous file that mixes both syntaxes. I wrote a .js with an import and a module.exports:

ReferenceError: module is not defined in ES module scope

Detection tries CommonJS first, fails, retries as ESM, so the import makes the whole file an ES module and then module blows up. The stack points at module.exports on line 2, but the actual defect is that the format was guessed. The same file wears a different face across versions: before 22.7 it reports Cannot use import statement outside a module, and only after 22.7 does it become the ReferenceError above. When something "works locally and fails in CI", compare versions before touching code.

Does require() hand you the same object as import()?

Since 22.12 require() can load ESM, but loading is not the same as sharing. I tested both shapes, with and without a default export.

Without a default export (only export const id), require() and import() return the same namespace object: r3 === i2 is true.

With a default export they differ: r1 === i1 is false. The require side carries an extra marker, and the key sets are:

require keys: __esModule,default,n
import  keys: default,n

__esModule reads as true on one side and undefined on the other. That marker is a transpiler interop convention, not part of the ES module spec, so any code that sniffs module shape via Object.keys gets two different answers for the same file.

Calling require() twice on one path returns the same object (r1 === r2 is true), matching the CommonJS cache. But one package can still be two instances. I gave a package exports of { import: './esm.mjs', require: './cjs.cjs' }, each file holding its own counter, then required and imported it:

cjs count: 1
esm count: 0
same object: false

One side incremented, the other stayed at zero. That is the dual package hazard in its smallest form. The documented fix is the "module-sync" condition: put it first in exports pointing at one native .mjs, and in my test both require() and import() received the native module with same true and a single counter.

There is also a rarely used but real escape hatch. An ESM declaring export { api as 'module.exports' } makes require() return that object directly, with keys of just hello and no default or __esModule. It corresponds to the "support 'module.exports' interop export in require(esm)" commit in 22.12, and it is the channel a library author uses to dictate the require-side shape.

Named imports work or not depending on how you assign

The documentation hedges on purpose: Named exports may be available, provided by static analysis as a convenience for better ecosystem compatibility. The load-bearing words are "may" and "static analysis". I ran the four most common assignment styles:

Two of four work, exactly 50%. The third row is the trap: at runtime it is identical to the second, but static analysis cannot see the key.

Force it and you get:

SyntaxError: Named export 'bar' not found. The requested module './dynamic.cjs'
is a CommonJS module, which may not support all module.exports as named exports.
CommonJS modules can always be imported via the default export, for example using:

import pkg from './dynamic.cjs';
const { bar } = pkg;

Note that it is a SyntaxError thrown during linking. An earlier named import in the same file had already resolved, yet the module never executes a single line. "Default import then destructure" is the only stable form, at the cost of static analyzability.

exports: key order beats condition content

One sentence in the packages docs is easy to skip: Within the "exports" object, key order is significant. During condition matching, earlier entries have higher priority and take precedence over later entries. And about the fallback: This condition should always come last.

I built an A/B pair that differs only in key order:

{ "default": "./a.js", "require": "./b.js", "import": "./c.mjs" }   -> require got a.js
{ "require": "./b.js", "import": "./c.mjs", "default": "./a.js" }   -> require got b.js

In the first, require() received a.js because matching follows insertion order and default matches unconditionally, so the later require entry never gets a turn. No warning is printed; the package author's intent and the actual behavior are opposites.

When main and exports coexist, exports wins. My test returned { from: 'exports field' }, and the docs say it will take precedence over the "main" field.

Wildcards hide another one. The docs state that * is a direct static matching and replacement without any special handling for file extensions. I wrote "./*": "./src/*.js" and requested wpkg/feat/a.js, which resolved to src/feat/a.js.js:

Error: Cannot find module 'D:\lab\cases2\i-exports-wildcard\node_modules\wpkg\src\feat\a.js.js'

The correct form puts *.js on both sides: "./*.js": "./src/*.js".

Troubleshooting: six real errors, with the fix for each

Every message below came out of my terminal on this machine. None of them is a "typical error" template.

One, ERR_MODULE_NOT_FOUND: import './util' inside ESM. The resolver does not append extensions. Fix it by writing the extension, or by importing explicitly:

node --input-type=module -e "import('./util.js').then(m => console.log(Object.keys(m)))"

Two, ERR_UNSUPPORTED_DIR_IMPORT: import './lib'. ESM will not read a directory index. Use import './lib/index.js', or add an exports map to the package.

Three, ERR_REQUIRE_ASYNC_MODULE: require('./tla.mjs') where that module uses top-level await. The text is require() cannot be used on an ESM graph with top-level await. Use import() instead. Either switch to await import() or remove the TLA. To find which module introduced it, add --experimental-print-required-tla.

Four, ERR_IMPORT_ATTRIBUTE_MISSING: import data from './d.json'. JSON modules became stable in 22.12, but the attribute is mandatory. Use with { type: 'json' }; the older assert { type: 'json' } yields SyntaxError: Unexpected identifier 'assert', because 22.0.0 dropped support for import assertions.

Five, ERR_PACKAGE_PATH_NOT_EXPORTED: the package declared only "." and I required mypkg/extra.js. The text is Package subpath './extra.js' is not defined by "exports" in ...package.json. Either list the subpath ("./extra.js": "./extra.js") or go back to deep imports, which no longer work once exports exists. The docs warn that consumers lose even package.json, and that This will likely be a breaking change.

Six, Named export not found: see the previous section for the full text. The fix is always a default import followed by destructuring.

Migration checklist: six commands you can paste

Run them in order before touching code; each one surfaces a different risk.

node -p "process.features.require_module"
node -p "process.versions.node"
npm pkg get type

The first confirms whether this instance supports require(esm), which is true here. The third prints the nearest type field; an empty object means none is declared. The fourth deliberately disables the feature to reproduce the old behavior, which is how you tell whether a production error is a version difference. The fifth prints the namespace so you can verify that named imports really resolve. The sixth disables detection to simulate the pre-22.7 judgement.

FAQ

Q: Should I actually add "type": "module" to package.json?

A: Yes. Detection has no measured cost for CommonJS but the release note says it incurs a slight penalty for ES modules; an explicit type removes that penalty and stops the format from being a guess.

Q: Is require(esm) stable now?

A: The 22.12 release notes call it "still experimental". Enabled by default is not the same as frozen interface.

Q: What is the cheapest fix for a package loading as two instances?

A: Point both paths at one native ESM with the "module-sync" condition. If you cannot, move mutable state out of module scope (globalThis, or explicit injection) instead of trusting the cache.

Q: Why does the error tell me to rename to .cjs instead of .js?

A: The format of .js is decided by the nearest package.json, so inside a "type": "module" package you cannot make a .js file CommonJS. .cjs is the only extension that ignores type.

Closing note

Two defaults turned "wrong syntax" into "different resolution result". After 22.7 the format of a .js file is guessed, and after 22.12 require() can hand you an ES module namespace. A guess does not throw; it just gives you another file and another instance. Of the 40 cases I ran, the 18 that failed were the easy ones, because they printed a filename and a line number. The ones worth watching are among the 22 that exited 0 and returned the wrong thing without a word.
