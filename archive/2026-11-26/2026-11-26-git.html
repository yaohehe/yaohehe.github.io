同一个文件在 Git 里有三份字节：换行符在哪一层被改写

Git换行符版本控制

一个三行的文本文件，我只在中间那行改了两个字母，合并时 Git 给了一整块冲突：左边三行，右边三行，逐行内容一模一样，只有行尾不一样。这不是 Git 的 bug，而是它把同一个文件存了三份，你平时只看见其中一份。

我把这件事拆成 12 组实验，全部跑在同一台机器上：Windows 11 10.0.26300、git version 2.55.0.windows.3、每个仓库都用独立的 GIT_CONFIG_GLOBAL 与 GIT_CONFIG_SYSTEM 指向空文件，避免被本机全局配置污染。下面出现的每一个字节、每一条报错都是原始输出。

三份字节同时存在

拿同一个两行文件 line1\r\nline2\r\n（14 字节）做对照，core.autocrlf=true 下：

  • 工作区字节：b'line1\r\nline2\r\n'
  • 索引与 blob 字节：b'line1\nline2\n'（12 字节）
  • git ls-files --eol 输出：i/lf w/crlf attr/ a.txt

i/ 是索引，w/ 是工作区，attr/ 是当前生效的属性。三个字段同时打出来，你才知道自己看到的是哪一层。

更能说明问题的是同一个文件的两个哈希：

$ git hash-object a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8
$ git hash-object --no-filters a.txt
8561d5d6dca37a4e5d7a60b130242f748fcfec84
$ git rev-parse :a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8

带过滤器的哈希等于索引里的 blob 哈希，不带过滤器的哈希是磁盘上的原始字节。换句话说：git add 的那一刻文件已经不是原来那份了，改写发生在进入索引之前。这一点决定了后面所有结论 —— 讨论「Git 会不会改我的文件」，必须先问是进库时还是出库时。

autocrlf 三档：同一份文件三种落盘

同一份 CRLF 文件，只改 core.autocrlf，结果如下（三组独立仓库，各跑一次 add 与一次删除后 checkout）：

autocrlfblob 字节ls-files --eol重新 checkout 后工作区add 时 stderr
falseCRLFi/crlf w/crlfCRLF无
trueLFi/lf w/crlfCRLF无
inputLFi/lf w/crlfLFwarning: CRLF will be replaced by LF

true 与 input 的入库结果一样，出库结果相反。官方 git-config 文档对这个变量的定义值得逐字读：「Setting this variable to "true" is the same as setting the text attribute to "auto" on all files and core.eol to "crlf".」以及「This variable can be set to input, in which case no output conversion is performed.」

所以 autocrlf=true 不是「自动处理换行符」，它是一条等价改写：全仓库 text=auto 加 core.eol=crlf。它管不到二进制检测的例外，也管不到已经在库里的 CRLF blob —— 这两件事后面都会讲到。

还有一件容易被忽略的事：本机 git config --system --get core.autocrlf 返回 true，而 git config --global --get core.autocrlf 返回空（退出码 1）。Git for Windows 安装时把这一项写进了系统级配置，于是团队里「谁都没配过」和「谁都配过」同时成立。排查换行符问题时，先跑这两条命令把结论落到具体层级，比看任何教程都有用。

text / text=auto / -text / eol 四个词

属性比配置更值得花时间，因为它跟着仓库走。五种写法，同一份磁盘 CRLF 文件（core.autocrlf=false）：

.gitattributesblobcheckout 出attr 显示
*.txt text=autoLFCRLFtext=auto
*.txt text eol=lfLFLFtext eol=lf
*.txt text eol=crlf（磁盘给的是 LF）LFCRLFtext eol=crlf
*.txt textLFCRLFtext
*.txt -textCRLFCRLF-text

官方 gitattributes 文档的说法是：设了 text 之后「Line endings are normalized to LF in the index every time the file is checked in」；text=auto 多一道内容检测；-text 是「tells Git not to attempt any end-of-line conversion upon checkin or checkout」。

两个坑就藏在这张表里。

第一，eol=lf 不等于「工作区一定是 LF」。官方原文：「This setting uses the same line endings in the working directory as in the index when the file is checked out.」它比的是索引，不是字母 L 和 F。我拿一个历史上以 CRLF 入库的 blob 套上 text eol=lf，checkout 出来仍然是 b'line1\r\nline2\r\n'，而 git status 立刻报 M。想让工作区真的变 LF，得先把 blob 里的 CRLF 清掉。

第二，!text 撤不掉 eol。写 *.txt text eol=lf 再补一行 special.txt !text，本意是让这个文件免转换，实测它的属性仍然显示 text eol=lf。原因是同一份文档里那句「specifying eol automatically sets text if text was left unspecified」—— !text 把 text 退回未指定，eol 立刻又把它设了回去。要真正免转换，两个都写：special.txt -text -eol。

属性谁说了算：目录、顺序、大小写

优先级官方给得很清楚：$GIT_DIR/info/attributes 最高，然后是「.gitattributes file in the same directory as the path in question, and its parent directories up to the toplevel of the work tree」，最后才是全局与系统级。

我建了三级目录验证：根 .gitattributes 写 *.txt text eol=lf，sub/.gitattributes 只写 *.txt eol=crlf（不带 text），sub/deep/.gitattributes 写 *.txt -text。三份文件同内容，结果：

i/lf   w/crlf  attr/text eol=lf      a.txt
i/lf   w/crlf  attr/text eol=crlf    sub/b.txt
i/crlf w/crlf  attr/-text            sub/deep/c.txt

两点：近的覆盖远的；子目录里只写 eol 也不会丢掉父目录给的 text，属性是逐条覆盖而不是整行替换。之后我往 .git/info/attributes 写一行 *.txt -text，根目录那个文件的 attr 立刻变成 -text —— 这项优先级最高，而且不随仓库分发，适合临时排障，不适合长期方案。

还有一个只在 Windows 上出现的变量：core.ignoreCase。同样的 .gitattributes：

*.txt text eol=lf
*.TXT -text

core.ignoreCase=true（Windows 默认）下，a.txt 的属性是 -text，blob 保留 CRLF；把 core.ignoreCase 设成 false 再跑，a.txt 恢复 text eol=lf，只有 b.TXT 是 -text。这也印证了另一条规则：「When more than one pattern matches the path, a later line overrides an earlier line.」后写的赢，而且大小写不敏感时 .txt 与 .TXT 是同一个模式。

二进制与纯 CR：Git 的眼界

text=auto 会自己判断文本与二进制。一个以 \x89PNG\r\n 开头、带 NUL 字节的文件，在 * text=auto eol=lf 下保持原样，ls-files 给 i/-text；跑 git add --renormalize . 扫 20 个文本文件，也正好只动那 20 个，png 一个字节没变。

但显式写 text 就没有这层保护。同一个带 NUL 的文件，.gitattributes 写 *.dat text，入库后 blob 变成 b'ABC\x00\ndef\n' —— CRLF 被清掉了，ls-files --eol 却还在报 i/-text。这个组合是真能损坏图片和可执行文件的，官方文档里那段「for binary files that are accidentally classified as text the conversion can corrupt data」说的就是它。

纯 CR 行尾（老 Mac 风格）是另一回事。一个 b'a\rb\rc\r' 的文件，core.autocrlf=true 下入库后 blob 一个字节不变，ls-files --eol 直接判 i/-text —— 在 Git 眼里它不是文本。把其中一个字符改掉，git diff --numstat 给 1 1，整个文件被当成一行。git add --renormalize 的官方说明也留了边界：「Lone CR characters are untouched, thus while a CRLF cleans to LF, a CRCRLF sequence is only partially cleaned to CRLF.」

顺便说一句 \r\r\n：用 open() 不带 newline='' 写 CSV 就会在磁盘上留下这种字节，我在 Python csv 的八个记录边界 里量过。它在 renormalize 之后只会被清成 \r\n，中间那个 CR 会留下来变成混合行尾，这正是 safecrlf 报警的来源。

历史 CRLF blob 不会自己好

2026-10 那篇 git 2.55 瘦身 里提过一个自锁：git lfs track 写进 .gitattributes 的 -text 会立刻生效。这次换个方向验证同一件事 —— 属性生效了，已入库的内容会不会跟着改。

不会。text=auto 的官方描述里有个条件句：「If it is text and the file was not already in Git with CRLF endings, line endings are converted」。已经以 CRLF 入库的文件正好被这句话豁免。实测：先提交一个 CRLF blob，再提交 * text=auto eol=lf，删掉文件重新 checkout，出来的还是 CRLF，git status 干净得像什么都没发生。

换成显式 text（不带 auto）就更难看：status 开始报 M a.txt，可 blob 还是 CRLF、checkout 出来还是 CRLF，看着像 Git 在闹脾气。真修只有一条路：

$ git add --renormalize .
$ git status --short
$ git commit -m "normalize line endings"

--renormalize 的官方定义就是为这一步写的：「Apply the "clean" process freshly to all tracked files to forcibly add them again to the index. This is useful after changing core.autocrlf configuration or the text attribute in order to correct files added with wrong CRLF/LF line endings.」

实测代价：3 个两行文件 → 3 files changed, 9 insertions(+), 9 deletions(-)；20 个文件 → 20 files changed, 40 insertions(+), 40 deletions(-)；png 不在 diff 里。命令本身完全静默，stdout 与 stderr 都是空，你只能靠 git status 或 git diff --cached --stat 确认它真的动了什么。大仓库里这一步会改写大量 blob，评审和 CI 都要提前打招呼。

status 说改了，diff 说没改

这是本次实验里最值得单独记一条的现象。text 属性下，我把工作区文件从 CRLF 换成 LF（内容逐行相同），然后：

$ git diff --quiet ; echo $?
0
$ git diff --stat
（空）
$ git status --porcelain
M a.txt
$ git hash-object a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8
$ git update-index --refresh
a.txt: needs update

diff 说没有差异（退出码 0），status 坚持说改了，哈希证明内容一模一样。这时 git add a.txt 之后 status 变干净，而 blob 的 sha 仍是 c0d0fb45… —— 什么都没提交，只是把索引里的 stat 信息刷新了一遍。所以看到「只有行尾变了」的改动，先用 git diff 确认是不是真有内容变化，别顺手 git commit -a 制造一个空提交。

反过来，如果属性是 -text，同样的操作就是真改动：a.txt | 4 ++--，两行全红。想让 diff 忽略行尾差异又不改属性，用 git diff --ignore-cr-at-eol。我拿一个 20 行的文件做对照：只改了第 8 行的内容、顺手把整个文件换成 LF，普通 git diff --numstat 给 20 20（整篇重写），加上参数之后是 1 1。评审时看到「一个变量改动、全文件飘红」，多数就是这个原因，和 Windows 路径与文件名的八处静默分歧 属于同一类问题：字符串看着一样，字节不一样。

Troubleshooting：六条原文与处置

报错一：warning: in the working copy of 'a.txt', CRLF will be replaced by LF the next time Git touches it

出现在 autocrlf=input 或 text eol=lf 下 add 一个 CRLF 文件时。它不是错误，是通知：这次已经按 LF 入库，下次 checkout 你会看到 LF。input 的含义就是官方那句「no output conversion is performed」。

报错二：warning: in the working copy of 'a.txt', LF will be replaced by CRLF the next time Git touches it

反过来：autocrlf=true 或 eol=crlf 下 add 一个磁盘上是 LF 的文件。混合行尾文件也会触发，我那个 a\r\nb\nc\r\n 的样本入库后被统一成 a\nb\nc\n。

报错三：fatal: LF would be replaced by CRLF in mixed.txt（退出码 128）

core.safecrlf=true 加上混合行尾时的硬拒绝。官方解释是「Git verifies if the conversion is reversible」—— 纯 CRLF 文件可以通过（我验证过，rc=0），混合行尾不可逆，所以直接挡下来。safecrlf=warn 只警告不挡，false 完全静默。团队统一开 true 能提前拦住损坏，代价是历史脏文件必须先统一行尾才能提交。

报错四：CONFLICT (content): Merge conflict in a.txt 加 Automatic merge failed; fix conflicts and then commit the result.

我复现的现场：base 是三行 CRLF；feat 分支改第 2 行（仍是 CRLF）；main 分支把整个文件换成 LF。合并后冲突块只有 1 个，但块里两侧各三行、内容逐行相同：

<<<<<<< HEAD
one
two
three
=======
one
TWO
three
>>>>>>> feat

逐行对比看不出任何差别，肉眼只能靠 git diff --word-diff 或 cat -A。根因不是文本冲突，是两边对「行」的定义不同。这类冲突不能靠「选一边」解决，必须让两边行尾先一致。

报错五：a.txt: needs update（git update-index --refresh 的输出）

配合 status 长期报 M 使用。它说的是 stat 与索引对不上，不是内容对不上。处置同上一节：git add 刷新，确认 git diff --cached 为空再退出。

报错六：.bat 脚本在 cmd 里报错，但文件看着正常

不是报错文本，而是真实后果。autocrlf=input 且没有属性的情况下，一个 CRLF 的 .bat 提交后再 checkout，工作区拿到的是 b'@echo off\ndir\n'；同一个仓库里给 *.bat 写上 text eol=crlf 之后，checkout 出来是 b'@echo off\r\ndir\r\n'。批处理解析器对纯 LF 的处理并不可靠，这类文件必须钉死。

一份可以直接抄的配置

* text=auto eol=lf
*.bat  text eol=crlf
*.cmd  text eol=crlf
*.ps1  text eol=crlf
*.png  binary
*.jpg  binary
*.pdf  binary

binary 是内置宏，官方定义为 [attr]binary -diff -merge -text，一次把三个属性关掉。* text=auto eol=lf 是最省事的一刀：文本一律按 LF 入库、按 LF 出库，Windows 上唯一需要例外的是 cmd 与 PowerShell 脚本，以及那些按行尾字节做校验的老工具。

配套三条检查，比读文档快：

  • git ls-files --eol | grep -v "i/lf"：列出所有入库不是 LF 的文件，CRLF blob 会在这里露头。
  • git diff --ignore-cr-at-eol --stat：评审前跑一次，把纯行尾噪音从真改动里摘出去。
  • git status --porcelain 与 git diff --quiet 同时跑：一个说改了、一个说没改，就是假改动。

改完属性记得按顺序走：先提交 .gitattributes，再 git add --renormalize .，再提交规范化，最后让所有人重新 clone 或清一次工作区缓存。跳过最后一步，别人本地的 CRLF 工作区会继续把旧字节提交回去。顺便给 CI 留一条 git ls-files --eol 的非零断言，比事后 review 便宜 —— 这和 HTTP 缓存用 ETag 判断内容是否真变了 是同一个思路：字节变了才叫变了。

FAQ

Q：只设 core.autocrlf=true 够不够？

不够。它等价于 * text=auto 加 core.eol=crlf，只对还没进库的文件有效；历史上的 CRLF blob 一个都不会改，text=auto 那句「was not already in Git with CRLF endings」的豁免就是专门留给它们的。想要仓库干净，属性加 renormalize 才是完整答案。

Q：为什么 Linux 和 macOS 的同事从来没遇到这个问题？

因为平台默认值不同：非 Windows 上 eol 的缺省是 lf，autocrlf 常常是 false 或 input，入库出库都是 LF，链条上没有转换点。问题只在跨平台交界处暴露，而交界处通常就是 CI，以及那个唯一用 Windows 的人。

Q：已经提交了几百个 CRLF 文件，怎么一次修干净？

按上一节的四步走，然后在 CI 里加一条 git ls-files --eol | grep "i/crlf" 的非零退出断言，防止新文件再漏进来。注意 --renormalize 会改写 blob，历史 commit 的哈希不变但后续 diff 会变长，PR 需要单独一个 commit 承载这件事。

Q：git ls-files --eol 里的 mixed 是什么意思？

索引或工作区里同一个文件既有 LF 又有 CRLF。它比 crlf 更值得处理，因为混合行尾在 safecrlf=true 下会直接拒绝提交，在合并时又会制造整块冲突。
