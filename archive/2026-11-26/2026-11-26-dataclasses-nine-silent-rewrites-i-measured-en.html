Python dataclasses: nine silent rewrites

pythondataclassdata-modeling

A job object had been running in production for three months without a complaint. Then two different jobs started sharing state: editing the note on job A changed the note on job B. There was no assignment between them anywhere in the business logic. Printing id() settled it — both instances held the same object, because the field was declared as a hashable custom class instance rather than payload: dict = {}.

@dataclass is not sugar for __init__. It is a code generator that runs once, at class creation, and what it generates depends on seven switches that interact with each other. Change one switch and you quietly change two others. I ran three rounds of probes on this machine (CPython 3.13.14, Windows 11 10.0.26300); every claim below has a captured return value or an unedited error message.

TL;DR:

  • An attribute without a type annotation is not a field. Positional arguments slide onto the next field with no exception.
  • Mutable defaults are only rejected when they are unhashable. A hashable custom instance passes and is shared by every instance.
  • With eq=True and frozen=False, __hash__ is None; with eq=False it falls back to id hashing, so two equal-looking instances become two set members.
  • frozen=True blocks the assignment statement, not mutability: object.__setattr__ works and mutable fields keep mutating.
  • slots=True returns a new class. Registries, isinstance checks and class-attribute defaults all break silently.
  • replace() calls __post_init__ again, so side effects run twice; init=False fields cannot be passed to it.
  • Since 3.13, __eq__ compares field by field, so an instance holding NaN no longer equals itself.

Six of the nine never raise anything — 66.7% of these traps stay quiet and only show up in the data. So here is the order I actually use when a field refuses to behave:

Two of the three hooks are decided at class creation

@dataclass does exactly one thing: it reads __annotations__, builds an ordered mapping of fields, generates __init__, __repr__, __eq__, __hash__ and the ordering methods according to the switches, and returns the class it was handed (with slots=True as the single exception, see rewrite five). All of this finishes at import time. Nothing re-reads your definition later.

That has two consequences. First, a field is defined by its annotation, not by its assignment. Second, every silent failure happens in the generation phase: something that should have been generated was not, or something that should have been rejected was not.

One sentence in the docs is easy to skip: fields() returns "a tuple of Field objects that define the fields for this dataclass" and "does not return pseudo-fields which are ClassVar or InitVar". That tuple is the only trustworthy inventory — every diagnosis below starts from it.

Rewrite one · an unannotated attribute is not a field, and positional arguments shift

Five lines reproduce it:

from dataclasses import dataclass, fields

@dataclass
class N:
    x = 0
    y: int = 0

print([f.name for f in fields(N)])   # ['y']
print(N(5).y)                        # 5
print(N().x)                         # 0

x = 0 looks like a field but is only a class attribute: without an annotation it never reaches __annotations__, and the decorator ignores it. fields(N) returns ['y'], so the 5 in N(5) lands on y — no exception, no warning. The instance __dict__ was {'y': 5}.

In real code this shows up as a forgotten annotation:

@dataclass
class Job:
    name: str
    retries = 3          # intended as a default, not even a field
    timeout: int = 30

Job("a", 30) puts 30 into timeout; retries stays a class attribute at 3, cannot be set per instance, and never appears in fields(). The fix is to annotate it: retries: int = 3.

The same "look it up by name and get nothing" shape appeared in the argument layer too: in eight silent divergences in argv parsing, type= only applies to strings that came from the command line. Here it is the annotation that decides membership in the field table.

Rewrite two · mutable defaults are only blocked when they are unhashable

list, dict and set are rejected outright:

ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory

It is tempting to conclude that the decorator protects you from mutable defaults. It does not. It rejects unhashable defaults:

From the docs (3.11 change): Instead of looking for and disallowing objects of type list, dict, or set, unhashable objects are now not allowed as default values. Unhashability is used to approximate mutability.

The same passage adds the sentence that matters most: "There is no general way for Data Classes to detect this condition." Hashability is an approximation of mutability, not a test for it. A custom class with a default __hash__ sails through:

class Box:
    def __init__(self):
        self.n = 0

@dataclass
class Good:
    box: Box = Box()      # no error

a, b = Good(), Good()
a.box.n = 7
print(a.box is b.box)     # True
print(b.box.n)            # 7

Both instances hold the same Box; mutating A mutates B. The rule of thumb is blunt: if it can be a dict key, it can be a default value, even when everything inside it is mutable. The fix is the same as for list:

from dataclasses import dataclass, field

@dataclass
class Good:
    box: Box = field(default_factory=Box)

Note that frozen dataclass instances are hashable, so using one as a default passes the same check and gets shared the same way.

Rewrite three · `__hash__` has three outcomes, and only one survives a set

This is the table I would memorise. The three rules, verbatim:

From the docs (the three hash rules): If eq and frozen are both true, by default @dataclass will generate a __hash__() method for you. If eq is true and frozen is false, __hash__() will be set to None, marking it unhashable (which it is, since it is mutable). If eq is false, __hash__() will be left untouched meaning the __hash__() method of the superclass will be used (if the superclass is object, this means it will fall back to id-based hashing).

Three classes, three completely different behaviours:

@dataclass
class H1:
    x: int

@dataclass(eq=False)
class H2:
    x: int

@dataclass(frozen=True)
class H3:
    x: int

H1.__hash__ is None, so hash(H1(1)) raises TypeError: unhashable type: 'H1'. For H2, __hash__ is object.__hash__ is True, which means len({H2(1), H2(1)}) is 2 and H2(1) == H2(1) is False — turning off eq also turns off content comparison. Only H3 behaves the way most people assume: len({H3(1), H3(1)}) is 1.

One more detail worth knowing: A() == B() between two different dataclasses is False even when the fields match exactly. The docs' "Both instances in the comparison must be of the identical type" is not a formality.

Rewrite four · `frozen=True` blocks the assignment, not mutability

@dataclass(frozen=True)
class F:
    x: int
    tags: list = field(default_factory=list)

f = F(1)
f.x = 2                      # FrozenInstanceError: cannot assign to field 'x'
object.__setattr__(f, "x", 99)
f.tags.append("mutated")
print(f.x, f.tags)           # 99 ['mutated']

frozen works by adding __setattr__ and __delattr__ to the class; hitting them raises FrozenInstanceError, a subclass of AttributeError. It cannot stop you from bypassing __setattr__, and it cannot stop a mutable field from mutating. "Frozen means immutable" is a convention, not a guarantee.

Three related limits are hard errors:

  • Defining __setattr__ in the class and passing frozen=True gives TypeError: Cannot overwrite attribute __setattr__ in class A
  • A frozen class cannot have a non-frozen subclass: TypeError: cannot inherit non-frozen dataclass from a frozen one
  • A non-frozen class cannot have a frozen subclass: TypeError: cannot inherit frozen dataclass from a non-frozen one

The last one bites during refactors: flip a base class to frozen=True and every subclass fails at import time, all at once.

There is a quieter variant. Assigning inside __post_init__ of a frozen class raises FrozenInstanceError: cannot assign to field 'b'. Derived values must go through object.__setattr__(self, "b", ...), which is exactly what the generated __init__ does — the docs note that with frozen=True, "__init__() cannot use simple assignment to initialize fields, and must use object.__setattr__()".

Rewrite five · `slots=True` returns a new class, and your registry keeps the old one

This is the only place where the docs contradict themselves. The general description says:

From the docs (decorator overview): The decorator returns the same class that it is called on; no new class is created.

The slots parameter says:

From the docs (the slots parameter): If true (the default is False), __slots__ attribute will be generated and new class will be returned instead of the original one.

Each sentence is true on its own; read together they are wrong. Three consequences, all measured.

First, class attributes disappear. Without slots, Plain.x is 1. With slots, Slot.x becomes a member_descriptor, and getattr(Slot, "x", None) == 1 is False.

Second, __dict__ and weak references are gone:

@dataclass(slots=True)
class S:
    x: int = 1

s = S()
s.__dict__        # AttributeError: 'S' object has no attribute '__dict__'
weakref.ref(s)    # TypeError: cannot create weak reference to 'S' object

Weak references require weakref_slot=True as well, available since 3.11; the two switches must be combined.

Third, and this is the dangerous one: the registry holds the old class. I wrote the standard registration decorator and wrapped it with slots=True:

registry = []

def register(cls):
    registry.append(cls)
    return cls

@dataclass(slots=True)
@register
class X:
    a: int = 0

print(registry[0] is X)              # False
print(isinstance(X(), registry[0]))  # False

Two False values and no exception. Any plugin-style code that registers a class and later checks it with isinstance breaks silently the moment slots=True is added. Reversing the decorator order (registration outermost) captures the new class instead — the outcome depends on which line is on top.

One more: writing __slots__ by hand and also passing slots=True raises ValueError: 'x' in __slots__ conflicts with class variable. The docs say TypeError for that case; the measured type is ValueError.

Rewrite six · when `__post_init__` runs, and why `replace()` runs it twice

__post_init__ is not a hook; it is a single call appended to the generated __init__. Its trigger condition therefore follows init:

From the docs: If no __init__() method is generated, then __post_init__() will not automatically be called.

Fields declared with init=False still need __post_init__ to get a value, but their default factory is always invoked — "the default factory function will always be called from the generated __init__() function".

The real trap is replace():

counter = {"n": 0}

@dataclass
class P:
    a: int
    b: int = 0

    def __post_init__(self):
        counter["n"] += 1
        self.b = self.a * 2

p = P(3)              # counter = {'n': 1}, b = 6
q = replace(p, a=5)   # counter = {'n': 2}, q.b = 10

The docs state: "The newly returned object is created by calling the __init__() method of the dataclass. This ensures that __post_init__(), if present, is also called." If that method sends notifications, writes audit rows or decrements inventory, one replace() re-runs the whole side effect. My counter went from 1 to 2 and b from 6 to 10.

There is a hard boundary: init=False fields cannot be passed to replace() — TypeError: field b is declared with init=False, it cannot be specified with replace(). And a misspelled field name gives TypeError: R.__init__() got an unexpected keyword argument 'zzz', which points at __init__ rather than at replace(); check the spelling first.

Rewrite seven · `MISSING` is a sentinel, and `if f.default:` misreads 0 and the empty string

Anyone writing a generic serializer, form renderer or config exporter iterates fields() to read default values. This trap is unavoidable:

@dataclass
class D:
    a: int = 0
    b: list = field(default_factory=list)
    c: str = ""

Measured, field by field:

  • a: default is MISSING is False, but bool(0) is False
  • b: default is MISSING is True, because it uses default_factory
  • c: default is MISSING is False, but bool("") is False

So if f.default: classifies a and c as having no default, and b as having one. All three are wrong. Test both sentinels separately:

from dataclasses import MISSING

for f in fields(D):
    has_default = f.default is not MISSING
    has_factory = f.default_factory is not MISSING

MISSING is a module-level sentinel; compare with is. Two related errors are explicit enough to need no guessing: fields() on a non-dataclass raises TypeError: must be called with a dataclass type or instance, and asdict() raises asdict() should be called on dataclass instances.

Rewrite eight · `order=True` compares declaration order, and `kw_only` fixes the order but not pattern matching

order=True generates comparisons over a tuple of fields in declaration order, so a mixed None breaks sorting:

@dataclass(order=True)
class O:
    v: int

sorted([O(2), O(None)])
# TypeError: '<' not supported between instances of 'NoneType' and 'int'

Two more preconditions. order=True requires eq=True, otherwise ValueError: eq must be true if order is true. And if the class already defines __lt__, passing order=True raises TypeError: Cannot overwrite attribute __lt__ in class C Consider using functools.total_ordering.

The field-order dead end — a defaulted field cannot precede a field without a default: TypeError: non-default argument 'b' follows default argument 'a' — shows up most often with inheritance: the base class is fully defaulted, the subclass adds one required field, and import fails. kw_only=True resolves it:

@dataclass(kw_only=True)
class C(P):
    b: int

Measured: C(b=3) constructs fine with a defaulting to 0. The cost is that those fields leave __match_args__ — "Keyword-only fields are not included in __match_args__". Positional pattern matching then fails:

@dataclass(kw_only=True)
class Q:
    x: int
    y: int

match Q(x=0, y=0):
    case Q(0, 0):     # TypeError: Q() accepts 0 positional sub-patterns (2 given)
        pass

Keyword patterns (case Q(x=0)) still work. The KW_ONLY pseudo-field behaves the same way: it never appears in fields(), __match_args__ keeps only ('a',), and K(1, 2) raises takes from 1 to 2 positional arguments but 3 were given.

Rewrite nine · since 3.13 `__eq__` compares field by field, so NaN instances stop equalling themselves

This one is a version drift, documented under eq:

From the docs (3.13 change): The generated __eq__ method now compares each field individually (for example, self.a == other.a and self.b == other.b), rather than comparing tuples of fields as in previous versions.

Why does it bite? Tuple comparison short-circuits on identity: (n,) == (n,) returns True when both elements are the same nan object, even though n == n is False. Per-field comparison has no such shortcut:

n = float("nan")

P(n) == P(n)        # False   (3.13)
(n,) == (n,)        # True    (the old shape)
n == n              # False

The consequence: code that deduplicates dataclass instances or uses == to decide "this record did not change" will treat one record as two as soon as a field holds NaN — a missing float, a null from pandas, a division by zero. In numerical pipelines this is not hypothetical.

Two decorator conflicts belong here as well, both hard errors: unsafe_hash=True together with a hand-written __hash__ gives TypeError: Cannot overwrite attribute __hash__ in class B; applying @dataclass twice is safe — it returns the same class object and the field table is unchanged.

Troubleshooting: eight real errors and their fixes

All eight come from the unedited output of CPython 3.13.14 on this machine, ordered by symptom, cause and fix. The snippets are copyable.

Error one · ValueError: mutable default, use default_factory

Symptom: the class definition line fails at import with ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory.

Cause: list is unhashable, so it is rejected as a default. This is protection, not a bug.

Fix:

from dataclasses import dataclass, field

@dataclass
class Job:
    items: list = field(default_factory=list)

Error two · TypeError: non-default argument follows default argument

Symptom: a fully defaulted base class plus one required field in the subclass fails at import with TypeError: non-default argument 'b' follows default argument 'a'.

Cause: fields are collected in reverse MRO order, base fields first; a field without a default cannot follow one with a default.

Fix one: give the subclass field a default. Fix two: use keyword-only fields:

@dataclass(kw_only=True)
class Child(Base):
    b: int

Error three · TypeError: cannot inherit non-frozen dataclass from a frozen one

Symptom: changing the base class to frozen breaks every subclass at import time.

Cause: frozen and non-frozen classes cannot share an inheritance chain, in either direction.

Fix: make the whole chain frozen=True, or replace inheritance with composition by holding the frozen instance as a field.

Error four · TypeError: unhashable type

Symptom: putting an instance in a set or using it as a dict key raises TypeError: unhashable type: 'H1'.

Cause: with eq=True and frozen=False, the generated __hash__ is explicitly set to None.

Fix: use frozen=True for field-based hashing; or exclude mutable fields with field(compare=False) and add unsafe_hash=True; or key on a tuple.

Error five · FrozenInstanceError: cannot assign to field

Symptom: assigning inside __post_init__ of a frozen class raises FrozenInstanceError: cannot assign to field 'b'.

Cause: frozen installs __setattr__, and that assignment goes through it.

Fix:

def __post_init__(self):
    object.__setattr__(self, "b", self.a * 2)

Error six · ValueError: eq must be true if order is true

Symptom: adding eq=False while asking for ordering fails at definition time with ValueError: eq must be true if order is true.

Cause: the ordering methods need equality semantics underneath.

Fix: drop eq=False; if you truly do not want __eq__, implement __lt__ and friends yourself and skip order=True.

Error seven · AttributeError: object has no attribute __dict__

Symptom: after enabling slots=True, serializers, vars() and obj.__dict__.update(...) all raise AttributeError: 'S' object has no attribute '__dict__'.

Cause: instances of a slots class have no instance dictionary.

Fix: read values through fields(), or do not enable slots for that class:

{k: getattr(obj, k) for k in (f.name for f in fields(obj))}

Error eight · TypeError: field is declared with init=False

Symptom: using replace() to change a derived field raises TypeError: field b is declared with init=False, it cannot be specified with replace().

Cause: replace() re-calls __init__, and an init=False field is not one of its parameters.

Fix: replace() the source field and let __post_init__ recompute, or build a new instance, or make the field init=True.

Four checks before this ships

Check one · count the field table against the annotations. Run print([(f.name, f.type) for f in fields(MyClass)]) and walk it line by line against the class body. A missing name means a missing annotation.

Check two · prove default sharing with id(). For every field with a default, build two instances and compare id(getattr(a, name)) == id(getattr(b, name)). Any True means that field must move to default_factory.

Check three · pick the hash strategy by use. Needs to go in a set or act as a dict key: frozen=True. Only needs ==: keep eq=True, frozen=False and accept that it is unhashable. Needs identity semantics: write eq=False and say why in a comment.

Check four · if slots=True, re-run every isinstance and registry path. Print the class stored in the registry and compare it with the current class using is. No static check will catch this one.

FAQ

Q: Why does default=[] fail while default=SomeObject() passes?

Because the check tests hashability, not mutability. A list is unhashable and gets rejected; a plain instance is hashable and gets shared by every instance. That has been the rule since 3.11, and the docs admit it is an approximation.

Q: Is slots=True worth enabling?

Only under two conditions: the class has many fields and you create enough instances that memory genuinely matters, and nothing in the codebase registers the class object and later checks it with isinstance. Otherwise you trade memory for three silent failures: class attributes become descriptors, __dict__ disappears, and the registry keeps the old class.

Q: Can a frozen instance be used as a dict key?

Yes. eq=True plus frozen=True generates a field-based __hash__; two instances with identical content collapse to one set member in my run. But if any field holds a list or dict, hashing raises unhashable type at runtime, so the fields of a frozen class have to be frozen too.

Q: Do these behaviours differ from 3.12?

Yes, in more than one place. Python 3.11 changed the mutable-default check from a type whitelist to a hashability test; 3.13 changed __eq__ from tuple comparison to per-field comparison, so NaN-holding instances stop equalling themselves. Everything here was measured on 3.13.14, and I would re-run check two against your own classes before a version bump.
