dataclass 不是语法糖：九个静默改判

pythondataclass数据模型

一个任务对象跑了三个月没出过事，昨天开始串数据：两个不同任务的 payload 变成了同一个 dict，改 A 的备注，B 的备注跟着变。死盯那段业务代码找不到赋值的地方，最后打印 id() 才发现 —— 两个实例的 payload 从头到尾就是同一个对象，因为类定义里写的不是 payload: dict = {}，而是一个可哈希的自定义类实例当默认值。

@dataclass 不是「省掉 __init__ 的语法糖」。它是一个在类创建那一刻执行一次的代码生成器，生成什么由七个开关决定；开关之间还会互相牵连，改一个会顺带改掉你没看的那几个。我在本机（CPython 3.13.14 / Windows 11 10.0.26300）写了三轮探针，把每个改判都跑出可复现的输出，下面九条全部有原样报错或原样返回值。

TL;DR：

  • 没有类型注解的属性不是字段，位置参数会安静地滑到下一个字段上，不抛异常。
  • 可变默认值只在「不可哈希」时被拦；可哈希的自定义实例当默认值会被所有实例共享。
  • eq=True + frozen=False 时 __hash__ 是 None，这类实例进不了集合；eq=False 时退回 id 哈希，内容相同的两个实例在集合里是两个。
  • frozen=True 只挡 obj.x = ... 这一种写法，object.__setattr__ 与可变字段的内容照样能改。
  • slots=True 会返回一个新类：旧类上的注册表、isinstance 检查、类属性默认值全部失效，且不报错。
  • replace() 会重新调用 __post_init__，副作用执行两次；init=False 的字段不能传给 replace()。
  • 3.13 起 __eq__ 改成逐字段比较，含 NaN 的实例不再等于自己（旧实现走元组比较，对同一对象有身份短路）。

九个改判里有六个连异常都不抛，只在结果里悄悄错 —— 也就是 66.7% 的坑不会自己跳出来。所以先说一个能落地的排查顺序，后面每条都在这条链上：

先把执行时机说清楚：三个钩子里的两个在类创建时定死

@dataclass 做的事只有一件：读 __annotations__，把字段整理成一个有序映射，再按参数生成 __init__、__repr__、__eq__、__hash__、比较方法，最后把类原样返回（slots=True 是唯一的例外，见改判五）。整个过程在 import 时结束，运行期不再回头看你的定义。

这意味着两件事。第一，字段的判定标准是注解，不是赋值。第二，所有「静默」都发生在生成阶段：该生成的没生成、该拦的没拦，运行时不会有人提醒你。

官方文档里有一句很容易被跳过的话：fields() 返回的是「用于定义这个 dataclass 的 Field 对象元组」，并且「不返回 ClassVar 或 InitVar 这类伪字段」。所以 fields() 的结果就是唯一可信的字段清单 —— 后面所有排查我都从它开始。

改判一 · 没有注解的属性不是字段，位置参数会安静地错位

最小复现只有五行：

from dataclasses import dataclass, fields

@dataclass
class N:
    x = 0
    y: int = 0

print([f.name for f in fields(N)])   # ['y']
print(N(5).y)                        # 5
print(N().x)                         # 0

x = 0 看着像个字段，实际上只是一条普通的类属性：没有注解就不进 __annotations__，@dataclass 压根不认它。fields(N) 只返回 ['y']，而 N(5) 里的 5 被唯一那个字段 y 接走了 —— 没有异常、没有警告，N(5).y 就是 5。我打印了实例的 __dict__，只有 {'y': 5}。

真实代码里这一条最常见的形态是漏写注解：

@dataclass
class Job:
    name: str
    retries = 3          # 想写默认值，结果连字段都不是
    timeout: int = 30

Job("a", 30) 会把 30 塞给 timeout，retries 永远是类属性 3，实例上改不了、fields() 里也找不到。修法只有一条：补注解，写成 retries: int = 3。

同类的「按名字找东西」问题在参数层也出现过一次：命令行参数解析的八个静默分歧 里，type= 只对命令行传来的字符串生效；这一次是注解决定谁进字段表。

改判二 · 可变默认值只拦「不可哈希」的那一半

list、dict、set 当默认值会直接报错：

ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory

于是很多人以为「@dataclass 会帮我拦住可变默认值」。文档写得很清楚，它拦的是不可哈希，不是可变：

文档原文（3.11 变更）：Changed in version 3.11: Instead of looking for and disallowing objects of type list, dict, or set, unhashable objects are now not allowed as default values. Unhashability is used to approximate mutability.

同一段文档还留了一句更关键的话：「There is no general way for Data Classes to detect this condition.」意思是用哈希近似可变性只是一个折中。我拿一个带默认 __hash__ 的自定义类试了一下，它顺利通过了检查：

class Box:
    def __init__(self):
        self.n = 0

@dataclass
class Good:
    box: Box = Box()      # 不报错

a, b = Good(), Good()
a.box.n = 7
print(a.box is b.box)     # True
print(b.box.n)            # 7

两个实例拿到的是同一个 Box，改 A 就是改 B —— 就是文章开头那个事故的最小形态。判据很简单：能在哈希表里当键，就可以当默认值，哪怕它内部全是可变状态。修法和 list 一样，用 default_factory：

from dataclasses import dataclass, field

@dataclass
class Good:
    box: Box = field(default_factory=Box)

顺带一提，frozen=True 的 dataclass 实例是可哈希的，所以拿它当默认值一样能通过检查、一样会被共享。

改判三 · `__hash__` 有三种结局，只有一种能进集合

这段是我觉得最值得背下来的一张表，文档原文三条规则：

文档原文（哈希三条规则）：If eq and frozen are both true, by default @dataclass will generate a __hash__() method for you. If eq is true and frozen is false, __hash__() will be set to None, marking it unhashable (which it is, since it is mutable). If eq is false, __hash__() will be left untouched meaning the __hash__() method of the superclass will be used (if the superclass is object, this means it will fall back to id-based hashing).

实测三个类，行为完全不同：

@dataclass
class H1:
    x: int

@dataclass(eq=False)
class H2:
    x: int

@dataclass(frozen=True)
class H3:
    x: int

H1.__hash__ 是 None，hash(H1(1)) 抛 TypeError: unhashable type: 'H1'。H2.__hash__ is object.__hash__ 为 True，于是 {H2(1), H2(1)} 的长度是 2，而 H2(1) == H2(1) 竟然是 False —— 因为关掉 eq 就等于关掉按内容比较，只剩身份。H3 才是大多数人以为的默认行为：{H3(1), H3(1)} 长度 1。

顺带一个容易忽略的点：A() == B() 在不同 dataclass 之间是 False，即使字段完全一样。文档里那句「Both instances in the comparison must be of the identical type」不是客套话。

改判四 · `frozen=True` 挡的是赋值语句，不是可变性

@dataclass(frozen=True)
class F:
    x: int
    tags: list = field(default_factory=list)

f = F(1)
f.x = 2                      # FrozenInstanceError: cannot assign to field 'x'
object.__setattr__(f, "x", 99)
f.tags.append("mutated")
print(f.x, f.tags)           # 99 ['mutated']

frozen 的实现是往类里加 __setattr__ / __delattr__，命中就抛 FrozenInstanceError（AttributeError 的子类）。它挡不住两件事：绕过 __setattr__ 的写法，以及字段内部的可变对象。所以「frozen 等于不可变」这句话在 Python 里只能算约定。

这条路上还有三个连带限制，都是真报错：

  • 类里自己定义了 __setattr__ 又传 frozen=True → TypeError: Cannot overwrite attribute __setattr__ in class A
  • 冻结类不能有非冻结子类 → TypeError: cannot inherit non-frozen dataclass from a frozen one
  • 非冻结类不能有冻结子类 → TypeError: cannot inherit frozen dataclass from a non-frozen one

最后一条在继承链上特别扎人：基类哪天改成 frozen=True，所有子类会同时炸，而且报错是在 import 时抛的。

还有一个更隐蔽的：在 frozen=True 的 __post_init__ 里给字段赋值，同样会抛 FrozenInstanceError: cannot assign to field 'b'。要初始化派生字段，得写 object.__setattr__(self, "b", ...)；文档里也明说了 frozen=True 时 __init__ 内部就是这么干的，「__init__() cannot use simple assignment to initialize fields, and must use object.__setattr__()」。

改判五 · `slots=True` 会返回一个新类，你的注册表里留下的是旧的

这是九条里唯一一个「文档自己前后不一致」的地方。装饰器总述写的是：

装饰器总述原文：The decorator returns the same class that it is called on; no new class is created.

而 slots 参数那一段写的是：

slots 参数原文：If true (the default is False), __slots__ attribute will be generated and new class will be returned instead of the original one.

两句话各自成立，合起来读就是错的。实测后果有三个。

第一，类属性没了。不加 slots 时 Plain.x 是 1；加了之后 Slot.x 变成一个 member_descriptor，getattr(Slot, "x", None) 已经不等于 1。

第二，__dict__ 没了，弱引用也没了：

@dataclass(slots=True)
class S:
    x: int = 1

s = S()
s.__dict__        # AttributeError: 'S' object has no attribute '__dict__'
weakref.ref(s)    # TypeError: cannot create weak reference to 'S' object

要弱引用必须再传 weakref_slot=True（3.11 起才有），两个参数一起用才成立。

第三，也是最危险的一条：注册表里存的是旧类。我写了个典型的注册装饰器，再用 slots=True 包一层：

registry = []

def register(cls):
    registry.append(cls)
    return cls

@dataclass(slots=True)
@register
class X:
    a: int = 0

print(registry[0] is X)              # False
print(isinstance(X(), registry[0]))  # False

两个 False，一个异常都没有。任何依赖「注册时拿到类、运行时用 isinstance 判断」的插件式代码，开了 slots=True 就静默失效。装饰器顺序反过来（@register 在最外层）才能拿到新类，而这取决于你写的是哪一行在上面。

再加一条：类里已经手写了 __slots__ 又传 slots=True，直接 ValueError: 'x' in __slots__ conflicts with class variable。文档那句「If __slots__ is already defined in the class, then TypeError is raised」和实测的类型也不一致 —— 实测是 ValueError。

改判六 · `__post_init__` 的触发条件，与 `replace()` 的二次执行

__post_init__ 不是钩子，是生成出来的 __init__ 末尾的一行调用。所以它的触发条件跟着 init 走：

文档原文：If no __init__() method is generated, then __post_init__() will not automatically be called.

init=False 的字段也一样要走 __post_init__ 才能算出值，但它的默认工厂会被调用（文档：「the default factory function will always be called from the generated __init__() function」）。

真正容易翻车的是 replace()：

counter = {"n": 0}

@dataclass
class P:
    a: int
    b: int = 0

    def __post_init__(self):
        counter["n"] += 1
        self.b = self.a * 2

p = P(3)              # counter = {'n': 1}, b = 6
q = replace(p, a=5)   # counter = {'n': 2}, q.b = 10

文档原话是「The newly returned object is created by calling the __init__() method of the dataclass. This ensures that __post_init__(), if present, is also called.」如果 __post_init__ 里有发通知、写审计日志、扣库存这类副作用，replace() 一次就等于再跑一遍业务。我实测计数从 1 变 2，b 从 6 变 10。

另一条硬边界：init=False 的字段不能传给 replace()，报 TypeError: field b is declared with init=False, it cannot be specified with replace()。而 replace() 传一个不存在的字段，报的是 TypeError: R.__init__() got an unexpected keyword argument 'zzz' —— 看到这句先查字段名拼写，别去查 replace 的实现。

改判七 · `MISSING` 是个哨兵，`if f.default:` 会把 0 和空串判成「没写」

要给字段做通用的序列化、表单渲染或者配置导出，几乎一定会遍历 fields() 读默认值。这里有个必然踩的坑：

@dataclass
class D:
    a: int = 0
    b: list = field(default_factory=list)
    c: str = ""

实测三行结果：

  • a：default is MISSING 为 False，但 bool(0) 是 False
  • b：default is MISSING 为 True（因为用的是 default_factory）
  • c：default is MISSING 为 False，但 bool("") 是 False

于是 if f.default: 会把 a 和 c 判成「没有默认值」，把 b 判成「有默认值」—— 三个全错。正确写法是两个哨兵分别判：

from dataclasses import MISSING

for f in fields(D):
    has_default = f.default is not MISSING
    has_factory = f.default_factory is not MISSING

MISSING 是模块级哨兵，只能用 is 比。顺带提醒：fields() 对非 dataclass 会抛 TypeError: must be called with a dataclass type or instance，asdict() 对非实例抛 asdict() should be called on dataclass instances —— 这两个错误信息足够直接，不用猜。

改判八 · `order=True` 比的是声明顺序，`kw_only` 救得了顺序救不了模式匹配

order=True 生成的是按字段声明顺序的元组比较，所以字段类型混着 None 就炸：

@dataclass(order=True)
class O:
    v: int

sorted([O(2), O(None)])
# TypeError: '<' not supported between instances of 'NoneType' and 'int'

同样的坑还有一个前置条件：order=True 必须配 eq=True，否则 ValueError: eq must be true if order is true。而类里已经有 __lt__ 时再传 order=True，报 TypeError: Cannot overwrite attribute __lt__ in class C Consider using functools.total_ordering。

字段顺序的死局（有默认值的字段不能排在没默认值的字段前面，TypeError: non-default argument 'b' follows default argument 'a'）在继承时最容易出现：基类全带默认值，子类加一个必填字段就炸。kw_only=True 能救：

@dataclass(kw_only=True)
class C(P):
    b: int

实测 C(b=3) 正常构造，a 取默认 0。但代价是这些字段会从 __match_args__ 里消失 —— 文档写着「Keyword-only fields are not included in __match_args__」。我拿位置模式匹配试了下：

@dataclass(kw_only=True)
class Q:
    x: int
    y: int

match Q(x=0, y=0):
    case Q(0, 0):     # TypeError: Q() accepts 0 positional sub-patterns (2 given)
        pass

关键字匹配 case Q(x=0) 正常，位置匹配直接抛 TypeError。KW_ONLY 伪字段同理：fields() 里看不到它，__match_args__ 只留 ('a',)，K(1, 2) 报 takes from 1 to 2 positional arguments but 3 were given。

改判九 · 3.13 起 `__eq__` 逐字段比较，含 NaN 的实例不再等于自己

这条是版本漂移，写在文档的 eq 参数下：

文档原文（3.13 变更）：The generated __eq__ method now compares each field individually (for example, self.a == other.a and self.b == other.b), rather than comparing tuples of fields as in previous versions.

为什么这个改动会咬人？因为元组比较对同一个对象有身份短路：(n,) == (n,) 在两个元素是同一个 nan 对象时返回 True，尽管 n == n 是 False。逐字段比较没有这条短路。实测：

n = float("nan")

P(n) == P(n)        # False   （3.13）
(n,) == (n,)        # True    （旧实现的形状）
n == n              # False

后果是：用 dataclass 实例当去重键、或者拿 == 判「这条记录没变」的代码，只要字段里有 NaN（浮点缺失值、pandas 出来的空值、除以零后的结果），升级到 3.13 之后同一条数据会被判成不同的两条。数值场景里这不是理论问题。

顺带把另外两条装饰器冲突也说清楚，都是真报错：unsafe_hash=True 与手写 __hash__ 同时存在 → TypeError: Cannot overwrite attribute __hash__ in class B；重复套 @dataclass 则是安全的（实测返回的仍是同一个类对象，字段表不变）。

Troubleshooting: 八个真实报错与修法

下面八个报错全部来自本机 3.13.14 的原样输出，按「现象 → 原因 → 修法」排列，代码块可直接复制。

报错一 · ValueError: mutable default 后面跟着 use default_factory

现象：类定义那一行就炸，import 阶段失败，抛 ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory。

原因：list 不可哈希，被当成可变默认值拦掉。这是保护，不是 bug。

修法：

from dataclasses import dataclass, field

@dataclass
class Job:
    items: list = field(default_factory=list)

报错二 · TypeError: non-default argument follows default argument

现象：基类全给默认值，子类加必填字段，import 时抛 TypeError: non-default argument 'b' follows default argument 'a'。

原因：字段顺序按 MRO 逆序拼装，基类字段在前，有默认值的字段后面不能再出现没默认值的字段。

修法一，给子类字段也加默认值；修法二，开 kw_only=True：

@dataclass(kw_only=True)
class Child(Base):
    b: int

报错三 · TypeError: cannot inherit non-frozen dataclass from a frozen one

现象：改了基类的 frozen，所有子类同时挂，报错发生在 import 阶段。

原因：冻结与不冻结不能混在一条继承链上，两个方向都拦。

修法：整条链统一 frozen=True，或者把冻结的基类改成组合（把实例当字段）而不是继承。

报错四 · TypeError: unhashable type

现象：把 dataclass 实例塞进 set 或当 dict 键时抛 TypeError: unhashable type: 'H1'。

原因：eq=True 且 frozen=False 时，生成的 __hash__ 被显式设为 None。

修法：要么 frozen=True（按字段哈希），要么把可变字段用 field(compare=False) 排除在比较之外再配 unsafe_hash=True，要么换成 tuple 键。

报错五 · FrozenInstanceError: cannot assign to field

现象：frozen=True 的类，在 __post_init__ 里给字段赋值，抛 FrozenInstanceError: cannot assign to field 'b'。

原因：frozen 加的是 __setattr__，__post_init__ 里那句赋值照样走它。

修法：

def __post_init__(self):
    object.__setattr__(self, "b", self.a * 2)

报错六 · ValueError: eq must be true if order is true

现象：只想排序，顺手写了 eq=False，定义时抛 ValueError: eq must be true if order is true。

原因：排序方法需要相等语义兜底。

修法：去掉 eq=False；确实不想要 __eq__，就自己实现 __lt__ 等方法，不要传 order=True。

报错七 · AttributeError: object has no attribute __dict__

现象：开了 slots=True 之后，序列化库、vars()、obj.__dict__.update(...) 全部报 AttributeError: 'S' object has no attribute '__dict__'。

原因：__slots__ 生成的类实例没有实例字典。

修法：改成显式遍历 fields() 取值，或者别对这个类开 slots：

{k: getattr(obj, k) for k in (f.name for f in fields(obj))}

报错八 · TypeError: field is declared with init=False, it cannot be specified with replace()

现象：想用 replace() 改一个派生字段，抛 TypeError: field b is declared with init=False, it cannot be specified with replace()。

原因：replace() 是重新调 __init__，而 init=False 的字段不在 __init__ 的参数里。

修法：先 replace() 改源字段，让 __post_init__ 重算；确实要改派生值，就构造新实例或者把该字段改成 init=True。

上线前要跑的四条检查

检查一 · 字段表对着注解数一遍。print([(f.name, f.type) for f in fields(MyClass)])，和类定义逐行对。数量对不上就是漏了注解。

检查二 · 用 id() 验默认值共享。对每个带默认值的字段，造两个实例比 id(getattr(a, name)) == id(getattr(b, name))。返回 True 的字段必须改成 default_factory。

检查三 · 按用途选哈希策略。要进 set / 当 dict 键：frozen=True；只用 == 判等：保持 eq=True, frozen=False 并接受它不可哈希；要 id 语义：显式写 eq=False 并在注释里说明原因。

检查四 · 有 slots=True 就重跑一遍 isinstance 与注册逻辑。把注册表里的类打印出来，和当前类比 is。这一条只能靠实测，静态检查看不出来。

eq=True（默认）可以当字典键__hash__ 是 None，抛 unhashable type
eq=False只是不比内容退回 id 哈希，内容相同的两个实例在集合里算两个
frozen=True完全不可变只挡赋值语句；object.__setattr__ 与可变字段内部照改
slots=True只是省内存返回新类；isinstance 与注册表失效；类属性变描述符

FAQ

Q：为什么 default=[] 报错，default=SomeObject() 不报错？

因为检查的是哈希能力，不是可变性。list 不可哈希 → 被拦；普通类实例可哈希 → 放行，然后被所有实例共享。3.11 起就是这么判的，文档也承认这只是近似（「There is no general way for Data Classes to detect this condition」）。

Q：slots=True 到底值不值得开？

只在两个前提下开：字段数量大、实例数量多到内存真的吃紧；以及代码里没有任何「注册类对象再用 isinstance 判断」的地方。否则省下的内存换来的是三个静默失效：类属性变描述符、__dict__ 消失、注册表里留下旧类。

Q：frozen=True 的实例能当字典键吗？

能。eq=True + frozen=True 会生成按字段的 __hash__，实测同一个内容造两次进 set 只剩 1 个。但字段里如果有 list / dict，哈希会在运行期抛 unhashable type，所以冻结类的字段本身也得是冻结的。

Q：这些行为和 3.12 之间有差别吗？

有，而且不止一处。3.11 把可变默认值的检查从「类型白名单」改成「不可哈希」；3.13 把 __eq__ 从元组比较改成逐字段比较（含 NaN 的实例不再等于自己）。我这份实测是 3.13.14 上的结果，跨版本迁移时建议用上面「检查二」的脚本在你自己的类上重跑一遍。

如果你也在排查「明明赋值了却没生效」这类问题，可以顺着另外三条线看：不写 encoding 时 Python 查哪张表 讲的是默认值从哪来，测试全绿但代码是坏的 讲的是断言为什么没拦住，subprocess 的七个静默失效 讲的是退出码为什么是 0。这三篇和本篇共用一个判断口径：先确认对象到底是什么，再谈它表现成什么样。
