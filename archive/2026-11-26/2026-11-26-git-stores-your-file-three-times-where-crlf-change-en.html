Git Stores Your File Three Times: Where CRLF Changes

Gitline endingsversion control

Three lines in a text file. I changed two letters on the middle line. The merge handed me one big conflict block: three lines on the left, three on the right, identical line by line, differing only in the bytes at the end of each line.

That is not a bug. Git stores the same file three times, and you spend most of your day looking at one of those copies.

I split the question into twelve experiments on a single machine: Windows 11 10.0.26300, git version 2.55.0.windows.3, every repo isolated with GIT_CONFIG_GLOBAL and GIT_CONFIG_SYSTEM pointing at an empty file so my own config could not leak in. Every byte and every warning below is raw output.

Three copies, one file

Take a two-line file, line1\r\nline2\r\n, 14 bytes, under core.autocrlf=true:

  • work tree: b'line1\r\nline2\r\n'
  • index and blob: b'line1\nline2\n', 12 bytes
  • git ls-files --eol: i/lf w/crlf attr/ a.txt

i/ is the index, w/ is the work tree, attr/ is the attribute that applies. Print all three and you finally know which copy you are looking at.

The sharper test is hashing the same file twice:

$ git hash-object a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8
$ git hash-object --no-filters a.txt
8561d5d6dca37a4e5d7a60b130242f748fcfec84
$ git rev-parse :a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8

The filtered hash equals the blob in the index. The unfiltered hash is the disk. In other words, by the time git add finishes, the file is not the file anymore. The rewrite happens before the index ever sees it, which settles the most common argument about this topic: whether Git touches your file depends entirely on which direction you are asking about.

autocrlf in three settings

One CRLF file, three fresh repos, one variable changed:

autocrlfblob bytesls-files --eolwork tree after re-checkoutstderr on add
falseCRLFi/crlf w/crlfCRLFnone
trueLFi/lf w/crlfCRLFnone
inputLFi/lf w/crlfLFwarning: CRLF will be replaced by LF

true and input write the same bytes into the repository and hand back opposite bytes on checkout. The manual is worth quoting because most tutorials paraphrase it badly: setting this variable to true is the same as setting the text attribute to auto on all files and core.eol to crlf, and input means no output conversion is performed.

So autocrlf=true is not "handle line endings for me". It is a rewrite rule with two halves, and neither half covers binary detection failures or CRLF blobs already sitting in history. Both of those come up later.

One detail that explains a lot of team confusion: on this machine git config --system --get core.autocrlf returns true, while git config --global --get core.autocrlf returns nothing and exits 1. The Git for Windows installer writes that value at system level, so "nobody configured anything" and "everybody configured it" are both true. Run those two commands before reading any guide.

text, text=auto, -text and eol

Attributes travel with the repo, which makes them worth more of your time than config. Five spellings, same CRLF file on disk, with core.autocrlf=false:

.gitattributesblobcheckout givesattr shown
*.txt text=autoLFCRLFtext=auto
*.txt text eol=lfLFLFtext eol=lf
*.txt text eol=crlf (disk held LF)LFCRLFtext eol=crlf
*.txt textLFCRLFtext
*.txt -textCRLFCRLF-text

The official wording: with text set, line endings are normalized to LF in the index every time the file is checked in; text=auto adds content detection; -text tells Git not to attempt any end-of-line conversion on checkin or checkout.

Two traps hide in that table.

First, eol=lf does not mean "the work tree is LF". The manual says this setting uses the same line endings in the working directory as in the index when the file is checked out. It compares against the index, not against the letters L and F. I took a blob that had been committed as CRLF and applied text eol=lf: checkout still produced b'line1\r\nline2\r\n', and git status immediately reported M. To get LF on disk you first have to get CRLF out of the blob.

Second, !text cannot undo eol. Writing *.txt text eol=lf and then special.txt !text looks like an exemption, but the attribute still reads text eol=lf, because specifying eol automatically sets text whenever text was left unspecified. Reset both: special.txt -text -eol.

Who wins: directory, order, case

Precedence is documented plainly. $GIT_DIR/info/attributes ranks highest, then the .gitattributes in the same directory as the path, then its parents up to the top of the work tree, then global and system files.

I built three levels to check: root sets *.txt text eol=lf, sub/.gitattributes sets only *.txt eol=crlf without text, sub/deep/.gitattributes sets *.txt -text. Same content in all three files:

i/lf   w/crlf  attr/text eol=lf      a.txt
i/lf   w/crlf  attr/text eol=crlf    sub/b.txt
i/crlf w/crlf  attr/-text            sub/deep/c.txt

Closer wins, and a child file that only declares eol does not lose the text inherited from its parent: attributes override one by one, not line by line. Then I wrote *.txt -text into .git/info/attributes and the root file flipped to -text instantly. That file outranks everything and never leaves your machine, which makes it a fine debugging tool and a poor permanent policy.

There is also a Windows-only variable in play: core.ignoreCase. With this attribute file:

*.txt text eol=lf
*.TXT -text

under core.ignoreCase=true, which is the Windows default, a.txt ends up with -text and its blob keeps CRLF. Set core.ignoreCase to false and rerun: a.txt goes back to text eol=lf and only b.TXT stays -text. This also confirms the ordering rule: when more than one pattern matches, a later line overrides an earlier line, and with case folding on, .txt and .TXT are the same pattern.

Binary files and lone CR

text=auto decides text or binary on its own. A file starting with \x89PNG\r\n and containing a NUL byte survives untouched under * text=auto eol=lf, reported as i/-text. Running git add --renormalize . across twenty text files plus that PNG rewrote exactly the twenty text files and left the image byte for byte identical.

Explicit text removes that protection. The same NUL-containing file under *.dat text came out of the index as b'ABC\x00\ndef\n': the CRLFs were stripped even though ls-files --eol still reported i/-text. This combination can genuinely corrupt images and executables, which is precisely what the manual means by the conversion corrupting data when binary files are accidentally classified as text.

A file with lone CR endings is a separate case. b'a\rb\rc\r' entered the repository unchanged under autocrlf=true and ls-files --eol called it i/-text: Git does not consider it text at all. Change one character and git diff --numstat reports 1 1, the whole file treated as a single line. The --renormalize documentation even keeps the boundary explicit: lone CR characters are untouched, so a CRLF cleans to LF while a CRCRLF sequence is only partially cleaned to CRLF.

That \r\r\n shape is what open() produces when you forget newline='' while writing CSV, which I measured in the eight record boundaries of Python csv. After renormalize it becomes \r\n, with a stray CR left behind as a mixed line ending, and mixed endings are exactly what makes safecrlf refuse a commit.

Old CRLF blobs never heal themselves

A git 2.55 repository diet I wrote earlier hit the same mechanism from the other side: a -text attribute written by git lfs track takes effect immediately. This time I asked the reverse question. When attributes take effect, does content already in history follow?

No. The text=auto description carries a condition: if it is text and the file was not already in Git with CRLF endings, line endings are converted. A file committed as CRLF is exempt by that sentence. Measured: commit a CRLF blob, then commit * text=auto eol=lf, delete the file, check it out again, and CRLF comes back while git status stays perfectly clean.

Explicit text looks worse before it looks better. Status starts reporting M a.txt, the blob is still CRLF, and checkout still returns CRLF. There is one way out:

$ git add --renormalize .
$ git status --short
$ git commit -m "normalize line endings"

The option exists for this exact step: apply the clean process freshly to all tracked files to forcibly add them again to the index, useful after changing core.autocrlf or the text attribute to correct files added with wrong line endings.

The measured cost: three two-line files became 3 files changed, 9 insertions(+), 9 deletions(-); twenty files became 20 files changed, 40 insertions(+), 40 deletions(-); the PNG stayed out of the diff. The command prints nothing at all, stdout and stderr both empty, so the only way to know what it did is git status or git diff --cached --stat. On a large repository this rewrites a lot of blobs, so warn reviewers and CI before pushing it.

When status says modified and diff says nothing

This one deserves its own section. With text set, I replaced the work tree file's CRLF with LF, content otherwise identical:

$ git diff --quiet ; echo $?
0
$ git diff --stat
(empty)
$ git status --porcelain
M a.txt
$ git hash-object a.txt
c0d0fb45c382919737f8d0c20aaf57cf89b74af8
$ git update-index --refresh
a.txt: needs update

diff reports no change and exits 0, status insists there is one, and the hash proves the content is identical. Running git add a.txt clears status while the blob sha stays c0d0fb45…: nothing was staged, the stat data in the index was simply refreshed. When a change looks like "only line endings moved", check git diff before reaching for git commit -a, or you will invent an empty commit.

With -text set, the same edit is real: a.txt | 4 ++--, both lines red. To ignore line-ending noise without touching attributes, use git diff --ignore-cr-at-eol. I took a twenty-line file, edited line 8 and converted the whole file to LF: plain git diff --numstat gave 20 20, the same command with the flag gave 1 1. A pull request that changes one variable and lights up the entire file is usually this, and it belongs to the same family as the eight silent divergences in Windows paths: the strings look the same, the bytes do not.

Troubleshooting: six messages and what to do

One: warning: in the working copy of 'a.txt', CRLF will be replaced by LF the next time Git touches it

Appears when adding a CRLF file under autocrlf=input or text eol=lf. It is a receipt, not an error: the index now holds LF and the next checkout will show you LF. That is what "no output conversion is performed" means in practice.

Two: warning: in the working copy of 'a.txt', LF will be replaced by CRLF the next time Git touches it

The mirror case, under autocrlf=true or eol=crlf, when the disk holds LF. Mixed endings trigger it too: my a\r\nb\nc\r\n sample was normalized to a\nb\nc\n on add.

Three: fatal: LF would be replaced by CRLF in mixed.txt, exit code 128

core.safecrlf=true refusing a mixed-ending file. Git verifies whether the conversion is reversible, and a pure CRLF file passes, which I confirmed with rc 0; mixed endings cannot be reconstructed, so the commit is blocked. safecrlf=warn warns and proceeds, false says nothing. Turning it on team-wide catches corruption early, at the price of forcing you to clean legacy files first.

Four: CONFLICT (content): Merge conflict in a.txt followed by Automatic merge failed; fix conflicts and then commit the result.

My reproduction: base is three CRLF lines, feat edits line 2 and stays CRLF, main converts the file to LF. The merge produces a single conflict block whose two sides are three identical lines each:

<<<<<<< HEAD
one
two
three
=======
one
TWO
three
>>>>>>> feat

Line-by-line comparison shows nothing; you need git diff --word-diff or cat -A to see it. The root cause is not a text conflict but two different definitions of a line, and picking a side does not fix it. Both sides need matching endings first.

Five: a.txt: needs update from git update-index --refresh

Pairs with a status that reports M forever. It means stat and index disagree, not content. Same remedy as above: git add, confirm git diff --cached is empty, move on.

Six: a .bat file that looks fine and fails in cmd

Not a message, a consequence. With autocrlf=input and no attributes, a CRLF .bat file is checked out as b'@echo off\ndir\n'. Add *.bat text eol=crlf in the same repo and checkout returns b'@echo off\r\ndir\r\n'. The batch parser is unreliable with bare LF, so pin those files.

A configuration you can copy

* text=auto eol=lf
*.bat  text eol=crlf
*.cmd  text eol=crlf
*.ps1  text eol=crlf
*.png  binary
*.jpg  binary
*.pdf  binary

binary is a built-in macro, defined as [attr]binary -diff -merge -text, which turns off three attributes at once. * text=auto eol=lf is the single cut that solves most of it: text in as LF, text out as LF, with exceptions only for cmd and PowerShell scripts plus older tooling that validates the bytes.

Three checks are faster than reading documentation:

  • git ls-files --eol | grep -v "i/lf" lists every file whose index copy is not LF, which is where stale CRLF blobs surface.
  • git diff --ignore-cr-at-eol --stat before review, to separate real edits from line-ending noise.
  • git status --porcelain next to git diff --quiet: one says modified, the other says nothing, and you have a phantom change.

Then do the steps in order: commit .gitattributes, run git add --renormalize ., commit the normalization, and finally have everyone re-clone or clear their work tree cache. Skip that last step and a colleague's CRLF work tree will quietly push the old bytes back. A CI assertion on git ls-files --eol is cheaper than a later review, and it is the same principle as using ETag to decide whether content really changed: bytes changed is the only definition of changed.

FAQ

Q: Is core.autocrlf=true enough?

No. It equals * text=auto plus core.eol=crlf and only affects files that have not been committed yet. Every historical CRLF blob stays exactly as it is, because the text=auto rule exempts files already in Git with CRLF endings. Attributes plus a renormalize pass is the complete answer.

Q: Why do my Linux and macOS colleagues never see this?

Because their defaults differ. Outside Windows the default eol is lf and autocrlf is usually false or input, so the conversion has no step to perform. The problem only appears where platforms meet, and that meeting point is usually CI plus the one person on Windows.

Q: Hundreds of CRLF files are already committed. How do I fix them once and for all?

Follow the four steps above, then add a CI check that fails when git ls-files --eol | grep "i/crlf" returns anything. Remember that --renormalize rewrites blobs: old commit hashes stay put, later diffs get longer, and the change deserves its own commit.

Q: What does mixed mean in git ls-files --eol?

The index or work tree copy contains both LF and CRLF. Treat it as more urgent than crlf, since mixed endings block commits under safecrlf=true and produce whole-file conflicts at merge time.
