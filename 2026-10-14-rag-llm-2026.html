微调 vs RAG vs 提示工程：三条路线的决策树

LLM微调RAG

TL;DR：微调、RAG、提示工程不是三选一，而是三个不同层次——提示工程管「怎么说」，RAG 管「不知道什么」，微调管「默认怎么做」。本文给出一张六步决策树、三笔成本账和四个真实报错：提示缓存在 5 分钟 TTL 下只需窗口内 2 次请求就回本（约 24 次/小时）；LoRA 在 8B 模型上按 2026 主流配方（全部 7 个投影、r=16）实测压缩 191.5 倍，而不是论文摘要里那个 10000 倍；OpenAI 自助微调平台已排定 2027-01-06 起对所有人关闭新建任务。所有价格与倍率均引自官方文档，截至发稿（2026-10-14）。本文不含任何联盟推广链接。

这三条路线根本不在同一层

绝大多数「要不要微调」的争论，起点就错了：把三件不同层的事当成同一个按钮在按。

路线它改的是能解决解决不了见效速度
提示工程每次请求带进去的上下文语气、格式、少样本示例、硬性约束模型训练时没见过的知识分钟级
RAG检索出来的外部知识时效性知识、长尾事实、可溯源引用输出风格不稳定、格式漂移天级（要先建索引）
微调模型权重本身稳定格式、领域语气、小模型追大模型新知识注入（反而会放大幻觉）周级

一句话判据：模型「不知道」走 RAG；模型「知道但不照做」走提示工程，提示工程压不住才走微调。

这个判据不是随口的口径。RAG 原始论文（arXiv:2005.11401，NeurIPS 2020，Patrick Lewis 等）把参数化记忆（权重里的知识）和非参数化记忆（Wikipedia 稠密向量索引）明确分成两套东西，并指出「为决策提供出处」和「更新世界知识」这两个开放问题正是参数化模型的短板。换句话说，知识注入从来就不是微调该干的活，那正是 RAG 被发明出来的原因。

六步决策树：按顺序问，别跳

第 1 步：它是缺知识，还是缺行为？

让模型先答一遍，看错误类型。答错事实属于缺知识；事实对但格式、语气、长度不对属于缺行为。缺知识直接进 RAG，不要再调提示词。

第 2 步：知识会不会变？

会变（价格表、库存、内部文档、新闻）只能走 RAG。把会变的东西烧进权重，等于给自己造一笔每次都要重训的债。

第 3 步：你有多少条干净的标注样本？

少于 50 条就用提示工程。OpenAI 官方给的建议是文本 SFT 从 50 条精心构造的样本起步，最低不少于 10 条——那是下限，不是「50 条就够」。

第 4 步：请求量够不够摊薄成本？

这步最容易被跳过，下一节给具体门槛。

第 5 步：你需要可溯源吗？

要回答「这句话出自哪份文档」，必须 RAG。

第 6 步：以上都过了，才考虑微调。

而且要先确认平台还让你做——见后面平台时间表那一节。

成本账一：提示缓存的回本点（用官方倍率反推）

Anthropic 官方文档（docs.anthropic.com 的 Pricing 页）给的提示缓存倍率是确定的：

  • 5 分钟 TTL 的缓存写入 = 基础输入价的 1.25 倍
  • 1 小时 TTL 的缓存写入 = 基础输入价的 2 倍
  • 缓存命中读取 = 基础输入价的 0.1 倍（Claude Opus 5.5 与 Sonnet 5.5 为 0.05 倍）

官方在文档里直接写了结论：caching pays off after one cache read for the 5-minute duration（1.25x write），or after two cache reads for the 1-hour duration（2x write）。我按这些倍率把账算了一遍，结果和官方说法完全对上：

5 分钟 TTL 窗口内请求数全量付费（相对倍数）走缓存（相对倍数）
11.00x1.25x
22.00x1.35x
33.00x1.45x
66.00x1.75x

1 小时 TTL 那一行要 3 次才开始划算（2.20x 对 3.00x），同样和官方的 two cache reads 一致。

换成能直接对照自己业务的门槛：5 分钟窗口内平均不少于 2 次请求，也就是大约 24 次/小时，开缓存就已经省钱了。 低于这个量级，缓存写入那 1.25 倍溢价根本摊不回来。

再补一条时效性信息：Anthropic 2026-10-07 的 API 发布说明把 Claude Sonnet 5.5 的缓存读取价从每百万 token $0.20 降到 $0.10，即从 0.1 倍改成 0.05 倍。同一套代码，一周之内成本结构就变了——这也是为什么这类数字必须标日期。

成本账二：LoRA 的真实压缩比（本机实测）

几乎所有讲 LoRA 的文章都会引用原论文摘要那句「可训练参数减少 10000 倍、GPU 显存要求降低 3 倍」（arXiv:2106.09685，Edward J. Hu 等，2021-06-17 投稿）。这句话是真的，但它对应的是论文自己的实验设置，不是你现在跑的配方。

我实际在本机用 peft 0.21.2 + transformers + torch 2.14.1+cpu 把这个数跑了出来。做法是按 Llama 3 8B 的公开架构建图（hidden 4096、intermediate 14336、32 层、32 头、8 个 KV 头），用 meta device 避免真分配几十 GB 内存，然后让 peft 真的注入 adapter 再数可训练参数：

import torch
from transformers import LlamaConfig, LlamaForCausalLM
from peft import LoraConfig, get_peft_model

DIM, FFN, LAYERS, HEADS, KV, VOCAB = 4096, 14336, 32, 32, 8, 128256

with torch.device("meta"):          # 只建图，不分配真实权重
    cfg = LlamaConfig(hidden_size=DIM, intermediate_size=FFN,
                      num_hidden_layers=LAYERS, num_attention_heads=HEADS,
                      num_key_value_heads=KV, vocab_size=VOCAB, rope_theta=500000)
    model = LlamaForCausalLM(cfg)

total = sum(p.numel() for p in model.parameters())          # 8,030,261,248

for r, mods in [(16, ["q_proj", "k_proj", "v_proj", "o_proj",
                      "gate_proj", "up_proj", "down_proj"]),
                (8,  ["q_proj", "v_proj"])]:
    lcfg = LoraConfig(r=r, lora_alpha=2 * r, lora_dropout=0.0,
                      target_modules=mods, task_type="CAUSAL_LM")
    pm = get_peft_model(model, lcfg)
    tr = sum(p.numel() for p in pm.parameters() if p.requires_grad)
    print(f"r={r} 模块数={len(mods)} 可训练={tr:,} 占比={tr/total*100:.3f}% 压缩={total/tr:.1f}x")
    pm = pm.unload()

实测输出：

r=16 模块数=7  peft 报告可训练 = 41,943,040  占比 0.522%  压缩 191.5x
r=8  模块数=2  peft 报告可训练 = 3,407,872   占比 0.042%  压缩 2356.4x

结论很直接：按 2026 年的主流配方（q/k/v/o 加 gate/up/down 共七个投影全开、r=16、alpha 取 2r），压缩比是 191.5 倍，不是 10000 倍。 那个 10000 倍怎么来的？我按论文设置也算了一遍：GPT-3 175B、只挂 q 和 v、r=4、96 层，可训练参数 18,874,368，压缩 9,272 倍——对上了。

差别在于三件事同时变了：基座从 175B 缩到 8B、rank 从 4 提到 16、挂载模块从 2 个涨到 7 个。

显存账同样要重算。按混合精度 AdamW 的常见账本（bf16 权重 2 字节加 bf16 梯度 2 字节加 fp32 主权重 4 字节加一阶动量 4 字节加二阶动量 4 字节，合计每参数 16 字节）：

  • 全量微调 8B：约 119.7 GiB 训练状态，单卡 80GB 装不下
  • LoRA r=16 全 7 模块：可训练 41,943,040 个参数，优化器状态约 40 MiB

这才是 LoRA 真正的价值：不是「省了 10000 倍参数」这个漂亮数字，而是把训练门槛从多卡集群降到单卡。 另外别忘了原论文那句 unlike adapters 不增加推理延迟——LoRA 权重可以 merge 回基座，推理时不加延迟。

成本账三：微调模型的单价还能叠四层折扣

很多人算微调成本只算训练费。但 OpenAI 官方定价页（developers.openai.com 的 Finetuning 段，o4-mini-2025-04-16）给的是一张多档表，同一个微调模型，输入单价能差 16 倍：

档位输入（每百万 token）输出（每百万 token）
标准$4.00$16.00
标准加开启数据共享$2.00$8.00
Batch$2.00$8.00
Batch 加数据共享$1.00$4.00
Batch 加数据共享再命中缓存$0.25$4.00

输入从 $4.00 到 $0.25 是 16 倍，输出从 $16.00 到 $4.00 是 4 倍。注意最后一行的 $0.25 是缓存输入那一档——微调模型和基座一样吃提示缓存，这两件事不冲突。

训练费那边，官方口径是 $100.00/小时（不是按 token 计）。换算一下：训练 1 小时等于 $100，相当于 25 MTok 的微调模型输入量。低频场景下，这笔钱直接拿来买输入 token 通常更划算，这也是决策树第 4 步要卡请求量的原因。

一个绕不开的现实：OpenAI 正在关停自助微调

做 2026 年的技术选型，这条必须知道。OpenAI 官方 Deprecations 页给出的时间表：

日期发生什么
2026-05-07从未跑过微调的组织，不能再创建微调任务
2026-07-02过去 60 天没对微调模型做过推理的组织，不能再创建新任务
2027-01-06所有客户都不能再创建任何新微调任务

已经训好的模型，推理会一直可用，直到它的基座模型下线为止。也就是说这不是「关掉你已经部署的服务」，而是「冻结你修改它的能力」。

第二条特别阴：门槛绑在你自己的用量上。一个 2025 年重度微调、后来停了三季度的项目，想回来重训，会发现门是被自己的 60 天静默关上的，而不是被 2027 那个日期关上的。如果微调在你的技术栈里，按模型维度监控调用量就是能力保险。

踩坑录：四个真实报错

报错一：Target modules 找不到

原文是 Target modules ['q_proj', 'k_proj'] not found in the base model. Please check the target modules and try again.，出自 peft 源码 tuners/tuners_utils.py，抛的是 NoMatchingPeftModuleError。原因是很多模型的注意力层是融合的——Gemma、Phi、部分 Qwen 变体用的是 qkv_proj 一个融合矩阵，压根没有独立的 q_proj、k_proj、v_proj。照抄 Llama 的配方就会撞上。修法有两个：把 target_modules 写成 all-linear 让 peft 自动匹配所有线性层，或者先遍历 model.named_modules() 把真实模块名打出来再填。

报错二：量化基座上不能 merge

原文是 ValueError: Cannot merge LORA layers when the model is gptq quantized，出自 peft/tuners/lora/model.py。在 GPTQ 量化过的基座上调 LoRA 没问题，但 merge_and_unload() 会失败——量化权重没法再和 adapter 相加。量化加 LoRA 的场景就别指望 merge，直接保留 adapter 结构推理。

报错三：层被复制后不能 merge

原文是 ValueError: Cannot merge LORA layers when base model layers are replicated，同一份源码的相邻分支。用了张量并行把层复制开之后，merge 会失败。多卡部署遇到这条，说明该在 merge 之后再切并行，而不是反过来。

报错四：梯度断在第一层

原文是 RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn。开 gradient checkpointing 省显存时，冻结的基座输出不带梯度，反向传播到第一层就断在这里。PEFT 场景的标准修法是调 model.enable_input_require_grads()，把输入嵌入层的输出重新挂上梯度。这个报错很容易误导——它指向 tensor 0，但根因在 checkpointing 与参数冻结的组合。

再顺手说一个不算报错但经常浪费一天的问题：LoRA 训完，加载 adapter 之后输出和基座一模一样。 八成是没调 model.eval()，或者多 adapter 场景下没 set_adapter()。先用 print_trainable_parameters() 确认 adapter 真的挂上了，再去怀疑训练本身。

什么时候该回头改提示词

我测试下来最省事的一条回归路径：微调后的模型在新数据上掉队时，先别急着重训。把微调学到的那些约束写成几句话放回 system prompt，在同一个基座上跑一遍对比。如果差距在能接受的范围内，就把微调这套退役——尤其在平台窗口只剩几个月的情况下，减少一个会过期的依赖本身就是收益。

FAQ

微调能让模型学会新知识吗？

不建议。RAG 论文把这件事讲得很清楚：参数化模型的短板是访问和精确操纵知识的能力有限，而且提供出处、更新世界知识是它的开放问题。知识会变就走 RAG。

LoRA 的 rank 该设多少？

Hugging Face 官方 PEFT 文档的口径是从 8 或 16 起步，lora_alpha 通常取 rank 的 2 倍；target_modules 覆盖越多适配能力越强，但显存也越高。上面的脚本可以直接改 r 值复跑。

提示缓存和 RAG 冲突吗？

不冲突，反而是叠加关系。把检索到的 chunk 放在 prompt 前缀里，前缀中不变的部分就能命中缓存。

现在还值得投微调吗？

看请求量和任务宽度。窄任务、高音量、格式要求死板，仍然值得——但要选一个不会在半年内关门的平台，开源基座加自托管通常更稳。
