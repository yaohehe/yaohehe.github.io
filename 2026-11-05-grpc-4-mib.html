gRPC 七个默认值实测：4 MiB 上限、三重试与截止时间

gRPC分布式调用实测

这次我实际测试了七组默认值：Windows 11、CPython 3.13.14、grpcio 1.85.1、grpcio-tools 1.85.1、protobuf 7.36.2，用 pip 装进独立目录，不动主环境。服务端由 subprocess 拉起，客户端在主进程 —— 跨进程这一点很关键：同进程里服务端计数器与客户端共享对象，看到的是自己写进去的数；取消与截止又是在传输层判定的，同进程直连会把这一层短路掉。

TL;DR：4 MiB 是单条消息的收、发上限，上行下行各拦一次；metadata 实测在 12,570 字节被拒，而报错文案里写的阈值是 8,192；0.25 秒的截止时间只让客户端放弃，服务端照样把 800 毫秒的活干完；service config 里写 maxAttempts 3，服务端就被调了 3 次；handler 抛出的任何未捕获异常，到客户端都变成 UNKNOWN。

先把实验台搭起来

proto 只留六个方法，每个方法对着一个默认值：Echo 用来量消息体积与单次开销，BigDown 用来撞收发上限，Sleep 与 SleepCheck 用来量截止时间，Fail 用来量重试与错误码，Stream 用来量流式取消，Count 回读服务端计数器。

方法用途对应默认值
Echo5,000 条记录往返消息体积与单次开销
BigDown返回指定字节数4 MiB 接收上限
Sleep 与 SleepCheck睡指定毫秒截止时间与副作用
Fail按 kind 抛异常或 abort错误码与重试
Stream每 10 毫秒吐一条流式取消
Count回读计数器服务端真实发生了什么

服务端启动后把端口打到 stdout，客户端读第一行再建通道，这样两个进程不必抢固定端口：

proc = subprocess.Popen([sys.executable, "server.py"], stdout=subprocess.PIPE, text=True)
port = int(proc.stdout.readline().strip().split("=")[1])
channel = grpc.insecure_channel("127.0.0.1:%d" % port)
grpc.channel_ready_future(channel).result(timeout=10)

顺带一个时间校准：500 次小消息 Echo，单次往返 0.709 毫秒。后面所有「服务端有没有跑完」的判断都建立在这个量级上 —— 0.25 秒的截止时间足够让客户端跑完几百次调用，所以超时后服务端还在干活这件事，不是采样误差。

默认值一：单条消息 4 MiB，上行下行各拦一次

先看体积。5,000 条记录（id、姓名、邮箱、布尔、浮点、三个标签）：protobuf 序列化 322,641 字节，同样内容的 JSON（紧凑分隔符）598,430 字节，JSON 是 protobuf 的 1.855 倍。一次往返 7.33 毫秒，服务端读到的记录数正好 5,000。这个倍数与线格式的选择有关，我在五种线格式的 50,000 条对拍里量过同一批字段，量级一致。

然后撞上限。客户端发一条 4 MiB 加 10 字节的消息，服务端拒收：

StatusCode.RESOURCE_EXHAUSTED
SERVER: Received message larger than max (4194362 vs. 4194304)

反过来，服务端返回 4 MiB 加 1 字节，客户端拒收：

StatusCode.RESOURCE_EXHAUSTED
Stream removed (CLIENT: Received message larger than max (4194315 vs. 4194304))

两条报错的差别只有前缀：SERVER: 表示对端拒收你的请求，CLIENT: 表示本地拒收对端的响应。两侧各自有独立的 grpc.max_receive_message_length，只调一边另一半还会炸。把客户端这个选项抬到 8 MiB 后，同样的 4,194,305 字节响应完整收到，长度校验一致。

实践上有两条：大于 1 MB 的响应改成 server streaming 分片发，不要在单条消息里硬塞；真需要调上限时两边一起调，并且想清楚为什么一条消息要超过 4 MB —— 通常答案是接口设计错了。

默认值二：metadata 两道闸，和它自己写错的阈值

metadata 是 gRPC 里最容易被当成随便塞的地方，实际上它有两级闸门。我二分到字节：

自定义 x-pad 长度头部总长结果
12,01712,568通过
12,01812,570RESOURCE_EXHAUSTED（soft limit，文案写 8192）
15,90016,451RESOURCE_EXHAUSTED（hard limit 16384）

报错原文很直白，还贴心地把每个 header 的字节数列了出来：

received metadata size exceeds soft limit (12570 vs. 8192);  :path:54B :authority:56B
:method:43B :scheme:43B content-type:60B te:42B grpc-accept-encoding:75B user-agent:92B x-pad:12037B

这里有个值得记住的细节：报错自己写的阈值是 8,192，实测触发点是 12,570，差 1.53 倍。老实说我没能从源码层面解释这个差值，所以本文只把它当实测事实记录 —— 但结论不变：自定义 metadata 按 8 KB 以内设计，别去试探上限。七个内置 HTTP/2 头的固定开销实测约 551 字节，这部分你控制不了。

用 metadata 传 JWT 的服务要特别注意这条：token 一膨胀，报错是 RESOURCE_EXHAUSTED，看起来像服务端资源耗尽，实际是你的头部太大。

默认值三：截止时间是客户端的承诺，不是服务端的停止键

这是七条里代价最大的一条。一个 800 毫秒的方法，客户端 timeout=0.2：

  • 客户端 0.2 秒返回 DEADLINE_EXCEEDED，details 就是 Deadline Exceeded；
  • 那一刻服务端计数器 started=1、finished=0；
  • 再等 1.2 秒，finished=1，而且 handler 里 context.is_active() 返回 False 的那次计数也加一。

也就是说服务端在 0.2 秒时就已经知道这个调用被取消了，但 handler 里那句 time.sleep(0.8) 不会被打断，它会睡满、返回、然后返回值被丢弃。官方文档把这件事写得很清楚，两句原文值得背下来：

A gRPC server deals with this situation by automatically cancelling a call (CANCELLED status) once a deadline set by the client has passed.
Please note that the server application is responsible for stopping any activity it has spawned to service the RPC.

再看 status codes 页对 DEADLINE_EXCEEDED 的解释，这一句是关键：

For operations that change the state of the system, this error may be returned even if the operation has completed successfully.

翻译成人话：客户端收到超时，不等于服务端没做完。写库、发消息、扣库存的 handler，必须自己检查 context.is_active()，或者给下游调用带上剩余时间。否则「客户端超时后重试」叠加「服务端照跑完」，就是重复副作用 —— 我上线第一天那两条重复记录就是这么来的。

还有一条前置事实：官方 Deadlines 页开头写着「By default, gRPC does not set a deadline」，不写 timeout 的调用可能一直等下去。

默认值四：重试默认是开着的，一次调用打了三次

给 Fail 方法配一段 service config，maxAttempts: 3、retryableStatusCodes: ["UNAVAILABLE"]，服务端每次进入 Fail 自增一个计数器。客户端只调用一次，服务端计数 加 3。

更值得注意的对照：再加上 grpc.enable_retries=1 跑一遍，还是 3 次。所以这不是「打开开关才生效」的陷阱，而是重试本来就开着，只差一份 policy。官方 Retry 页第一句就写了：

Retries are enabled by default, but there is no default retry policy.

同一页还给了两件容易漏的事：退避时间会加正负 20% 的抖动（initialBackoff 100 毫秒实际会落在 80 到 120 毫秒之间）；以及透明重试 —— RPC 根本没离开客户端时可以不限次重试，到达服务端库但应用还没看到时会重试一次。

危险在叠乘。我在HTTP 层的重试实测里量过 tenacity 3 次乘 urllib3 4 次等于 12 次请求；如果那条链路外面再包一层 gRPC 的 3 次，最坏情况是 36 次落到服务端。规则很简单：只给幂等调用配 retryableStatusCodes，并且全链路只保留一层重试。

日志观测也要改口径：同一次调用在服务端出现三条日志，不是客户端发了三次，是重试了两次。

默认值五：服务端抛异常一律变 UNKNOWN

同一个 Fail 方法，两种写法，客户端看到两个不同的 code。

普通 Python 异常（raise ValueError("record 42 not found")）：

StatusCode.UNKNOWN
Exception calling application: record 42 not found

显式 context.abort(grpc.StatusCode.NOT_FOUND, "record 42 not found")：

StatusCode.NOT_FOUND
record 42 not found

原因在源码里：grpc/_server.py 的 handler 包装层 except Exception 之后统一走 cygrpc.StatusCode.unknown，details 拼成 Exception calling application: {}。同一文件里还有一行容易踩的：abort() 传 StatusCode.OK 会被改成 UNKNOWN 并把 details 清空，只在服务端日志留一行 error。

还有一个反直觉的检查点：调用一个根本不存在的方法，客户端拿到的是 UNIMPLEMENTED，details 是 Method not found!。这不是 404，也不会被当成「记录不存在」。官方 status codes 页明确列了七个只由用户代码产生的码 —— INVALID_ARGUMENT、NOT_FOUND、ALREADY_EXISTS、FAILED_PRECONDITION、ABORTED、OUT_OF_RANGE、DATA_LOSS，所以线上看到 NOT_FOUND，一定是业务代码给的，不是框架。

监控上可以这样做：按 code 分组打点，UNKNOWN 的占比就是 handler 里没处理的异常的比例；这个数字一涨，说明有异常在裸奔。

默认值六：并发上限在服务端线程池，不在通道

服务端 ThreadPoolExecutor(max_workers=64)，被测方法睡 50 毫秒，客户端单通道打三组并发：

并发数总耗时折算轮次
640.084 秒1.68
1280.127 秒2.55
2560.227 秒4.54

折算轮次等于总耗时除以 50 毫秒。64 并发接近 1 轮（真并行），128 是 2.55 轮、256 是 4.54 轮 —— 正好是「超过 64 的部分排队」的形状。天花板是服务端的池大小，不是客户端的通道数。

再验证通道这一侧：200 个 50 毫秒调用，单通道并发 0.215 秒，200 个独立通道 0.221 秒。通道很便宜，多开没有收益，HTTP/2 的多路复用本来就在一条连接上跑并发流。

实践顺序是反的：多数人先调客户端并发，其实应该先看服务端池。Python 里 IO 型 handler 把池开大有效；CPU 型 handler 开大只会被 GIL 吃回去 —— 我在四形态并发对照里量到，16 线程跑纯 Python 循环比串行还慢 21.7%。

默认值七：流式取消立刻生效，但只对还活着的流

服务端 Stream 每 10 毫秒吐一条，计划 60 条。客户端收 3 条后 call.cancel()，服务端 sent 计数停在 3，1 秒后再读还是 3，没有继续吐。

原因是 handler 里在每次 yield 前检查了 context.is_active()。这条检查是可以省掉的，省掉的代价是：生成器还会把后面 57 次循环跑完，只是 yield 出去的东西没人收。如果那个循环里在做数据库分页查询，取消就等于白烧 57 次查询。

所以流式 handler 的写法固定下来：把 is_active() 检查放进循环第一行，而不是只在函数开头判一次。

与 HTTP/1.1 加 JSON 的同一负载对照

同一台机器，200 个 50 毫秒的请求：

形态总耗时
gRPC 单通道并发 2000.215 秒
HTTP/1.1 每次新建连接1.221 秒
HTTP/1.1 单连接串行10.333 秒

这组数字说明的是连接模型，不是框架优劣：gRPC 一条连接上跑 200 个并发流，HTTP/1.1 要么串行排队（10.3 秒），要么开 200 条连接（1.2 秒）。而且这里的 HTTP 服务端用的是 Python 的 ThreadingTCPServer，与 gRPC 的 64 线程池不是同一量级的实现，所以我不把它写成「gRPC 快 5.7 倍」——只能写「单连接跑并发的代价不同」。

Troubleshooting：六个真实报错原文

下面六条全部是本轮在同一台机器上打出来的原文，不是摘抄。

一、RESOURCE_EXHAUSTED：Received message larger than max (4194362 vs. 4194304)

带 SERVER: 前缀时是对端拒收你的请求。修法：拆消息、改流式，或服务端调 grpc.max_receive_message_length。

二、RESOURCE_EXHAUSTED：received metadata size exceeds soft limit (12570 vs. 8192)

自定义 metadata 超过约 12.5 KB（报错里写的 8,192 是另一套口径）。修法：别用 metadata 传大对象，token 改短字段或放请求体。

三、DEADLINE_EXCEEDED：Deadline Exceeded，而服务端 finished 计数还在涨

客户端放弃不等于服务端停机。修法：handler 内检查 context.is_active()，或给下游带 deadline。

四、UNKNOWN：Exception calling application: Protocol message CountReply has no "inactive" field.

这条是我本轮真踩的：改了 proto 加了字段，却忘了重跑 protoc，客户端拿旧桩、服务端返回新字段。修法：proto 与桩代码一起进版本库，改 proto 必须重编译两端。它同时演示了默认值五 —— 一个纯粹的编程错误，到客户端只剩 UNKNOWN。

五、UNIMPLEMENTED：Method not found!

调了不存在的方法名，或服务端没注册这个 servicer。修法：核对 /package.Service/Method 全名。

六、UNAVAILABLE：failed to connect to all addresses; last error: UNAVAILABLE: ipv4:127.0.0.1:1: WSAGetOverlappedResult: Connection refused ... 10061

端口没人监听时 2.01 秒返回，报错里带完整的内层错误。同一个端口加 wait_for_ready=True 后，2.0 秒变成 DEADLINE_EXCEEDED —— 同一件事，两个 code，按 code 做的告警规则会把它们分到两个桶里，这一点在配监控时要想清楚。

本文的边界

只测 Python 实现（grpcio 1.85.1）。Go 与 Java 的 deadline 传播默认开启，C++ 需要显式开启，这一点官方 Deadlines 页写得很清楚，跨语言不能照搬本篇的数字。

没有 TLS、没有负载均衡、没有压缩、没有跨机器 —— 全部在回环上跑，RTT 在 0.05 毫秒量级，公网上的截止时间与重试行为必然不同。

keepalive 那组我没测出结论：客户端把 keepalive_time_ms 设成 1,000，服务端用默认的最小心跳间隔（300,000 毫秒），45 秒内没有复现 GOAWAY 或 ENHANCE_YOUR_CALM。没复现就不写，只在这里留个记号。

单机 16 逻辑核，服务端池 64 个 worker，这些数字换了机器都要重测。

七条可以直接抄走的规则

  • 单条消息按 4 MiB 设计上限，两个方向的选项要一起调。
  • 自定义 metadata 控制在 8 KB 以内，不要拿它传 token 之外的大对象。
  • 每个调用都写 timeout，handler 里主动检查 context.is_active()。
  • 只给幂等方法配 retryableStatusCodes，全链路只留一层重试。
  • handler 里用 context.abort(code, details)，不要靠抛异常传错误语义。
  • 并发先调服务端线程池，再谈客户端通道数。
  • 流式 handler 把 is_active() 检查放进循环第一行。

本文不含任何联盟推广链接，全部数字来自本机实测；proto 与脚本都在同一台机器上可重跑。
