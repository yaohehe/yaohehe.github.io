Python re 正则：8 个不报错的匹配错误

Python正则表达式排错复盘

给这套博客写自检脚本时，我把「加粗格式错误」的判据写成 [ \t]\*\*。跑一遍，75 行里报出 44 处违例。换成 \*\*(.+?)\*\* 再判捕获组首尾有没有空格，违例变成 0。

同一条规则，两次结果差 44 处。文本一个字没改，变的是正则描述的「字符面」和真实文本对不对得上。

这类事故后来又来了三次。内链检查写成 class="internal-link"[^>]*href=，命中 0 条 —— 因为渲染出来的属性顺序是 href 在前、class 在后。抓 GitHub Trending 时用 取链接，站方把 data-hydro-click 挪到前面之后，上千个页面一条都取不到。给关键词自动注入写 \bPython\b，中文段落里一次都不命中，而英文段落全部命中。

TL;DR：一条正则的命中数由四层决定 —— 字符面（\d 到底认哪些字符）、边界（$ 与 \b 在哪个位置成立）、转义层（pattern 与替换串各解析一次）、引擎预算（回溯次数 + 512 槽编译缓存）。本文 8 个坑全部在本机复现，最后给四段真实报错原文。本文不含任何联盟推广链接。

先分清四层，再谈「为什么不命中」

把这四层分开看，绝大多数「正则玄学」都能落到具体某一行文档上：

层决定什么典型症状
字符面\d \w \s 认哪些字符校验器放过不该放过的输入
边界^ $ \b \A \Z 在哪个位置成立完全相同的词，位置一换就不命中
转义pattern 与替换串各解析一次Windows 路径写进替换串直接炸
引擎回溯预算、编译缓存容量不报错，只是从 3 毫秒变成 1185 毫秒

下面按层拆，每条都给可复制的复现片段。所有数字来自本机 CPython 3.13.14 + Windows 11，只用标准库 re，零安装。

第一层：$ 不是「字符串结尾」

Python 官方文档对 $ 的定义是：「Matches the end of the string or just before the newline at the end of the string」，并且在 MULTILINE 模式下还会在每个换行前匹配。同一段文档里还留了一句很好用的例子：在 'foo\n' 里搜一个 $，会找到两个空匹配。

本机复现：

import re
print(re.findall(r'$', 'foo\n'))      # ['', '']  两个
print(re.findall(r'^', 'foo\n'))      # ['']     一个
print(bool(re.match(r'foo$', 'foo\n')))        # True
print(bool(re.fullmatch(r'foo$', 'foo\n')))    # False
print(bool(re.fullmatch(r'foo\Z', 'foo\n')))   # False

第三行和第四行是同一个 pattern，re.match 说匹配、re.fullmatch 说不匹配。原因不复杂：$ 允许停在末尾换行之前，re.match 只要前缀对上就算赢；re.fullmatch 要求整个字符串被消费掉，剩下那个 \n 没人消费，于是失败。

这个差别在「校验一行是不是纯数字」时会直接翻车：

print(bool(re.search(r'^\d+$', '42\n')))       # True   多一个换行也算通过
print(bool(re.search(r'^\d+$', '42\r\n')))     # False  CRLF 反而失败
print(bool(re.search(r'^\d+\r?$', '42\r\n')))  # True

同一台 Windows 机器上，用文本模式 open(p, 'r') 读，CRLF 会被翻译成 LF，第二种写法的隐患藏得住；一旦用 open(p, 'r', newline='') 按原样读（做行尾审计时必须这么读），\r 就留在字符串里，^\d+$ 立刻失效。

要判断「真的到结尾了」，用 \Z：

print(bool(re.fullmatch(r'\d+\Z', '42')))     # True
print(bool(re.fullmatch(r'\d+\Z', '42\n')))   # False

版本提醒：Python 3.14 新增了 \z，官方文档写 \Z 与 \z 现在同义、保留 \Z 只为兼容老代码。3.13 及以前只有 \Z。写工具函数时用 \Z 更稳。

第二层：\b 在中文里几乎不成立

\b 的官方定义是「the boundary between a \w and a \W character」，而 \w 在 str 模式下是「Unicode alphanumerics or the underscore」—— 汉字属于 alphanumerics。于是「汉字」和「英文字母」之间没有边界。

本机复现，五个样本同一 pattern：

文本\bprint 命中(? 命中
'print(x)'11
'print测试'11
'这是 print 测试'11
'用print输出'01
'my_print'01

注意第二行和第四行：print测试 能命中，用print输出 不能。区别只在 print 前面那个字符是汉字还是句首。写关键词高亮、敏感词替换、自动内链时，这就是「同一篇文章里一半命中一半不命中」的根因。

修法是别用 \b 表达「英文单词边界」，直接用断言：

text = '调用API接口'
print(re.sub(r'\bAPI\b', 'X', text))                       # 调用API接口，没替换
print(re.sub(r'(?

逆向也成立：只想在中文之间匹配，就不能指望 \w，得写 [\u4e00-\u9fff] 这类显式区间。

附带一个自己挖的坑：我第一次写本文的探针脚本时，在 f-string 里写了 r"\\bprint"，那实际是「反斜杠 + bprint」，五个样本全部 0 命中。我一度以为 \b 在 CJK 里彻底失效，回头一看是探针自己的双重转义。报 0 之前先怀疑探针，这条在正则调试里出现的频率比想象中高。

第三层：\d 认的是 Unicode 的 Nd，不是 0-9

文档写得很清楚：str 模式下 \d 匹配「any Unicode decimal digit (that is, any character in Unicode character category [Nd])」，并且明说「This includes [0-9], and also many other digit characters」。

本机实测：

输入\d{4}[0-9]{4}int()
'4242'TrueTrue4242
'٤٢٤٢' 阿拉伯-印度数字TrueFalse4242
'４２４２' 全角TrueFalse4242

第四列才是麻烦的地方：int() 也认这些字符。一个 re.fullmatch(r'\d{4}', s) 的校验器会把 '٤٢٤٢' 放过去，随后 int(s) 得到 4242 —— 校验和转换都「成功」，落库的却是一串和用户输入看起来完全不同的数字。短信验证码、订单尾号、四位口令，全都吃这一口。

float() 同理：

print(float('１.５'))   # 1.5
print(float('١.٥'))    # 1.5

要严格 ASCII 数字，两种写法任选一种并写进代码规范：

import re
print(bool(re.fullmatch(r'[0-9]{4}', '٤٢٤٢')))            # False
print(bool(re.fullmatch(r'\d{4}', '٤٢٤٢', re.ASCII)))     # False

re.ASCII 的更隐蔽影响是它同时让 \w \b \s 退回 ASCII 语义 —— 打开之前先确认 \b 的其它用法没有依赖 Unicode。

第四层：替换串会被再解析一次

这是最容易在生产里炸的一条：re.sub 的替换值不是普通字符串，它和 pattern 一样要过一遍转义解析。文档在 Standard escapes 一节写：「Unknown escapes of ASCII letters are reserved for future use and treated as errors.」

于是把 Windows 路径当替换值时：

import re
print(re.sub('a', r'C:\new', 'a'))   # 'C:' + 换行 + 'ew'，长度 5，不是 6
print(re.sub('a', r'C:\dir', 'a'))   # re.PatternError: bad escape \d at position 2

第一行不报错但结果错了：\n 被当成换行。第二行报错。最容易误判的是「那我换个写法构造这个字符串」—— 不行，'C:' + chr(92) + 'new' 得到的还是同一个字符串，re.sub 照样解析，长度还是 5。

只有两条路能拿到字面反斜杠：

print(re.sub('a', r'C:\\new', 'a'))            # C:\new   长度 6，双反斜杠
print(re.sub('a', lambda m: r'C:\new', 'a'))   # C:\new   长度 6，callable

批量改写文件路径、把匹配到的占位符替换成含反斜杠的模板时，一律用 callable 版本 —— 它跳过替换串解析，也不会因为目标串里恰好出现 \1 而被当成组引用。这一条我在改生成脚本的路径替换时踩过，报错位置指向 position 2，看起来像 pattern 的问题，其实是替换串。

html = '

print(re.findall(r'

print(re.findall(r'

补充一个容易混的点：re.S（DOTALL）只影响 .，不影响 ^ $；想让 ^ $ 逐行生效是 re.M。两个 flag 一起开的时候，^.*$ 的行为会同时被两边改变，这是很多「本地通过、上线全乱」的来源。


第六层：用户输入直接进 pattern


把搜索框内容当 pattern 用，是最常见的一类静默错误：


pattern文本直接 re.searchre.escape 后
'1.5''1x5'TrueFalse
'a+b''aab'TrueFalse
'(2026)''2026'TrueFalse


第一行意味着「搜 1.5 会搜出 1x5」。第二行 a+b 会匹配 aab。第三行看起来是布尔组合，实际是捕获组。


修法只有一句：凡是来自用户、文件名、配置的字符串进 pattern，一律 re.escape()。注意 re.escape 在 3.7 改过行为，文档写「Only characters that can have special meaning in a regular expression are escaped」—— 空格现在也会被转义，这仍然是合法 pattern，但拼进 URL 或日志时会看着有点怪。


第七层：回溯，24 个字符把一次匹配拖到 1185 毫秒


这条不报错，只是慢。pattern (a+)+$ 在 24 个 a 加一个 b 上，需要枚举所有切分方式：


n(a+)+$ 回溯型(?>a+)+$ 原子组(a++)+$ 占有量词
1816.295 ms0.004 ms0.003 ms
2067.789 ms0.002 ms0.001 ms
22267.270 ms0.002 ms0.001 ms
241185.359 ms0.002 ms0.001 ms


每加两个字符耗时乘四倍左右，这是标准的灾难性回溯曲线。(\w+\s?)*$ 更狠，24 个字符 2486.720 ms。四行的匹配结果完全一致（都是 False），差别只在花了多久。


原子组 (?>...) 与占有量词 *+ ++ ?+ 是 Python 3.11 新增的，官方 What's New 3.11 写：「Atomic grouping ((?>...)) and possessive quantifiers (*+, ++, ?+, {m,n}+) are now supported in regular expressions」。re 文档解释机制的原话是「once exited, the expression, known as an atomic group, has thrown away all stack points within itself」—— 栈点被丢弃，回溯就没了入口。


实际防守顺序：


  • 先给输入长度上限，正则不是用来处理 10 MB 文本的
  • 嵌套量词 (...+)+ 视为高危写法，改成原子组或分步匹配
  • 校验类 pattern 用 fullmatch 加显式字符类，别用 .* 兜
  • 上线前用最坏输入跑一次计时，别只用正常样本


第八层：512 个槽位的编译缓存断崖


re 有一个进程级编译缓存，源码常量 _MAXCACHE = 512（Lib/re/_constants.py，文档没写这个数）。re.match(pattern, ...) 这种直接调函数的写法，每次都要先查缓存；超过 512 个不同 pattern 之后开始互相挤占，命中率断崖下跌。


本机四轮取中位，同一批匹配分别用「直接调 re.match」与「预编译后调用」：


pattern 数re.match预编译比值
1000.17 ms0.06 ms2.87x
5123.23 ms0.36 ms9.07x
60050.88 ms0.37 ms139.27x
1200103.11 ms0.80 ms128.49x


512 到 600 之间那道坎是断崖：只多出 88 个 pattern，单轮耗时从 3.23 ms 跳到 50.88 ms，涨了 1475%，因为从这一批开始每轮都要重新编译。预编译版本在 600 上仍然是 0.37 ms。


还有一个容易忽略的事实：这个缓存是进程级共享的，不是你的模块独占。re.purge() 之后 import logging，缓存立刻多出 8 条 —— 标准库也在往里塞。所以「我这里只有 20 个 pattern，不可能超过 512」这个推理不成立。


import re
re.purge()
print(len(re._cache))     # 0
import logging
print(len(re._cache))     # 8


结论很简单：循环或热路径里出现的 pattern，一律 re.compile 一次、复用对象。判断标准不是「我 pattern 少」，而是「这段代码每秒钟跑多少次」。


报错实录：四段真实异常


下面四条都能在 3.13 上直接复现，报错原文照抄。


报错一：替换 Windows 路径时 bad escape


re.PatternError: bad escape \d at position 2


复现：re.sub('a', r'C:\dir', 'a')。原因见第四层 —— 替换串要过一遍转义解析，\d 是未知 ASCII 转义。修复用 callable：re.sub('a', lambda m: r'C:\dir', 'a')。


报错二：内联 flag 写在了中间


re.PatternError: global flags not at the start of the expression at position 1


复现：re.compile('a(?i)b')。Python 3.11 起内联全局 flag 只能放在表达式开头，What's New 3.11 的原话是「global inline flags (e.g. (?i)) can now only be used at the start of regular expressions」，并注明从 3.6 起写在别处就已是弃用状态。修复：把 (?i) 提到最前，或改用 re.I；只有局部需要忽略大小写时用作用域组 (?i:...)。


报错三：在 None 上调 .group()


AttributeError: 'NoneType' object has no attribute 'group'


复现：re.search(r'\d+', 'abc').group()。search 找不到就返回 None，这是文档写明的行为：「It is never an error if a string contains no match for a pattern」—— 不匹配本身不算错误，所以不会抛 PatternError。修复：先判空再取组，或写成 m.group(0) if m else ''。日志解析脚本里这个异常最容易把整批任务打断，因为每一行「格式不同但合法」的日志都会触发它。


报错四：组号越界


re.PatternError: invalid group reference 2 at position 1


复现：re.sub(r'(a)', r'\2', 'a')。pattern 里只有一个组。修复：改成 \g<1>，并养成按名字引用的习惯 —— (?P...) 配 \g 在 pattern 改动后不会连带崩。


第五类不算异常：1185 毫秒


第七层那个 24 字符样本没有抛任何异常，退出码是 0，日志里只有一条耗时。这类问题只能靠计时暴露，所以要给关键 pattern 加一条耗时断言，别等用户投诉接口变慢。


上线前照着走一遍


  • 第 1 问：pattern 里的 \d \w \s 是不是真的想要 Unicode 面？不确定就加 re.ASCII
  • 第 2 问：\b 用在中文文本上了吗？是就换成 (? 与 (?![A-Za-z])
  • 第 3 问：$ 后面还会不会有换行？要绝对结尾用 \Z，要完整消费用 fullmatch
  • 第 4 问：替换串里有反斜杠吗？有就用 callable
  • 第 5 问：要跨行匹配吗？要就 re.S，并确认 ^ $ 的语义没有被顺手改掉
  • 第 6 问：pattern 里有用户输入吗？有就 re.escape
  • 第 7 问：有嵌套量词 (...+)+ 吗？有就换原子组，并给输入长度设上限
  • 第 8 问：这个 pattern 在热路径上吗？在就预编译，别依赖 512 槽缓存


这八问和另一类「默认值变了但没人告诉你」的问题同源。我在 pandas 3.x 写时复制那篇里列过五个赋值静默失效，在 subprocess 静默失效那篇里列过七个退出码为 0 的故障，在 asyncio 取消与超时那篇里列过六处取消根本没送到的情况。共同点是：失败形态不是异常，而是结果不对、流程却走完了。正则这一层尤其隐蔽，因为同一个 pattern 会随输入文本的语言、行尾、长度改变行为。


常见问题


Q： 为什么 re.match 明明能匹配上，我却拿到了 None？


re.match 只从字符串开头匹配，等价于 re.search 加上开头锚定。re.match(r'\d+', 'abc 42') 返回 None，re.search(r'\d+', 'abc 42') 才有结果。要「整个字符串必须完全符合」，用 re.fullmatch，它的语义和上面两个都不一样。


Q： 打开 re.I 之后，[A-Z] 为什么匹配到了看起来不是字母的字符？


re.I 在 str 模式下走 Unicode 大小写折叠，不是简单的 A 对 a 映射。本机实测三个反直觉样本：开尔文符号 K（U+212A）被 [A-Z] 命中，长 s（U+017F）被 [a-z] 命中，带点大写 I（U+0130）也被 [A-Z] 命中。做 ASCII 口径的白名单校验时，加 re.ASCII 把折叠范围收回来。


Q： 我在在线正则测试站上验证通过，为什么到代码里不通过？


在线站多数按 JavaScript 引擎算，Python 的 re 在几处不一样：\Z 在 Python 里是绝对结尾，在 PCRE 系里语义不同（PCRE 另有 \z）；\d 的 Unicode 面各家默认值不一致；原子组与占有量词只有 3.11 之后的 Python 才有。搬运正则时逐条对照目标引擎文档，别只看高亮结果。


八层都覆盖了。最后留一句方法上的话：正则出问题时，先写一个最小复现样本，把「输入、pattern、预期、实际」四件事钉死，再去查文档。上面八条里有五条是靠最小样本推翻了我原本的判断 —— 包括那条一开始以为「\b 在中文里彻底失效」的探针。
