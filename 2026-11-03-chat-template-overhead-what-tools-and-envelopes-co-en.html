Chat Template Overhead: What Tools and Envelopes Cost

tokenchat templateLLM

I rendered the same 40-message operations conversation through four official chat templates and counted the ids. The message text came to 1,842 tokens. What actually entered the context was 3,012. The extra 1,170 tokens were not conversation at all — they were envelopes and a tool list added by the template.

The short version: budgeting from message text alone underestimates the real count by 3.6% to 63.5% on these four models. Two of the four templates do not read the tools argument at all: zero tokens added, zero errors raised. No affiliate links in this article; every number below comes from a run on my own machine.

What I actually measured

The environment was CPython 3.13.14 with transformers 5.22.1 and tokenizers 0.23.3. I pulled the four chat templates from each repository's tokenizer_config.json on 2026-11-03: Llama-3.1 at 348 characters, DeepSeek-V3 at 2,145, Mistral-7B-Instruct-v0.3 at 3,959, and Qwen3-8B at 4,168.

The method is one path, no guessing: hand the messages list to apply_chat_template with tokenize on, and count the ids. Then encode each message content separately and sum. The difference is what the template added. Twenty turns, 40 messages, roughly 35 words per user message and 12 words per reply.

A single Llama-3.1 user message renders as <|begin_of_text|><|start_header_id|>user<|end_header_id|>, two newlines, the text, and <|eot_id|>. Five tokens just to say "the user is talking". Qwen3 uses <|im_start|>user plus a newline, also five. DeepSeek-V3 is the cheapest at one token per user message, because its <｜User｜> marker was trained as a single vocabulary entry.

The Mistral column says "cannot add alone" for a reason I come back to later: that template refuses two consecutive user messages, so you can only add user-and-assistant pairs.

The envelope itself is not frightening — 207 tokens at most across 40 messages. What matters is that it grows linearly. A 200-message session pays roughly 1,000 tokens of envelope, and none of it appears anywhere in the text you are counting.

Tool definitions are not priced by their JSON

The real weight is in the tools. I built ten realistic function schemas. Serialised as single-line JSON, the bare tool list costs 745 tokens under Llama's vocabulary, 756 under Qwen3's, and 888 under Mistral's.

But no template pastes the JSON as-is. They add prose:

One Qwen3 tool costs 175 tokens while its JSON is only 69. The extra 106 come from a system message the template writes itself, starting with # Tools, then You may call one or more functions to assist with the user query., then You are provided with function signatures within XML tags: — and only then the JSON. With ten tools that preamble is added once, so the unit price drops to about 96.

Mistral takes a different route: it wraps the tool list in [AVAILABLE_TOOLS] and places it just before the last user message. One tool costs 113 tokens, ten cost 939, and the marginal cost is around 94.

The part that is easy to miss: on Qwen3, ten tools (963 tokens) are more than half of the entire 40-turn message text (1,842). If you are shipping a twenty-tool agent, extrapolating the measured 96 tokens per tool puts the tool list near 1,900 tokens before anyone says anything. That extrapolation is arithmetic, not a measurement — I flag it as an order of magnitude, not a number to quote.

Two templates swallow the tools entirely

The Llama-3.1 template is 348 characters. It loops over messages, concatenates <|start_header_id|>, the role and <|end_header_id|>, appends the content, and finishes with an assistant header. The variable name tools never appears in it.

So when you pass tools, the template accepts the argument and produces a string that is byte-for-byte identical to the one without tools. I asserted string equality: tools_rendered_identical came back true. Across 40 messages, ten tools produced 1,905 tokens, exactly the same as no tools.

DeepSeek-V3 is trickier. Its 2,145-character template does have tool branches: message['tool_calls'] is rendered into the <｜tool▁call▁begin｜> family of tokens, and the tool role has its own output format. But the template never reads the tools variable. In other words, it can render a history where the model already called a tool, but it cannot tell the model which tools exist.

That failure is the hardest to debug. Nothing raises. Your log shows tools=[...] was passed. The model simply never calls anything, so you blame model capability first, the prompt second, and the template last.

There is exactly one cheap check: render the same messages twice, once with tools and once without, and compare the strings. If they are equal, the tools never entered the prompt.

18,780 versus 939: my own test tripped the equality check

The Mistral footnote deserves its own section, because it was the most expensive lesson of this run.

The Mistral template contains this condition: {%- if tools is not none and (message == user_messages[-1]) %}. In words: inject the tool list only when this message is the last user message. It compares dictionaries, not indices.

My first version of the test was lazy: all 20 user messages had identical content, and all 20 assistant replies were identical too. Since every user dictionary equalled the last one, the condition held for all of them and the tool list was injected 20 times.

That version measured 20,681 tokens against 1,740 of message text — a tool cost of 18,780, or 1,088.6% over. My first instinct was "Mistral resends the tools on every turn." I nearly wrote that down as a finding.

The fix was trivial: append a distinct suffix to each message so the dictionaries differ. Same 40 messages, same ten tools, tool cost fell from 18,780 to 939 — a factor of exactly 20.

Two lessons. The first is about my own test: a control group has to actually differ, otherwise you cannot tell whether you measured the template's behaviour or an amplification caused by duplicate test data. The second is about the template: deciding position by dictionary equality means any client that resends an identical message — a retry, a backfill, a placeholder turn — gets the tool list injected again, at double the cost, with no warning at all.

Add the layers and you get the real count:

Use it in that order: count the text with your own tokenizer, add the envelope unit price times the number of messages, then confirm whether the tool template reads tools at all. The third step is the one people skip, and it is the only one that fails without telling you.

One more detail: an empty system message still costs tokens. On Llama an empty system message adds 5 tokens, on Mistral 3, on Qwen3 5. On DeepSeek it is 0, because that template concatenates system content into the opening rather than emitting a system block.

Troubleshooting: four real errors and three silent traps

Error one: ValueError: Cannot use chat template functions because tokenizer.chat_template is not set and no template argument was passed! I hit this when loading tokenizer.json alone. Fix it by reading chat_template out of tokenizer_config.json and assigning it, or by passing template= directly.

Error two: jinja2.exceptions.UndefinedError: 'dict object' has no attribute 'role'. One message had content but no role. The template reads message['role'] directly, so the render stage fails, well before tokenization is involved.

Error three: ValueError: Cannot apply chat template to an empty conversation. Provide at least one message. An empty list does not even reach rendering. It shows up most often when a retry happens after history was cleared.

Error four: TemplateError: After the optional system message, conversation roles must alternate user/assistant/user/assistant/... This is Mistral's alternation check, and two consecutive user messages fail it. Insert an assistant turn or merge the two user messages.

Then the three traps that do not raise at all:

A role of wizard renders literally as <|start_header_id|>wizard<|end_header_id|> — 11 tokens, and the model sees a role name it was never trained on.

A content of None renders as the string None, also 11 tokens, and the model treats it as something the user said.

A multimodal content list gets repr'd by a text template: [{'type': 'text', 'text': 'hi'}], 24 tokens instead of 11, and the model sees a Python literal with quotes in it.

What the documentation says, and whether it matches

The Hugging Face chat templating docs describe the mechanism plainly: the list of role and content dictionaries "get converted to a token sequence, often with control tokens like <|user|> or <|assistant|> or <|end_of_message|>, which allow the model to see the chat structure." The same page warns that chat templates should already include all necessary special tokens, and that adding more is often incorrect or duplicated.

On generation prompts the wording is: "Not all models require generation prompts, and some models, like Llama, don't have any special tokens before the assistant response. In these cases, add_generation_prompt has no effect." My numbers match exactly — Llama 0, Mistral 0, Qwen3 3, DeepSeek 1.

On tools, the docs say only that "when a model supports tool-use, pass functions to the tools argument of apply_chat_template()." They never say what happens when the model does not. What I measured is: silently dropped, zero tokens, zero errors.

OpenAI's side runs a different rulebook. Its cookbook counting function adds 3 tokens per message plus 3 to prime the reply, and the page itself says to treat the result as "an estimate, not a timeless guarantee." It also notes that "requests that use the optional functions input will consume extra tokens on top of the estimates calculated below." So even there, counting message text alone undercounts.

One more format for scale: the o200k_harmony encoding in tiktoken carries 1,091 special tokens. The same two-turn exchange is 11 tokens as plain text and 22 tokens once wrapped in <|start|>user<|message|>…<|end|>. The envelope doubles it.

Where this stops

I measured tokenizer and template rendering only. I did not measure server-side billing; an API may wrap another layer on top or count a different message format. All four models were used for prefix encoding, not generation quality, so whether tool calling actually works still depends on the model. The four templates are the ones in the open-weights repositories on Hugging Face, and DeepSeek's hosted API uses a different server-side template, not the file I measured.

Both cover how to count the text; this one covers everything around it. Three sentences to take away

Render first, count second. Render twice and assert equality so you know the tools actually entered the prompt. And budget the envelope by message count, never by character count.
