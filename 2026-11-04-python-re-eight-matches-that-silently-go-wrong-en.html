Python re: Eight Matches That Silently Go Wrong

Pythonregextroubleshooting

My blog pipeline has a checker that flags badly formatted bold text. The first version of it used the pattern [ \t]\*\*. On one draft it reported 44 violations across 75 lines. I rewrote it as \*\*(.+?)\*\* plus a check on the captured group, and the count dropped to zero.

Same rule, same draft, 44 violations to none. Nothing in the file changed. What changed was whether the pattern described the text that was actually there.

Three more of these followed. My internal-link checker used class="internal-link"[^>]*href= and found zero links, because the renderer emits href first and class second. My scraper for GitHub Trending used and returned nothing on a thousand pages once the site moved data-hydro-click ahead of href. My keyword-injection step used \bPython\b, which matched every English paragraph and none of the Chinese ones.

TL;DR: the number of matches a pattern returns is decided by four layers. The character surface (\d is not [0-9], \w includes Chinese characters), the boundary rules ($ stops before a trailing newline, \b needs a \w/\W transition), the escaping layer (pattern and replacement are each parsed once), and the engine budget (backtracking plus a 512-slot compile cache). All eight failures below reproduce on a clean machine with the standard library only. No affiliate links in this post.

Layer one: the end anchor is not the end of the string

The documentation defines $ as matching "the end of the string or just before the newline at the end of the string", and notes it also matches before every newline under MULTILINE. The same page gives a deliberately surprising example: searching for a single $ in 'foo\n' finds two empty matches.

import re
print(re.findall(r'$', 'foo\n'))      # ['', '']  two
print(re.findall(r'^', 'foo\n'))      # ['']     one
print(bool(re.match(r'foo$', 'foo\n')))        # True
print(bool(re.fullmatch(r'foo$', 'foo\n')))    # False
print(bool(re.fullmatch(r'foo\Z', 'foo\n')))   # False

Lines three and four use the identical pattern and disagree. $ is allowed to stop before the trailing newline, and re.match only needs a matching prefix. re.fullmatch requires the whole string to be consumed, and the leftover \n never gets consumed, so it fails.

That difference breaks the most ordinary validator in the world, "is this line a number":

print(bool(re.search(r'^\d+$', '42\n')))       # True   the extra newline passes
print(bool(re.search(r'^\d+$', '42\r\n')))     # False  CRLF fails instead
print(bool(re.search(r'^\d+\r?$', '42\r\n')))  # True

On Windows, reading with open(p, 'r') translates CRLF to LF and hides the second case. Read the same file with open(p, 'r', newline=''), which you must do when auditing line endings, and the \r survives, so ^\d+$ fails.

When you mean "the string really ends here", use \Z:

print(bool(re.fullmatch(r'\d+\Z', '42')))     # True
print(bool(re.fullmatch(r'\d+\Z', '42\n')))   # False

Version note: Python 3.14 added \z, and the docs now describe \Z as the same thing, kept for compatibility. Before 3.14 there is only \Z. If you write library code, \Z is the portable choice.

Layer two: boundaries do not exist between Chinese and ASCII

\b is defined as "the boundary between a \w and a \W character", and in str mode \w is "Unicode alphanumerics or the underscore". Chinese characters are alphanumerics. So there is no boundary between a Chinese character and a Latin letter, and \b silently fails to fire in exactly the place you wanted it.

For a few minutes I believed \b was broken for Chinese entirely. It was my own double escaping. Suspect the probe before you suspect the pattern; this happens more often than anyone admits.

Layer three: the digit class is Unicode Nd, not zero to nine

The docs are explicit. In str mode \d matches "any Unicode decimal digit (that is, any character in Unicode character category [Nd])", and they add "This includes [0-9], and also many other digit characters".

Measured:

Input\d{4}[0-9]{4}int()
'4242'TrueTrue4242
'٤٢٤٢' Arabic-IndicTrueFalse4242
'４２４２' fullwidthTrueFalse4242

The last column is the dangerous one. int() accepts those characters too. A validator written as re.fullmatch(r'\d{4}', s) passes '٤٢٤٢', and then int(s) returns 4242, so validation and conversion both succeed while the value you store is not the string the user typed. One-time codes, order suffixes, and four-digit PINs all sit in this hole.

float() behaves the same way:

print(float('１.５'))   # 1.5
print(float('١.٥'))    # 1.5

Pick one of these two and put it in your style guide:

import re
print(bool(re.fullmatch(r'[0-9]{4}', '٤٢٤٢')))            # False
print(bool(re.fullmatch(r'\d{4}', '٤٢٤٢', re.ASCII)))     # False

Remember that re.ASCII also pushes \w, \b and \s back to ASCII semantics, so check for other boundary uses before switching it on.

Layer four: the replacement string is parsed a second time

This one reaches production easily. The replacement argument to re.sub is not a plain string. It goes through its own escape pass, and the docs say so under Standard escapes: "Unknown escapes of ASCII letters are reserved for future use and treated as errors."

Feed it a Windows path and one of two things happens:

import re
print(re.sub('a', r'C:\new', 'a'))   # 'C:' + newline + 'ew', length 5, not 6
print(re.sub('a', r'C:\dir', 'a'))   # re.PatternError: bad escape \d at position 2

The first line returns a wrong value without raising. The second raises. And the obvious workaround does not work: 'C:' + chr(92) + 'new' produces the same string, which is then parsed the same way, and the length is still 5.

Only two forms give you a literal backslash:

print(re.sub('a', r'C:\\new', 'a'))            # C:\new   length 6, doubled backslash
print(re.sub('a', lambda m: r'C:\new', 'a'))   # C:\new   length 6, callable

For bulk path rewriting, or for replacing matches with a template that contains backslashes, always use the callable form. It skips the replacement parser entirely, so it also cannot be tricked into treating a \1 in your data as a group reference. I hit this while rewriting the path handling in my own generator, and the error message pointed at position 2, which reads like a problem in the pattern rather than in the replacement.

Layer five: the dot never crosses a newline

My first version of the

html = '

print(re.findall(r'

print(re.findall(r'

One thing that gets mixed up constantly: re.S (DOTALL) affects only ., and does nothing for ^ and $. Making anchors per-line is re.M. With both flags on, ^.*$ changes behaviour from two directions at once, which is where a lot of "works locally, wrong on the server" comes from.


Layer six: user input becomes a pattern


Search boxes get pasted into re.search all the time:


PatternTextDirect re.searchAfter re.escape
'1.5''1x5'TrueFalse
'a+b''aab'TrueFalse
'(2026)''2026'TrueFalse


The first row means searching for 1.5 finds 1x5. The second means a+b matches aab. The third is not a boolean expression, it is a capture group.


The rule is a single sentence: any string that comes from a user, a filename, or configuration goes through re.escape before it reaches a pattern. Note that re.escape changed in 3.7; the docs now say "Only characters that can have special meaning in a regular expression are escaped". Spaces are escaped too, which is still a valid pattern but looks odd once you paste the result into a URL or a log line.


Layer seven: 24 characters turn one match into 1185 ms


No exception here, just time. The pattern (a+)+$ against 24 a characters followed by a b has to enumerate every way of splitting the run:


n(a+)+$ backtracking(?>a+)+$ atomic(a++)+$ possessive
1816.295 ms0.004 ms0.003 ms
2067.789 ms0.002 ms0.001 ms
22267.270 ms0.002 ms0.001 ms
241185.359 ms0.002 ms0.001 ms


Two more characters multiply the time by roughly four. That is the textbook catastrophic backtracking curve. (\w+\s?)*$ is worse: 2486.720 ms at 24 characters. All of these return the same answer, False, and the only difference is how long it took to say so.


Atomic groups and possessive quantifiers arrived in Python 3.11. What's New 3.11 says: "Atomic grouping ((?>...)) and possessive quantifiers (*+, ++, ?+, {m,n}+) are now supported in regular expressions". The mechanism is in the re docs: once an atomic group is exited, it "has thrown away all stack points within itself", so there is nothing left to backtrack into.


A workable order of defence:


  • Cap input length before the pattern runs; regex is not a tool for 10 MB strings
  • Treat nested quantifiers like (...+)+ as a red flag, rewrite with atomic groups or split the match into steps
  • Use fullmatch with explicit character classes for validation instead of a trailing .*
  • Time the worst-case input before shipping, not just the happy path


Layer eight: the 512-slot cache cliff


re keeps a process-wide compile cache. The constant is _MAXCACHE = 512 in Lib/re/_constants.py; it is not described in the docs. Calling re.match(pattern, ...) with a string looks the pattern up every time, and past 512 distinct patterns the entries start evicting each other.


Median of four rounds, same work, two ways of calling it:


Patternsre.matchPrecompiledRatio
1000.17 ms0.06 ms2.87x
5123.23 ms0.36 ms9.07x
60050.88 ms0.37 ms139.27x
1200103.11 ms0.80 ms128.49x


The cliff sits between 512 and 600. Adding 88 patterns takes one round from 3.23 ms to 50.88 ms, a 1475% jump, because from that point every round recompiles. The precompiled version stays at 0.37 ms at 600.


A second detail makes the arithmetic worse: the cache is shared by the whole process, not owned by your module. Purge it, then import logging, and eight entries appear immediately.


import re
re.purge()
print(len(re._cache))     # 0
import logging
print(len(re._cache))     # 8


So "I only have 20 patterns, I cannot reach 512" is not a valid argument. The rule is simpler: any pattern on a hot path gets compiled once and reused, and the question is not how many patterns you have but how many times per second that code runs.


Troubleshooting: four errors I reproduced


All four raise on 3.13 immediately. Messages below are copied from the tracebacks.


Error one: bad escape when substituting a Windows path


re.PatternError: bad escape \d at position 2


Reproduce with re.sub('a', r'C:\dir', 'a'). The replacement is parsed, \d is not a known ASCII escape, and the position refers to the replacement string, not the pattern. Fix: re.sub('a', lambda m: r'C:\dir', 'a').


Error two: an inline flag in the middle


re.PatternError: global flags not at the start of the expression at position 1


Reproduce with re.compile('a(?i)b'). Since 3.11 a global inline flag must sit at the start; What's New 3.11 says "global inline flags (e.g. (?i)) can now only be used at the start of regular expressions" and notes that anywhere else has been deprecated since 3.6. Fix: move it to the front, pass re.I, or scope it as (?i:...) if only part of the pattern needs it.


Error three: calling group() on None


AttributeError: 'NoneType' object has no attribute 'group'


Reproduce with re.search(r'\d+', 'abc').group(). A failed search returns None, which is documented behaviour: "It is never an error if a string contains no match for a pattern". So no PatternError is raised, and the failure surfaces one line later. Fix: check first, or write m.group(0) if m else ''. In log-parsing code this is the exception that kills a whole batch, because every line that is different but valid triggers it.


Error four: group reference out of range


re.PatternError: invalid group reference 2 at position 1


Reproduce with re.sub(r'(a)', r'\2', 'a'). The pattern has one group. Fix: use \g<1>, and prefer named groups, (?P...) with \g, so the reference survives the next edit of the pattern.


The fifth case is not an exception


The 24-character sample from layer seven raises nothing, exits 0, and leaves one timing line in the log. That class of problem only shows up if you measure, which is why critical patterns deserve a duration assertion instead of a user complaint.


Eight questions before you ship


  • Question 1: Do \d, \w, \s really mean the Unicode surface here? If unsure, add re.ASCII
  • Question 2: Is \b being applied to Chinese or Japanese text? Replace it with (? and (?![A-Za-z])
  • Question 3: Can a newline follow the position where $ matches? Use \Z for an absolute end, fullmatch for full consumption
  • Question 4: Does the replacement contain backslashes? Use a callable
  • Question 5: Does the match need to cross lines? Use re.S, and confirm you did not also change what ^ and $ mean
  • Question 6: Does the pattern contain user input? Run it through re.escape
  • Question 7: Is there a nested quantifier like (...+)+? Switch to an atomic group and cap the input length
  • Question 8: Is the pattern on a hot path? Precompile it rather than trusting the 512-slot cache

FAQ


Q: Why does re.match return None when the text clearly contains my pattern?


re.match only looks at the start of the string, which is re.search with an implicit leading anchor. re.match(r'\d+', 'abc 42') returns None, while re.search(r'\d+', 'abc 42') finds 42. If you want the whole string to conform, use re.fullmatch, whose semantics differ from both.


Q: Why does [A-Z] match characters that are not letters once I add re.I?


In str mode, re.I uses Unicode case folding rather than a simple A-to-a mapping. Three measured examples: the Kelvin sign K (U+212A) matches [A-Z], the long s character U+017F matches [a-z], and capital I with dot (U+0130) matches [A-Z]. For an ASCII-only whitelist, add re.ASCII to bring the folding range back.


Q: It passed on an online regex tester. Why does it fail in my code?


Most online testers run a JavaScript engine. Python's re differs in several places: \Z means absolute end of string in Python, while the PCRE family defines it differently and uses \z for the absolute end; the Unicode surface of \d has different defaults per engine; atomic groups and possessive quantifiers only exist in Python 3.11 and later. Port a pattern by checking each construct against the target engine's docs, not by looking at the highlight.

One methodological note to close: when a pattern misbehaves, write the smallest possible reproduction and pin down four things, the input, the pattern, the expected result and the actual result, before reading any documentation.
