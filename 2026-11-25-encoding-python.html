不写 encoding 的时候，Python 在六个地方各查一次默认值

python-encodinglocaleutf-8

有个 CSV 文件在一台 Windows 机器上跑了三年没出过事。它九成内容是英文列名和时间戳，最后两列写着中文状态。把文件按原始字节打出来，长这样：

612c620ab6a9b5a52c310a

a,b\n 后面那 4 个字节 b6a9b5a5 是「订单」，用 GBK 编的；同样的两个字用 UTF-8 是 6 个字节 e8aea2e58d95。代码里没有任何一行提到编码，长度却不一样 —— 这就是本文要拆的那一层：不写 encoding 的时候，解释器到底去哪张表上查答案，以及这张表在 Python 3.15 里已经换掉了。

上一篇拆的是坏字节交给哪个错误处理器（strict / ignore / replace 那一组），这一篇拆的是更前面一步：字节还没读进来，先决定用哪个编解码器。

同一个字符串，两条路写出两种字节

先看一组对照。三个动作写的是同一段文字：

写法落盘字节长度
'订单'.encode()e8aea2e58d956 B
open(p, 'w').write('订单')b6a9b5a54 B
open(p, 'wb').write('订单'.encode())e8aea2e58d956 B

str.encode() 的默认编码是 UTF-8，和系统语言无关；open() 的默认编码是 locale 编码。同一个进程里，两个「默认」指向两个不同的编码，而且没有任何警告。

后果是同一个文件、两条读法、两个结果：

open(p).read()                  # '订单已发货'
open(p, 'rb').read().decode()   # UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb6 in position 0: invalid start byte

这不是文件坏了，是两条路查了两张表。凡是「某个库读得出来、open() 读不出来」的怪事，先按这个方向查，比猜文件损坏快得多。

一个进程里，六处默认值各报一个答案

测法：CPython 3.13.14、Windows 11 10.0.26300、简体中文系统、未设 PYTHONUTF8 与 PYTHONIOENCODING。

调用返回值它管哪一段
sys.getdefaultencoding()utf-8只给 str.encode() 与 bytes.decode()
locale.getencoding()cp936系统 ANSI 代码页，不看 UTF-8 模式
locale.getpreferredencoding()cp936会看 UTF-8 模式，开了就变 utf-8
open(p) 的 .encodingcp936文本文件读写
sys.stdout.encodinggbk标准输出（重定向到文件和管道时也是它）
sys.getfilesystemencoding()utf-8文件名、命令行参数、环境变量

六行里出现三个不同的编码名：utf-8、cp936、gbk。而 cp936 和 gbk 是同一个东西 —— codecs.lookup('cp936').name 返回 gbk，cp936、gbk、ms936 三个别名全部规范化到 gbk。

所以同一个故障会在三个位置显示三种名字：报错里写 'gbk' codec can't encode，句柄上写 encoding='cp936'，locale.getdefaultlocale() 返回 ('zh_CN', 'cp936')。排查时不要因为这些字符串不同，就当成两件事去查。

还有一处容易被读错：locale.getdefaultlocale() 在 UTF-8 模式下照样返回 ('zh_CN', 'cp936')（实测）。它是从环境变量和系统代码页推的，不跟 UTF-8 模式走 —— 拿它当判据，会永远得到旧值。

为什么中文文件名从不出事，中文内容总出事

因为文件名根本不走这张表。Windows 上文件系统编码从 PEP 529 起固定为 UTF-8，错误处理器是 surrogatepass，两种模式下都没有变过（实测 getfilesystemencoding 恒为 utf-8；建一个中文目录再 listdir 回来，名字原样命中）。

于是出现一个很能骗人的组合：你的目录叫「订单导出」，文件名带日期，os.listdir() 一切正常，Path 拼接也正常，只有文件内容里的中文是 GBK。测试时顺手用了中文路径，看起来「中文没问题」，实际上一行都没覆盖到真正出问题的那层。

顺带说清边界：路径层和编码层是两套东西，路径那条线的坑（反斜杠、大小写、短名）在 Windows 路径的八个语义分歧 里拆过；文件系统层的错误处理（os.fsencode 在 Windows 上给的是 surrogatepass 而不是 surrogateescape）在 编码错误处理的五种策略 里说过。本文只处理文本句柄这一层。

三个开关各管一段，优先级还不一样

把 -X utf8、PYTHONUTF8、PYTHONIOENCODING 摆在一起跑，六组结果如下（全部实测，同一台机器）：

设置open() 默认stdout.encodinglocale.getencoding()encoding="locale"
什么都不设cp936gbkcp936cp936
-X utf8 或 PYTHONUTF8=1utf-8utf-8cp936cp936
只设 PYTHONIOENCODING=utf-8cp936utf-8cp936cp936
PYTHONUTF8=1 加 -X utf8=0cp936gbkcp936cp936
PYTHONUTF8=0 加 -X utf8utf-8utf-8cp936cp936
PYTHONUTF8=1 加 PYTHONIOENCODING=gbkutf-8gbkcp936cp936

三条能直接用的结论：

  • 命令行 -X 压过环境变量。第 4 行和第 5 行是两个方向的对照，谁写在命令行谁赢，所以「我只在系统里设了 PYTHONUTF8=1」这句话不足以说明程序的行为。
  • PYTHONIOENCODING 只管标准输入输出，一行都没碰 open()。第 3 行最典型：stdout 已经是 utf-8，写文件还是 cp936。最后一行更进一步，它在 UTF-8 模式下也能把 stdout 拽回 gbk。
  • locale.getencoding() 和 encoding="locale" 在 UTF-8 模式下都不动，两者恒为 cp936。想知道「这台机器真正的系统编码」，问 getencoding()；想复刻旧行为，写 encoding="locale"。

补一条文档里的差异，不是我测的：UTF-8 模式下 sys.stdin 和 sys.stdout 用 surrogateescape 错误处理器，而 sys.stderr 仍然是 backslashreplace。所以同一段坏字节进 stderr 和进 stdout，落盘的样子不一样。

3.15 已经把默认值换掉了

PEP 686 的状态是 Final，Python-Version 写的是 3.15，原文一句是「Python will enable UTF-8 mode by default from Python 3.15」，同时保留退出通道「Users can still disable UTF-8 mode by setting PYTHONUTF8=0 or -X utf8=0」。python.org 的下载页上，3.15.0 于 2026-10-09 发布，截至发稿最新为 3.15.2（2026-10-25）。

先交代取证边界：本机是 3.13.14，没有装 3.15，所以下面这组数据是在 3.13 上加 PYTHONUTF8=1 跑出来的 —— 复现的是「UTF-8 模式开启时那段代码路径」，不是在新版本上的实测。结论只对这一层负责。

动作默认模式（3.14 及更早）UTF-8 模式（3.15 默认）
写「订单」4 B b6a9b5a56 B e8aea2e58d95
写带 emoji 的串UnicodeEncodeError成功
写生僻字 U+20000UnicodeEncodeError成功
写欧元符号UnicodeEncodeError成功
读 GBK 文件正常UnicodeDecodeError
读 UTF-8 文件报错或静默乱码正常

一句话概括：3.15 修好了写入侧，同时弄坏了读取侧。 旧默认下 emoji、生僻字、欧元符号这些根本写不进去，报错原文是 'gbk' codec can't encode character '\U0001f600' in position 2: illegal multibyte sequence；UTF-8 模式下它们全部可写。而反过来，所有当年用默认编码写出来的 GBK 文件，升级后首次用 open() 读就会炸。

这件事在 Windows 上尤其明显，因为同一份代码在 Linux 容器里早就没事：当 locale 是 C 或 POSIX 这类 legacy ASCII locale 时，解释器会自己开 UTF-8 模式（PEP 540 起的行为，locale coercion 失败时也开）。所以「本地测不出来、CI 上一切正常、线上偶发乱码」这类现象，方向基本就是这个。

升级之后，昨天能读的文件今天读不了

三个方向各有一条实测原文，症状完全不同：

  • 旧默认读 UTF-8 文件：UnicodeDecodeError: 'gbk' codec can't decode byte 0xa7 in position 14: illegal multibyte sequence。有时不报错，直接变成能读但全错的乱码 —— 到底报错还是静默，取决于那串字节恰好有没有落进 GBK 的合法区间。
  • UTF-8 模式读 GBK 文件：UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb6 in position 0: invalid start byte。这个更干脆，一个字符都读不出来。
  • 写含 emoji 的文本：UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f600' in position 2: illegal multibyte sequence。

PEP 686 的 Backward Compatibility 一节把风险写得很直白：「may cause UnicodeError, mojibake, or even silent data corruption」，并且点名这次改动主要影响 Windows 用户。

按文件来源分一下类，优先级不完全一样：

  • 自己程序写的日志和报表：跟着部署机走，最容易坏，也最容易修（写的时候显式 utf-8）。
  • 办公软件导出的 CSV：多半是 GBK 或带 BOM 的 UTF-8，读的时候必须显式指定。
  • 第三方接口下载的 JSON：基本都是 UTF-8，反而最安全。
  • 历史归档：这一批才是迁移的真正成本，读的时候给 encoding='gbk' 或者更宽的 gb18030。

用两个开关把隐患变成测试失败

PEP 597 给了 EncodingWarning，默认关闭，要靠开关打开。我用的是把警告直接升级成异常的组合：

python -X warn_default_encoding -W error::EncodingWarning -m pytest

实测效果是 open() 立刻抛 EncodingWarning: 'encoding' argument not specified，带行号，测试直接红，不再是一条容易被刷掉的警告。等价的环境变量是 PYTHONWARNDEFAULTENCODING=1。

覆盖面也量了一遍，同样是逐个调用点验证的：

调用点带开关时的 EncodingWarning 条数
open(path, 'w')1

两个细节值得注意。一是二进制模式不报警，因为它压根不涉及文本编解码；二是加了 -X utf8 之后触发条件一条没变（四组开关组合结果完全一致），说明它查的是「有没有写 encoding」，不是「会不会坏」—— 所以它是静态检查的廉价替代品，不是运行时保护。另外 locale.getpreferredencoding() 也会被点名，这一条是 PEP 686 明确要求加的。

-W error 的副作用要提前想清楚：整个进程里任何一处省略 encoding 都会变成硬失败，第三方库里的也算（它们最终也走 open() 或 TextIOWrapper）。先只跑测试套件，别直接挂到生产启动参数上。

迁移顺序：先定读取侧，再动写入侧

顺序反了会很痛，因为写入侧改了之后，文件内容立刻换编码，而读取侧还没跟上。

  • 读外部文件一律写 encoding。不确定就 utf-8，确定是中文办公软件产物就 gbk 或 gb18030。
  • 自己写出去的文件统一 utf-8。日志这一路记得给 logging.basicConfig(filename=..., encoding='utf-8')，实测 handler 的 encoding 会变成 utf-8，落盘字节也是 UTF-8。
  • 需要临时复刻旧行为就写 encoding="locale"（3.10 起可用）。它在 UTF-8 模式下仍返回 cp936，能救老代码，但它跟着系统走，换台机器又变。想彻底固定，直接写死 gbk 或 utf-8。
  • 别抄 Python 2 时代的 sys.setdefaultencoding('utf-8')。3.x 里这个属性直接不存在，实测 AttributeError: module 'sys' has no attribute 'setdefaultencoding'，网上流传的那段兜底代码在 3.x 里跑都跑不起来。
  • 判断系统编码用 locale.getencoding()，不要用 getpreferredencoding()。后者在 UTF-8 模式下会返回 utf-8，PEP 686 引入前者的理由就是这个漂移。

排错：四个真实报错

UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f600' in position 2: illegal multibyte sequence

写入侧。要么是 open(p, 'w') 没写编码，要么是 print() 的输出被重定向到了文件。修法：文件句柄写 encoding='utf-8'；重定向场景设 PYTHONIOENCODING=utf-8 或加 -X utf8。

UnicodeDecodeError: 'gbk' codec can't decode byte 0xa7 in position 14: illegal multibyte sequence

旧默认读 UTF-8 文件。位置 14 说明前面十几个字符都读成功了，是半路撞上一个 GBK 不认的字节 —— 这也是这类故障看起来「部分乱码」的原因。修法：读的时候显式 encoding='utf-8'。

UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb6 in position 0: invalid start byte

反向：UTF-8 模式（或 3.15 默认）读 GBK 老文件。0xb6 是「订」的 GBK 首字节。修法：encoding='gbk'，或者更宽的 gb18030（cp936 编不了的四字节区它能编，实测 U+20000 在 cp936 下抛错、在 gb18030 下得到 95328236）。

EncodingWarning: 'encoding' argument not specified

不是故障，是你把开关打开了。它指的那一行就是漏写 encoding 的位置。修法二选一：补 encoding='utf-8'；如果这一处本来就要跟系统走，就写 encoding='locale' 明确表态，警告随之消失。

常见问题

Q：我把 PYTHONIOENCODING 设成 utf-8 了，为什么写文件还是 GBK？

因为它只改标准流，不改 open()。实测在只设这一个变量的进程里，sys.stdout.encoding 是 utf-8，而 open(p).encoding 仍然是 cp936。要改文件那一层，用 -X utf8、PYTHONUTF8=1，或者在每个 open() 上写 encoding。

Q：升级到 3.15 之后，能不能让 open() 回到旧行为？

两种。全局层面用 PYTHONUTF8=0 或 -X utf8=0，但这两个开关只在解释器启动时生效，运行中改不了；单点层面写 encoding="locale"，它在 UTF-8 模式下仍然给出 cp936（实测）。后者更适合逐步迁移。

Q：为什么同一个程序在 Docker 里正常，Windows 上乱码？

容器里通常是 C 或 POSIX locale，解释器会自动开 UTF-8 模式，open() 默认就是 utf-8；Windows 中文系统给的是 cp936。同一份代码，两个默认值，谁都没写错，但结果不一样。

Q：中文文件名一直没问题，是不是说明我的编码处理是对的？

不能。文件名走文件系统编码（Windows 上固定 UTF-8），文件内容走 locale 编码，两层不共享同一张表。实测在两种模式下建中文目录、listdir 回来都正常命中，而同一进程里写文件内容的默认值已经从 cp936 变成 utf-8。用中文路径做测试，覆盖不到真正会坏的那一层。

最后

三条判据，贴在代码评审里就够用：

  • 看到 open() 没写 encoding，就当它是「跟机器走」的代码，跨平台不可信。
  • 看到 str.encode() 不用怀疑环境，它恒定 UTF-8；看到 open() 才需要怀疑。
  • 迁移前先跑 -X warn_default_encoding -W error::EncodingWarning，把「哪些文件路径依赖了默认值」一次性列出来，再决定每一处写死还是写 locale。

至于那个跑了三年的 CSV，它没有坏，只是从来没在 UTF-8 模式下被读过。3.15 之后，它会在首次 open() 的那一刻告诉你这件事。想先看「坏字节进来之后五种处理器各自怎么办」，可以接着读 编码错误处理的五种策略；想弄清管道那一层（subprocess 的 text=True 为什么能返回空字符串），七个静默失败的 subprocess 用法 里有实测；CSV 的记录边界在 八个静默移动边界的 CSV 坑 里。
