Windows path 的 8 处静默分歧：写进去的不是那个名字

WindowsPythonpathlib

TL;DR：Windows 上的路径不是「一个字符串对应一个文件」的映射，而是一条流水线：你先写一个串，Win32 层做规范化，再决定用哪个命名空间，最后才到 NTFS 解析名字。流水线上每一步都可能把串改掉或者换掉，而其中大部分动作不抛异常、不写日志、exit code 还是 0。

这篇文章里的数字全部来自 2026-11-14 在本机的实测：Windows 11 build 26300、CPython 3.13.12、NTFS 卷。被测对象是我自己建的临时目录，不是别人的仓库。官方口径逐条对照了 Microsoft Learn 的 Naming Files, Paths, and Namespaces 与 CPython 3.13 的文档和源码。

先说结论：路径比较永远不要用字符串相等，遍历目录前永远先问一句「这是不是一个重解析点」，写文件前永远先看一眼 abspath 之后的长度。下面八处，每一处都配了实测输出和它会咬人的场景。

尾随空格与点：你写的名字被改掉了，没人告诉你

我实际测试的第一件事，是在一个空目录里写两个文件：

open('note.txt ', 'w')      # 结尾有一个空格
open('report.txt.', 'w')    # 结尾有一个点

两个 open 都成功返回。然后 os.listdir 给出的结果是 ['note.txt', 'report.txt']，空格和点都不见了。文件的字节数正常、内容能读回、open('note.txt ') 也能打开它——因为系统在打开时又做了一次同样的剥离，所以你完全看不出中间发生过什么。

微软的官方文档把这条写在命名规则里：「Do not end a file or directory name with a space or a period. Although the underlying file system may support such names, the Windows shell and user interface does not.」注意这句话的结构：文件系统支持，是 shell 和界面不支持。真正做剥离的是 Win32 那条路径上的一层，NTFS 本身并不禁止。

更细的一处：os.path.abspath 的官方文档直接写了这个行为，「Trailing dots and spaces are stripped」，并给了一个例子 os.path.abspath('c:/temp/spam. . .') 返回 c:\temp\spam。也就是说，你在规范化函数里能看到这个动作，但在 open 里看不到。

危险场景有三个：从表格或文件名列表批量导入名字时，a.txt 和 a.txt 会指向同一个文件，去重逻辑却认为是两个；把标题直接当文件名时，结尾的点被吃掉后扩展名判断跟着变；以及跨平台同步——在 Linux 上这样命名是合法的，两个平台各自维护索引，最后对不上。

data.txt:hidden 里的 18 字节：任何目录列表都看不见

同一台机器上，我写了这样一个文件：

open(str(path) + ':hidden', 'w').write('secret-stream-here')

主文件 data.txt 仍然是 9 字节，内容仍是 main-body。而 os.path.getsize(路径 + ':hidden') 返回 18。目录列表 os.listdir 只有一条 data.txt，dir 也看不出来。只有 dir /r 会多打一行：

2026/11/14  06:13                 9 data.txt
                                 18 data.txt:hidden:$DATA

这是 NTFS 的备用数据流（alternate data stream）。官方 File Streams 文档的命名规则写得很清楚：完整形式是 filename:stream name:stream type，默认数据流是无名的，写全了就是 filename::$DATA。文档里还有一句容易漏掉的：「There are no file times associated with a stream. The file times for a file are updated when any stream in a file is updated.」——流没有自己的时间戳，但改了流会动主文件的时间，于是任何靠 mtime 判断「这个文件有没有变」的增量备份都会误判。

我顺手验了最容易踩的一步：shutil.copy2 复制过去的 copy.txt 再打开 copy.txt:hidden 直接 FileNotFoundError。Python 的复制走的是读主数据流再写新文件，流不在其中。这不是 Python 的缺陷，Windows 自己的 copy 命令行为一致。

这一条的现实影响集中在三处：备份工具只备份主数据流，流里的内容静默消失；杀毒软件与取证工具如果不扫 :$DATA，看的是半个文件；而做体积统计时，sum(getsize(f) for f in listdir()) 得到的是 9 而不是 27。

C:rel.txt 不是 C:\rel.txt，它指向一个你看不见的工作目录

这是我认为最容易被写进生产代码的一条。先看两组实测：

os.chdir('C:\\Windows')
os.path.abspath('C:rel.txt')     ->  'C:\\Windows\\rel.txt'
os.chdir('D:\\')
os.path.abspath('C:rel.txt')     ->  'C:\\Windows\\rel.txt'   # 没变

第二行才是重点。cmd 的 cd 只改当前盘的工作目录，Windows 为每个盘符单独保留了一个「该盘的当前目录」，而且这个值在进程里是隐藏的、os.getcwd() 永远只报当前盘那一个。所以 C:rel.txt 的含义不是 C:\rel.txt，而是「C 盘那个隐藏工作目录下的 rel.txt」；你把进程切到 D 盘，它照样回 C 盘去解析。

os.path.isabs('C:rel.txt') 返回 False，os.path.splitdrive 给出 ('C:', 'rel.txt')，PureWindowsPath('C:rel.txt').is_absolute() 也是 False。官方 os.path.abspath 文档写的是同一件事：「A drive-relative path is resolved against the current directory of the specified drive, and the drive letter is capitalized.」

拼接函数也会配合这个语义：os.path.join('C:', 'x.txt') 得到 'C:x.txt'，而 os.path.join('C:\\', 'x.txt') 才是 'C:\\x.txt'。少一个反斜杠，就从一个绝对路径退化成一个依赖隐藏状态的相对路径，而且不报错。

还有一个跨盘的硬错误值得记住：os.path.relpath('C:/x.txt', 'D:/openclaw-blog') 直接抛 ValueError: path is on mount 'C:', start on mount 'D:'。这不是 bug，是两个卷之间没有相对路径可言。

\\?\ 前缀：关掉字符串解析的同时，也关掉了你的容错

\\?\ 前缀的用途写在官方命名空间一节里：「the '\\?\' prefix to a path string tells the Windows APIs to disable all string parsing and to send the string that follows it straight to the file system」，并且它能让路径突破 MAX_PATH。

但「不解析」是双向的。实测四种写法：

写法结果
\\?\D:\...\v4\a.txt正常读回内容
\\?\D:\...\v4\..\v4\a.txtOSError: [Errno 22] Invalid argument
\\?\D:\...\v4/a.txt（混正斜杠）OSError: [Errno 22] Invalid argument
\\?\a.txt（相对路径）FileNotFoundError: [Errno 2]

也就是说，前缀不是「路径清洗器」，它是「免检通道」：写了 .. 就是往文件系统里塞一个叫 .. 的成分，写了正斜杠就是不认，写相对路径就是不认。要用它，必须自己先 abspath 再统一成反斜杠，而且路径本身必须是完整限定名。

官方文档里有一句容易被误读的话：前缀「also allows the use of ".." and "." in the path names」。这句的本意是关掉自动展开后，你可以拿这些字面量当文件名的一部分去操作；在把 .. 当目录成分用的场景下，本机实测是直接 EINVAL。这类文档句子必须配一次实测才能落进代码。

259 与 260：exists() 在这条线上会骗你

我用了很短的基座目录 D:\pl1114，再拼两级各 100 字符的目录，把父路径定死在 211 字符，然后二分文件名长度：

完整路径长度结果
259写入成功
260FileNotFoundError: [Errno 2] No such file or directory

同一时刻，对那条 260 字符的路径：os.path.exists() 返回 False，os.path.isfile() 返回 False，os.stat() 抛 FileNotFoundError: [WinError 3] 系统找不到指定的路径，os.listdir() 同样 WinError 3，Path.mkdir() 也是 WinError 3。

这是我最想让人记住的一点：超长路径不会给你一个「太长」的错，它给你一个「不存在」。任何 if not exists(p): create(p) 的写法在这条线上会静默走进创建分支，然后再崩在创建那一步。

官方口径：Windows 10 1607 之前的路径上限就是 MAX_PATH = 260；之后的版本要「changing a registry key or using the Group Policy tool」才能解除。本机 HKLM\SYSTEM\CurrentControlSet\Control\FileSystem 下的 LongPathsEnabled 是 0，也就是出厂默认，所以 260 这条线是活的。

另外两个数字：单段名字的上限是 255，我测到 255 字符的文件名（路径 258）可以建，256 字符（路径 259）抛 OSError: [Errno 22] Invalid argument——注意这里路径还没到 260，所以它是名字长度超限，不是总长超限。而加 \\?\ 前缀后，260 字符的路径可以正常写入，前提是父目录已经存在：前缀只免除长度检查，不负责替你建目录。

实践判据只有一句：len(os.path.abspath(p)) >= 260 就当超长处理，别问 exists。

junction：islink 说它不是链接，os.walk 却走进去了

用 cmd /c mklink /J 建一个目录联结（不需要管理员权限，实测返回码 0），然后问 Python 它是什么：

os.path.islink(junc)         ->  False
os.path.isjunction(junc)     ->  True
os.path.isdir(junc)          ->  True
os.path.samefile(junc, real) ->  True
Path(junc).resolve()         ->  ...\real

islink 为 False 不是 bug：符号链接和 junction 是两种不同的重解析点。官方 Hard Links and Junctions 页说 junction「is implemented through reparse points」，Python 从 3.12 才补上 os.path.isjunction（文档标注 Added in version 3.12）。

后果在遍历上。我在父目录里放了 real\x.txt 和一个指向 real 的 junc，然后：

os.walk(父目录, followlinks=False)  ->  ['junc\\x.txt', 'real\\x.txt']
Path(父目录).rglob('*.txt')         ->  ['junc\\x.txt', 'real\\x.txt']

同一个文件被数了两次。原因能追到源码：CPython 3.13.12 的 Lib/os.py 第 434 行是 if followlinks or not islink(new_path):——followlinks=False 只挡住了 islink 为真的项，junction 不在其中。followlinks 这个名字会让人以为是「别跟着链接走」，实际语义是「别跟着符号链接走」。

这一条对备份、磁盘占用统计、静态资源扫描是硬伤：统计会偏大，复制会重复，如果 junction 指回自己的祖先目录，就是无限递归。

C:/PROGRA~1 与 8.3 短名：同一个目录，两个字符串

同一台机器上：

os.path.exists('C:/PROGRA~1')                        ->  True
os.path.samefile('C:/Program Files', 'C:/PROGRA~1')  ->  True
os.listdir('C:/PROGRA~1')                            ->  ['AMD', 'Android', 'Autodesk', ...]
os.path.exists('C:/WINDOW~1')                        ->  False

前两条说明短名是真实存在的别名，第三条说明它指向的就是同一个目录。第四条才是坑：同一台机器上、同样是系统目录，C:\Windows 没有 WINDOW~1 这个短名。8.3 名字的生成取决于卷的策略和条目创建时机，不是普遍存在的东西。

于是字符串比较全线失败：'C:/PROGRA~1' != 'C:/Program Files'，长度、哈希、白名单匹配全都不一样，但 samefile 说是同一个目录。

所以要判「是不是同一个东西」，用 os.path.samefile，不要用 ==。要判「是不是同一个字符串」，用 os.path.normcase——官方文档：「On Windows, convert all characters in the pathname to lowercase, and also convert forward slashes to backward slashes.」

a[1].txt：glob 会把方括号当字符类

我在一个目录里建了 a[1].txt 和 a1.txt 两个文件，然后按字面去匹配第一个：

Path(d).glob('a[1].txt')                  ->  ['a1.txt']
Path(d).glob(glob.escape('a[1].txt'))     ->  ['a[1].txt']
fnmatch.fnmatch('a[1].txt', 'a[1].txt')   ->  False

[1] 被当成「匹配字符 1」，于是模式命中的是 a1.txt。glob 文档自己给了说法：「For a literal match, wrap the meta-characters in brackets. For example, '[?]' matches the character '?'」——这句是在教你写模式，不是在告诉你它会自动转义；glob.escape 才是转义入口（转义 ?、*、[ 三个字符）。

现实中这个形状很常见：日志文件、备份文件名、从用户输入拼出来的路径，都可能带方括号。用模式去复制、删除、统计时，少一次 escape，动到的就是另一个文件。这也是所有「按模式批量操作」的默认风险，不是 glob 独有。

Troubleshooting：四个真实报错怎么读

OSError: [Errno 22] Invalid argument，路径里带 \\?\ 前缀。 八成是前缀后面的串里有 .. 或正斜杠。修法：先 os.path.abspath()，再 .replace('/', '\\')，确认没有 .. 残留，最后才拼前缀。

FileNotFoundError: [Errno 2] No such file or directory，而文件其实就在那儿。 先量长度。260 及以上在默认配置下就是这个报错，exists() 还会配合着返回 False。判据是 len(p) >= 260，不是「文件真的没了」。

FileNotFoundError: [WinError 3] 系统找不到指定的路径，出现在 os.stat 或 os.listdir。 同一个原因，不同的 API 报不同的码：open 给 Errno 2，stat 与 listdir 给 WinError 3。看到 WinError 3 先怀疑长度，不要先怀疑权限。

OSError: [WinError 17] 系统无法将文件移到不同的磁盘驱动器，出现在 os.replace。 跨卷重命名在 Windows 上根本不成立。实测 os.replace 抛 17，而 shutil.move 成功——后者会退化成复制加删除，代价是原子性没了，源文件可能已经删掉而目标只写了一半。

顺带一个：对文件调 os.listdir 会得到 NotADirectoryError: [WinError 267] 目录名称无效，这个码只在「路径存在但类型不对」时出现，和「不存在」是两回事。

另外两处可以顺手记住

大小写。写 Case.TXT，用 case.txt 能直接读到内容，os.path.samefile 判 True，Path('C:/Temp/Case.TXT') == Path('c:/temp/case.txt') 在 Windows 上也是 True——PurePath 在 Windows 上的相等比较不分大小写。但字符串 == 是 False。所以「同一个文件」在 Python 里有三种答案：字符串不等、Path 对象相等、samefile 相等。

设备名。官方命名规则明确写「Also avoid these names followed immediately by an extension; for example, NUL.txt and NUL.tar.gz are both equivalent to NUL」。而我这台 build 26300 上，cmd /c echo hello > nul.txt 建出了一个 12 字节的真文件，type nul.txt 能读回 hello，os.listdir 也列得出来；只有不带扩展名的裸 nul 仍然是个黑洞，写进去返回成功、磁盘上什么都没有。两个行为都能复现，所以我给的建议不是「哪个对」，而是：别把设备名当文件名用，也别写依赖某一种行为的代码。

一份能直接抄进代码的清单

  • 判断「是不是同一个文件」用 os.path.samefile；判断「是不是同一个字符串」用 os.path.normcase。两者都不等于 ==。
  • 遍历目录时先问 os.path.isjunction，不要只信 followlinks=False。
  • 写文件前先 abspath 并量长度，>= 260 就走短路径或加前缀，不要依赖 exists。
  • 备份或统计前先枚举流（dir /r 或 FindFirstStreamW），主数据流不等于整个文件。
  • 用 glob 或任何模式匹配去复制、删除之前，先 glob.escape。
  • 名字来源是用户输入或表格时，先剥尾随空格与点，再判空——否则你判的那个名字和磁盘上的名字不是一个。

这一套的门槛很低，但漏掉任何一条，出错时都只会看到「文件不存在」或者「结果多了一份」，看不到真正的原因。路径这一层和模块导入层是同一类问题：你以为你在描述一个对象，其实你在写一个会被重新解释的字符串。站内另一篇讲 Python import 的 8 处静默取错 是同一个思路的另一个面；再往前，tarfile 解压的五种写到目录外 讲的是路径字符串被下游重新解释后的安全后果，而 Shell 脚本九个静默失败 讲的是同一种「退出码 0、什么都没发生」的失败形态。

FAQ

Q：os.path.exists 返回 False，就一定说明文件不存在吗？

不一定。路径长度达到 260 时它同样返回 False，而文件可能真的在那里。先量 abspath 之后的长度，再怀疑存在性。

Q：为什么 shutil.copy2 复制过去的文件少了东西？

因为它复制的是主数据流。NTFS 的命名流（file:stream）不在复制范围内，Windows 自带的 copy 也一样。要连流一起搬，得用支持流的工具或 CopyFile2 一类 API。

Q：followlinks=False 为什么还会走进 junction？

这个参数只检查 islink。junction 的 islink 是 False，所以在 os.walk 眼里它是一个普通目录，会被正常下钻。要挡掉它，遍历时自己判 os.path.isjunction。

Q：\\?\ 前缀是不是「长路径开关」？

它关掉的是字符串解析，顺带绕开长度检查。代价是 ..、正斜杠、相对路径全部不再被处理。要用就得自己先把路径规范化好。
