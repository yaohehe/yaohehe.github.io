pip-audit 2.10.1 实测：37 条告警去重后只剩 19 个真问题

pip-audit供应链安全依赖漏洞

CI 里那行 pip-audit -r requirements.txt 绿了，很多人就认为供应链审计这一关过了。我在 Windows 11 + CPython 3.13.14 上装了 pip-audit 2.10.1（PyPI 上截至发稿的最新版，2.10.1 的上传时间是 2026-06-10），把同一份依赖文件从锁定改成范围、从默认漏洞服务换成 OSV、从 --fix 跑到 --strict，一共跑了十几轮。

第一个结论很不舒服：Found 37 known vulnerabilities in 3 packages 里的 37 不是漏洞数。去重之后是 19 个。差的 18 条不是噪声，是同一条安全公告被 OSV 用两套编号各发了一次，而 pip-audit 2.10.1 把它们都留下了。

本文是一次本机实测记录，不是工具介绍。所有数字都来自我自己跑出来的输出，命令和文件都写在正文里，你可以逐条复现。本文不含任何联盟推广链接，也没有 affiliate 佣金链接——纯技术，不带货。

这件事在站内属于哪一层

站里已经有三篇相邻的文章，决策层各不相同，先划清楚界限，免得读重：

09-29 那篇讲的是 CI 层的供应链事件复盘（GitHub Actions 被投毒之后怎么看）；xz 后门那篇讲的是产物溯源层（tarball 和 git 仓库对不上怎么办）；10-21 那篇讲 PEP 440 版本钉死的语法层。本篇往下走一层：本机 Python 依赖层——你手上这台机器、这份锁文件，到底被审了几个包、审出了几个真问题。

实验台：六个文件，一台机器

环境固定：Windows 11、CPython 3.13.14、pip-audit 2.10.1，装在隔离目录 tmp/w46-pipa（用 pip install --target 装，不动主环境），调用方式是 PYTHONPATH=tmp/w46-pipa python -m pip_audit。

我测试了六份文件，内容都很短，你可以照着建：

  • reqs-req.txt：requests==2.19.0
  • reqs-range.txt：requests>=2.0
  • reqs-flask-pin.txt：flask==3.0.0
  • reqs-flask-range.txt：flask>=3.0
  • reqs-vuln2.txt：requests 2.19.0 + PyYAML 5.1 + Jinja2 2.11.2 + setuptools 65.5.0 + certifi 2022.12.7
  • reqs-local.txt：requests==2.19.0 加一行本地路径依赖 tmp/audit-1109/localpkg

另外还有两份故意写坏的，用来取真实报错（见第八节）。

一、37 这个数字是怎么来的

先看单个包。requests==2.19.0 跑出来是这样：

Found 37 known vulnerabilities in 3 packages

三个包（requests、idna、urllib3）合计 37 条。我把 JSON 输出按 id 去重，数字立刻变了：

包版本告警行数去重后公告数
requests2.19.0105
idna2.742
urllib31.232312
chardet3.0.400
合计-3719

每一条都恰好出现两次。不是巧合，是两套编号在同一个响应里并存。

二、直接问 OSV：同一个版本，10 条记录只对应 5 个公告

跳过 pip-audit，直接 POST 到 https://api.osv.dev/v1/query，只用包名和版本：

POST /v1/query
{"package": {"name": "requests", "ecosystem": "PyPI"}, "version": "2.19.0"}

返回 10 条，distinct 也是 10——OSV 这边没重复，它老老实实给了 10 条记录。但看 id 和 aliases 就明白了：

GHSA-x84v-xcm2-53pg  aliases: ["CVE-2018-18074", "PYSEC-2018-28"]
PYSEC-2018-28        aliases: ["CVE-2018-18074", "GHSA-x84v-xcm2-53pg"]
GHSA-j8r2-6x86-q33q  aliases: ["CVE-2023-32681", "PYSEC-2023-74"]
PYSEC-2023-74        aliases: ["CVE-2023-32681", "GHSA-j8r2-6x86-q33q"]

5 对，每对自己指自己。这是 OSV 的正常形态：一篇 GitHub Advisory（GHSA-）和一条 PyPA 的 PYSEC 记录，指同一个问题，互为别名。真正的问题是下一步。

pip-audit 拿到这 10 条之后，在 pip_audit/_service/interface.py 里做了一次主 id 归一化——VulnerabilityResult.create() 把 ids 排序后取第一个当主 id，排序规则优先 PYSEC 和 CVE。于是那条 GHSA 记录也被改写成 PYSEC-2018-28。到这里还算合理，两条记录现在长得一模一样了。

再往下就出问题了。pip_audit/_audit.py 的去重分两轮：第一轮只挑 id 以 PYSEC 开头的，直接 append，不查彼此是不是别名；第二轮才处理非 PYSEC 的，会拿 seen_aliases 去判重。第一轮进来的两条已经是同一个 PYSEC id、别名集也完全相同，但没人拦，就都留下了。

结果就是：一条公告，两行输出，数字翻倍。urllib3 1.23 那 23 行里，只有 12 个是真公告——其中一条 PYSEC-2026-4177 只出现一次，因为它没有 PYSEC 对手（OSV 只有 GHSA 那条）。这也解释了为什么 37 不是 38 的整数倍关系，重复是"大多数被复制"，不是"全都复制"。

顺带一个直接证据：同一条公告的两行，description 措辞不一样。PYSEC 那条写 "The Requests package before 2.20.0..."，GHSA 那条写 "The Requests package through 2.19.1 before 2018-09-14..."。这是同一条公告的两个版本。

三、`--dry-run` 那一行才是真正的体检结果

README 里写得很清楚：pip-audit --dry-run 单独使用时会跳过审计步骤、只打印"本来会审多少个依赖"。这一行是我现在每轮必看的：

INFO:pip_audit._audit:Dry run: would have audited 4 packages
INFO:pip_audit._audit:Dry run: would have audited 7 packages
INFO:pip_audit._audit:Dry run: would have audited 0 packages

三条分别对应 requests==2.19.0、flask>=3.0、requests>=2.0。

前两个正常。第三个要命：同一个未锁定的写法，flask>=3.0 审了 7 个包，requests>=2.0 审了 0 个包，两次的命令、退出码、末行输出完全一样——都是 No known vulnerabilities found，都是 exit 0。我换了一个从没跑过的新文件名重测，结果不变；逐层复现到 pip-audit 内部的临时虚拟环境，installed_packages 就是空列表，而我自己手工建一个 venv 跑同一条 pip install --dry-run --report，pip 老老实实解析出了 requests 2.34.2 加四个依赖。

我翻完了 _dependency_source/requirement.py 的收集逻辑和内建 venv 的报告解析，没有找到一条显式规则能解释这个差异。所以我不把它当成"设计意图"写，只当成"2.10.1 上实测到的现象"：同样是范围声明，能不能被审到因包而异。可操作的结论只有一条——别信末行那句 No known vulnerabilities found，去看 --dry-run 报的包数。

同一节还有一个更常见的坑：版本漂移。flask==3.0.0 报 2 行（去重后 1 个公告 PYSEC-2026-2151，也就是 CVE-2026-27205，官方修复版本 3.1.3）；而 flask>=3.0 因为解析到最新的 3.1.3，7 个包全干净、exit 0。也就是说，审计范围声明审的是"将来会装的最新版"，不是你线上正在跑的那一版。

四、三种"没审到"，只有一种会响

情况表现退出码会不会响
本地路径依赖（不在 PyPI）JSON 里 skip_reason 一行，不计入总数由其它包决定默认不响，加 --strict 才失败
版本范围声明（本例）审 0 个包0不响
包名打错、版本不存在No matching distribution found1响

本地路径依赖那一条值得单独说。JSON 输出是这样的：

{"name": "localsample", "skip_reason": "Dependency not found on PyPI and could not be audited: localsample (0.1.0)"}

它出现在 dependencies 数组里，但没有 version 字段，也没有 vulns。你的解析脚本如果写 dep["version"]，这里直接 KeyError——我第一版就是这么崩的。它不计入 Found N vulnerabilities，也不影响退出码；同一份文件里只要有一个包有漏洞，你还是拿到 exit 1，看起来"审计跑过了"，其实内部包一个都没审。

加 --strict 才会把这件事变成失败，报错原文是：

ERROR:pip_audit._cli:localsample: Dependency not found on PyPI and could not be audited: localsample (0.1.0)

README 对 --strict 的定义是"dependency collection fails 时让整个审计失败"。私有包、内部 sdist 多的项目，这个开关基本是必须的。

五、`--fix` 会把 CI 的失败改成成功

这是我这一轮最不想要、但确实存在的发现。把 requests==2.19.0 那份文件复制一份，跑 pip-audit --fix：

Found 37 known vulnerabilities in 3 packages and fixed 37 vulnerabilities in 3 packages

退出码是 0。也就是说，一个本来该让流水线红掉的命令，加上 --fix 之后变成了绿灯，而它做的事是两件：把 requests==2.19.0 改成 requests==2.33.0，并且往文件里追加两条原本没有的依赖：

requests==2.33.0
# pip-audit: subdependency explicitly fixed
idna==3.15
    # pip-audit: subdependency explicitly fixed
urllib3==2.8.0

两个细节值得记：注释缩进不一致（第二条多了四个空格）；子依赖被提升成了直接依赖并钉死。这在"锁文件由工具生成"的流程里也许没问题，但如果你把 requirements.txt 当人工维护的清单，下次有人手动改版本时就会发现多出两行没人记得加过的包。

--fix --dry-run 是安全的那个：它只打印"would have upgraded requests to 2.33.0"这类信息，不改文件。要用就用这个，改文件的那一步留在人手上。

六、换一个漏洞服务，数字又变了

默认服务不是 OSV。命令行参数解析日志里写着 vulnerability_service=，README 的参数表也把默认值列在 PIP_AUDIT_VULNERABILITY_SERVICE 那一行。同一份文件显式加 -s osv：

  • 默认（pypi）：37 行，去重 19 个
  • -s osv：38 行，去重 19 个

两者去重后的公告集合完全相同（我用"包名 + id"做键对比，两个方向的差集都是空）。差的 1 条只是某一条公告在 OSV 侧又多复制了一次。所以"换服务数字变了"这个现象是真的，"换服务审出的问题变了"是假的——至少在这三个包上是假的。

七、我建议接进 CI 的最小写法

三条命令，各管一件事：

# 1. 先确认到底审了几个包（这一步决定后面两步有没有意义）
python -m pip_audit -r requirements.txt --strict --dry-run

# 2. 真审计，输出 JSON 自己数（别信末行的数字）
python -m pip_audit -r requirements.txt --strict --progress-spinner off -f json -o audit.json

# 3. 解析：按"包名 + id"去重，报"去重后的公告数"和"审计包数"

第 3 步的判据我建议写成两条与：去重后公告数等于 0，且审计包数等于你预期的值（比如锁文件里 == 的行数）。只判第一条，就会漏掉"审了 0 个包"这种绿灯。只判退出码，会同时漏掉这两种——CI 面板上照样是 100% 通过。

另外两个提醒：pip-audit 要出网（它建临时 venv 让 pip 解析依赖），网络受限的 CI 上先跑一次确认；--fix 不要放进流水线，它会把失败改成成功并且改文件。

八、Troubleshooting：三个我实际撞到的报错

报错一：`ResolutionImpossible`

我第一版文件写了 requests==2.19.0 加 urllib3==1.24.1，想"一次多扫几个"，结果：

ERROR:pip_audit._virtual_env:internal pip failure: ERROR: Cannot install -r tmp\audit-1109\reqs-vuln.txt (line 1) and urllib3==1.24.1 because these package versions have conflicting dependencies.
ERROR: ResolutionImpossible: for help visit https://pip.pypa.io/en/latest/topics/dependency-resolution/#dealing-with-dependency-conflicts
ERROR:pip_audit._cli:Failed to install packages: [...]

原因是 requests 2.19.0 自己要求 urllib3<1.24，和手写的 urllib3==1.24.1 直接冲突。pip-audit 靠"把文件装进临时环境"来解析，装不上就没有审计对象。处置：别手工指定子依赖的版本，让它自己解析；或者拆成两个文件分别跑。好消息是这类失败是响的，exit 1。

报错二：`No matching distribution found`

ERROR:pip_audit._virtual_env:internal pip failure: ERROR: Could not find a version that satisfies the requirement not-a-real-package-zzz==1.0.0 (from versions: none)
ERROR: No matching distribution found for not-a-real-package-zzz==1.0.0

这是我故意用一个不存在的包名测的。行为符合预期：直接失败、exit 1。但它也解释了一个隐蔽情况：如果包名拼错发生在依赖树深处（某个包的 install_requires 写错），整轮审计会直接崩，而不是"跳过这一条继续"。看到这条不要以为是网络问题，先去看包名和私有源配置。

报错三：`Dependency not found on PyPI and could not be audited`

ERROR:pip_audit._cli:localsample: Dependency not found on PyPI and could not be audited: localsample (0.1.0)

这条只在加了 --strict 时出现（不加就静默跳过，见第四节）。你的私有包、内部 SDK、本地路径依赖，全部走这一条。处置：私有包在企业内部源上时，用 --index-url / --extra-index-url 指过去；本地开发期的路径依赖，接受它被跳过，但要在 CI 里用 --strict 让"被跳过的数量"变成可见的失败。

九、这篇没解决的问题

三条，写清楚以免读者误用：

1. requests>=2.0 为什么一个包都没审到，我没定位到根因。复现路径在第三节，源码层面只确认了它是空集合，没找到规则。

2. 只测了 Windows。Linux 上临时 venv 和 pip install --dry-run --report 的行为可能有差异，尤其涉及系统包时。

3. 没碰 SBOM 和 CycloneDX 输出（-f cyclonedx-json）。pip-audit 2.10.1 的依赖里已经带了 cyclonedx-python-lib 11.12.0，这条路是通的，但它是另一个决策层的事，留到以后。

结语

如果这篇只留一句话：pip-audit 的末行数字不是漏洞数，退出码也不是审计覆盖率。去重后有几个公告、实际审了几个包，这两件事都得自己数。想继续往上游走，可以看 10-17 那篇 xz 后门（产物怎么和源码对不上）和 10-29 那篇 tarfile 解压安全（装进来的东西会写到哪去）——一个在依赖进来之前，一个在依赖落地之后，中间这段才是本篇覆盖的本机扫描层。
