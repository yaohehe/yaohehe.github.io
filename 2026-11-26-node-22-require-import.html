require 与 import 在 Node 22 里解析到哪一份文件

Node.jsESM模块解析

TL;DR：Node 22.7 和 22.12 各改了一条默认值，一条让「Cannot use import statement outside a module」不再出现，另一条让 require() 可以直接加载 ESM。老报错消失之后，真正咬人的问题换成了「这次到底解析到哪个文件、哪一份实例」。我在 Node 22.22.2 上跑了 40 次子进程用例，18 次以退出码 1 收场，22 次退出码 0 —— 而退出码 0 的那批里，有好几次拿到的并不是我想要的东西。下面每条报错都附原始文案与可复制命令。

两个分水岭：22.7 和 22.12 各改了一条默认值

先把版本事实钉住，因为后面所有「为什么我这里不报错」都源于这两条。

Node v22.7.0（2024-08-22）的发布说明原文是 Module syntax detection is now enabled by default.，并给了判据：ambiguous files 指的是 .js 或无扩展名的文件，且最近的父级 package.json 没有 "type" 字段；这类文件先按 CommonJS 解析，解析失败再按 ES module 跑一遍。想要回旧行为，用 --no-experimental-detect-module。

Node v22.12.0（2024-12-03，LTS Jod）的发布说明原文是 require(esm) is now enabled by default。同一段里还有三句关键话：Node.js will no longer throw ERR_REQUIRE_ESM；但它 can, however, throw ERR_REQUIRE_ASYNC_MODULE（当被加载的 ESM 或它的依赖含 top-level await）；成功时返回的对象 either a ES module namespace object similar to what's returned by import(), or what gets exported as "module.exports"。同一段还给了两个开关：--no-experimental-require-module 关闭，process.features.require_module 探测。

我这台机器的 node -p "process.features.require_module" 打印 true，版本 v22.22.2，V8 12.4.254.21-node.39，系统 Windows 11 10.0.26300。

解析层：import 不补扩展名，也不认 index

官方文档在 resolver 特性里写得很直白：No default extensions、No folder mains。而 CJS 侧几十年来的习惯恰好是两样都补。

于是同一份目录结构，两套规则给出两个结局。require('./util') 退出码 0；import './util' 报：

Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'D:\lab\cases\e-import-noext\util'
imported from D:\lab\cases\e-import-noext\main.js
Did you mean to import "./util.js"?

那句 Did you mean 是 Node 自己给的提示，不是我加的注释。目录导入更狠一点，import './lib' 报 ERR_UNSUPPORTED_DIR_IMPORT，同样附一句 Did you mean to import "./lib/index.js"?。

这条规则没有开关，也没有兼容期。所以从 CJS 迁到 ESM 时，「先把所有相对导入的扩展名补上」不是风格问题，是硬性前置条件。动手前可以先机械地数一遍规模，把不带扩展名的相对导入筛出来：

grep -rnE "from '[^']*'" --include=*.js --include=*.mjs src | grep -vE "\.(js|mjs|cjs|json)'"

我拿三个测试文件验过这条两级过滤：带扩展名的 ./a.js 被筛掉，只留下 ./b 与 ./dir 两行；后者属于目录导入，还得补成 /index.js 才算完。

格式层：一个 .js 由谁决定是 CJS 还是 ESM

判定顺序可以实测出来，官方 packages 文档也给了同样的层次：

第一层是扩展名。文档原文：Regardless of the value of the "type" field, .mjs files are always treated as ES modules and .cjs files are always treated as CommonJS.

第二层是最近的父级 package.json 的 type 字段。文档原文：The "type" field defines the module format that Node.js uses for all .js files that have that package.json file as their nearest parent.

第三层是语法探测，第四层是默认按 CJS。

我实测了第二层的边界：根目录 package.json 写 "type": "module"，sub/package.json 写 "type": "commonjs"，sub/main.js 里用 require('./dep.cjs') 退出码 0。也就是说「最近的那个 package.json 说了算」，父级的设置不会越过子目录的声明。

一旦落到 ESM，require 这个名字就不存在了：

ReferenceError: require is not defined in ES module scope, you can use import instead
This file is being treated as an ES module because it has a '.js' file extension
and 'D:\lab\cases\e-require-undefined\package.json' contains "type": "module".
To treat it as a CommonJS script, rename it to use the '.cjs' file extension.

报错自己把三层信息都写全了：哪个文件、因为哪个 package.json、改成 .cjs 可以脱离。要留在 ESM 里又需要同步加载，用 createRequire(import.meta.url)，而不是往全局塞一个 require。

语法探测：一条老报错变成了静默通过

这是 22.7 之后最容易误判的一处。同一个文件内容 —— 只有一行 import fs from 'node:fs'，没有 package.json —— 在 22.22.2 上退出码 0，正常打印。加上 --no-experimental-detect-module 才回到那条熟悉的报错：

SyntaxError: Cannot use import statement outside a module

.cjs 文件里写 import 同样退出码 1，只是前面会多一行 Warning: Failed to load the ES module: ...main.cjs. Make sure to set "type": "module" in the nearest package.json file or use the .mjs extension. 也就是说探测只对「模糊文件」（.js 或无扩展名）生效，.cjs 是明确声明，不猜。

真正危险的是歧义文件同时写了两种语法。我构造了一份既有 import 又有 module.exports 的 .js：

ReferenceError: module is not defined in ES module scope

探测先按 CJS 试、失败再按 ESM，于是这份文件的 import 让整体被判定为 ESM，随后撞到 module 这个词。报错指向第 2 行的 module.exports，但问题出在「文件格式被猜出来」这件事本身。这种错误在版本不一致的环境里会换一副面孔：同一份文件，22.7 之前报的是 Cannot use import statement outside a module，22.7 之后才是我上面这条 ReferenceError。所以遇到「本地能跑、CI 挂」先对版本号，不要先改代码。

require 与 import 拿到的是不是同一个对象

22.12 之后 require() 能加载 ESM，但「能加载」不等于「拿到同一个东西」。我按有无 default 导出各测了一遍，结论分成两支。

没有 default 导出的 ESM（只有 export const id），require() 与 import() 返回的是同一个命名空间对象，r3 === i2 为 true。

有 default 导出的 ESM，两者不是同一个对象：r1 === i1 为 false。require() 那一侧多一个标记位，两边的 keys 分别是：

require keys: __esModule,default,n
import  keys: default,n

__esModule 的值为 true，import 侧读同一属性拿到 undefined。这是给转译产物做互操作判断用的约定，不是 ESM 规范的一部分 —— 所以任何「用 keys 判断模块形状」的代码会在这里得到两个答案。

同一路径 require() 两次拿到的是同一个对象（r1 === r2 为 true），这点和 CJS 缓存一致。但「同一个包」可以是两份：我在一个包上把 exports 写成 { import: './esm.mjs', require: './cjs.cjs' }，两个文件各有一份计数器，先 require 再 import，结果是

cjs count: 1
esm count: 0
same object: false

一方加一，另一方还是 0 —— 这就是 dual package hazard 的最小复现。官方给的正解是 "module-sync" 条件：把它放在 exports 最前面指向同一份 .mjs，我实测 require() 与 import() 都拿到 native ESM，same 为 true，计数只有一份。

还有一条冷门但真实存在的出口：ESM 里写 export { api as 'module.exports' }，require() 会直接返回 api 这个对象本体（keys 只有 hello，没有 default、也没有 __esModule）。它对应 22.12 里那条 support module.exports interop export 的提交，属于「库作者主动指定 require 侧形状」的通道。

具名导入能不能用，取决于你怎么赋值

从 CJS 里具名导入，官方口径是 Named exports may be available, provided by static analysis as a convenience for better ecosystem compatibility. —— 关键词是 may 和 static analysis。我把四种最常见的赋值写法各跑了一遍：

CJS 侧写法import() 看到的 keys能否具名导入
module.exports.foo = 1default,foo能
module.exports = { foo: 1 }default不能
先建对象、赋值、再整体导出default不能
Object.defineProperty(exports, foo, ...)default,foo能

四种写法里能具名导入的只有两种，恰好 50%。第三种最容易被误认为等价 —— 它和第二种的运行时结果完全一样，但静态分析拿不到键名。

强行具名导入的报错长这样：

SyntaxError: Named export 'bar' not found. The requested module './dynamic.cjs'
is a CommonJS module, which may not support all module.exports as named exports.
CommonJS modules can always be imported via the default export, for example using:

import pkg from './dynamic.cjs';
const { bar } = pkg;

注意它是 SyntaxError 且在链接阶段抛出：同一个文件里前面的具名导入已经通过，整个模块仍然一行都不会执行。所以「改成 default 导入再解构」是唯一稳的写法，代价是丢掉静态可分析性。

exports 字段：条件顺序先于条件内容

packages 文档有一句容易被跳过的原文：Within the "exports" object, key order is significant. During condition matching, earlier entries have higher priority and take precedence over later entries. 以及关于 default 的那句：This condition should always come last.

我把它做成 A/B 两组，除键序外完全相同：

{ "default": "./a.js", "require": "./b.js", "import": "./c.mjs" }   -> require got a.js
{ "require": "./b.js", "import": "./c.mjs", "default": "./a.js" }   -> require got b.js

第一组里 require() 拿到的是 default 指向的 a.js。原因是匹配按插入顺序走，default 无条件命中，后面的 require 永远轮不到。这种错误没有任何警告，包作者的意图和实际行为正好相反。

同一份 package.json 里 main 与 exports 并存时，exports 胜出（我实测返回 { from: 'exports field' }），官方原文是 this will take precedence over the "main" field。

通配符那条更隐蔽。文档说 * 是 a direct static matching and replacement without any special handling for file extensions。我写了 "./*": "./src/*.js"，然后请求 wpkg/feat/a.js，解析结果是 src/feat/a.js.js：

Error: Cannot find module 'D:\lab\cases2\i-exports-wildcard\node_modules\wpkg\src\feat\a.js.js'

正确形态是两边都写 *.js："./*.js": "./src/*.js"。

排错：六条真实报错的现象、原因与修法

以下每条都是我在本机跑出来的原始文案，不是「典型报错」模板。

第一条 · ERR_MODULE_NOT_FOUND：ESM 里 import './util'。原因是 ESM resolver 不做扩展名补全。修法只有补全，或用动态导入显式给出完整路径：

node --input-type=module -e "import('./util.js').then(m => console.log(Object.keys(m)))"

第二条 · ERR_UNSUPPORTED_DIR_IMPORT：import './lib'。ESM 不认目录的 index.js。修成 import './lib/index.js'，或给包加 exports 映射。

第三条 · ERR_REQUIRE_ASYNC_MODULE：require('./tla.mjs')，而那个模块里有 top-level await。原文是 require() cannot be used on an ESM graph with top-level await. Use import() instead. 修法二选一：改 await import()，或去掉 TLA。想定位是哪个模块引入的 TLA，加 --experimental-print-required-tla。

第四条 · ERR_IMPORT_ATTRIBUTE_MISSING：import data from './d.json'。22.12 起 JSON 模块转正，但属性是强制的。修法是 with { type: 'json' }；写成旧的 assert { type: 'json' } 会得到 SyntaxError: Unexpected identifier 'assert'，因为 22.0.0 已 drop support for import assertions。

第五条 · ERR_PACKAGE_PATH_NOT_EXPORTED：包只声明了 "."，我 require 了 mypkg/extra.js。原文 Package subpath './extra.js' is not defined by "exports" in ...package.json。修法是在 exports 里显式开口子（"./extra.js": "./extra.js"），或者退回 main 时代的深层路径 —— 但后者在有 exports 的包里已经不可用，官方明确提醒这会连带 package.json 都拿不到，This will likely be a breaking change.

第六条 · Named export not found：见上一节的原文。修法固定为 default 导入再解构。

迁移检查清单：六条可直接复制的命令

按顺序跑，能在改代码前把风险点扫出来。

node -p "process.features.require_module"
node -p "process.versions.node"
npm pkg get type

第一条确认当前实例是否支持 require(esm)（我这里是 true）；第三条打印最近的 type 字段，空对象表示没写；第四条故意关掉开关复现旧行为，用来判断线上报错是否来自版本差异；第五条打印命名空间，用来验证具名导入是否真能用；第六条把语法探测关掉，模拟 22.7 之前的判定。

常见问题

Q：那我到底该不该在 package.json 里写 "type": "module"？

写。语法探测对 CJS 无性能影响，但官方明说它对 ESM 有轻微开销，而显式 type 能消掉这笔开销，也让「这个文件是 ESM」不再依赖猜。

Q：require(esm) 现在算稳定了吗？

22.12 的发布说明自己写的是 This feature is still experimental。能力默认开启，不等于接口冻结。

Q：同一个包被加载成两份实例，最省事的修法是什么？

优先用 "module-sync" 条件让两条路径指向同一份 ESM；退而求其次是把可变状态挪出模块作用域（放 globalThis 或显式注入），别指望缓存。

Q：为什么报错让我改名 .cjs，而不是 .js？

因为 .js 的格式由最近的 package.json 决定，你在一个 "type": "module" 的包里改不出 CJS；.cjs 是唯一能无视 type 的写法。

一句话收尾

两条默认值把「写法错误」变成了「解析结果不同」：22.7 之后 .js 的格式是猜出来的，22.12 之后 require() 能拿到 ESM 命名空间。猜出来的东西不会报错，只会给你另一份文件、另一个实例。我实际跑的 40 次用例里，18 次报错反而好办 —— 它们给了文件名和行号；退出码 0 的那 22 次里，真正要盯住的是拿错了东西却一声不响的那些。

如果你也在处理「同一份内容在磁盘上有多个版本」这类问题，站内还有两篇同层的复盘可以接着看：pip 装完之后为什么还在跑旧代码，以及同一个文件在 Git 里为什么有三份字节。编码层的对应问题是五种错误处理器各自的产出，而「不写 encoding 时默认值从哪张表来」在默认编码篇里有完整实测。四篇合起来是同一个问题域：你以为你读的是那一个，其实系统给了你另一个。
