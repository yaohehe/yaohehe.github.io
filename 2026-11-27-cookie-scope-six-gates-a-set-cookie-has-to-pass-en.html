Cookie Scope: Six Gates a Set-Cookie Has to Pass

cookiehttp semanticsdebugging

To reproduce a session that logged in successfully and was a stranger on the next request, I started two HTTP servers on this machine, one on 8101 and one on 8102, sharing a single CookieJar. The session cookie set on 8101 came back on the 8102 request without complaint. The same jar, asked for /app/v1/other, sent it. Asked for /app/v1x, it sent nothing.

Neither result is a bug. Both are written into RFC 6265. What is rare is seeing them side by side, which is why "the cookie disappeared" usually ends with "clear your browser cache".

This article answers one question: after a server sends Set-Cookie, will the next request carry it.

Every number below was measured here: Windows 11 10.0.26300, CPython 3.13.14, the standard-library http.cookiejar module (2,123 lines), requests 2.31.0. The subject under test is the standard library and requests, not a browser; wherever browser behaviour matters I quote official documentation and label it as such. There is only one rulebook: four filters before the header

RFC 6265 section 5.4 says that before a Cookie header is generated, the user agent selects every stored cookie meeting all of these conditions: a host-only cookie requires the request host to be identical, everything else goes through domain-match; the request path must path-match; a cookie with the secure-only flag requires a secure scheme; http-only only excludes non-HTTP APIs. The surviving list is then sorted, longer paths first, earlier creation first when paths are equal, and serialised into a single name=value; name=value header.

The standard library turns that rulebook into a policy object. DefaultCookiePolicy takes 13 constructor arguments, and three defaults settle most of the behaviour that follows: strict_domain=False, strict_ns_domain=DomainLiberal (zero, meaning every Netscape domain strictness flag is off), and strict_ns_set_path=False.

So "the standard library is looser than a browser" is not an opinion. It is those three default values.

Gate one: omitting Domain makes the scope wider

Start with what actually lands in the jar. A request to http://127.0.0.1:8101/set returns two cookies, one without a Domain attribute and one with Domain=127.0.0.1. Read back, they are two records:

  • Without Domain: domain is 127.0.0.1, domain_specified=False, a host-only cookie
  • With Domain: the stored domain becomes .127.0.0.1, a dot prepended, domain_specified=True

RFC 6265 section 5.4 is strict about the first kind: a host-only cookie is sent only when the request host is identical to the cookie's domain. That is a narrower scope than the Domain form. The default policy does not judge it that way.

I called policy.return_ok() directly with fabricated Request objects, skipping DNS and the network, to test the matching logic alone. Four hosts times two policies, eight combinations, split into two columns:

Switch strict_ns_domain from the default 0 to DomainStrictNonDomain and the behaviour lines up with the RFC immediately. The source comment on the default path is blunt (Lib/http/cookiejar.py, line 1171): strict check of non-domain cookies: Mozilla does this, MSIE5 doesn't.

The official documentation for DomainStrictNonDomain says cookies that did not explicitly specify a domain attribute can only be returned to the domain that set them. The switch exists. It is simply off by default.

The damage shows up on shared domains. On a multi-tenant host, a session cookie set by tenant A on a.example.com without a Domain attribute will, under the default policy of many scripted clients, also be sent to b.example.com. Browsers will not do that. The standard library will.

Gate two: the port is not part of the scope at all

The cookie set on 8101 arrives complete on the 8102 request, both records. This is not laziness in the library: RFC 6265 has no port attribute at all. The filter in section 5.4 covers domain, path and scheme; the Port attribute from RFC 2965 was removed.

That produces the two most common local failures. localhost:3000 and localhost:8080 overwrite each other's session cookies. A front-end dev server proxying to a back end lets both sides pollute one jar.

There is a fix that needs no code change. 127.0.0.1 and localhost are different hosts, and cookies do not cross between them. Isolate by host name, not by port number.

Gate three: the default Path is the parent directory

Set a cookie at /app/v1/settings with no Path attribute. The jar stores the path as /app/v1, not /.

RFC 6265 section 5.1.4 spells out the algorithm: take the request URI path and drop everything from the rightmost slash onward. The parent directory is the default. / is the answer most people assume.

Requesting five paths with that cookie produced this:

Request pathSent?
/app/v1/otheryes
/app/v1yes
/app/v1xno

An explicit Path=/foo draws a sharper edge: /foo yes, /foo/bar yes, /foobar no, /foo2 no. Path-match requires a prefix match plus a / as the first extra character. /foobar has a b there, so it fails.

One documentation discrepancy is worth noting. The MDN example says a cookie set by https://example.com/docs/Web/HTTP/index.html defaults to /docs/Web/HTTP/ with a trailing slash; the RFC algorithm yields /docs/Web/HTTP without one. Both produce the same path-match set, and the measured behaviour follows the RFC version.

The real-world failure is a single-page app. The login endpoint sits at /api/login, the front-end routes at /. Without a Path attribute the cookie's scope is /api only, so document.cookie on the page sees nothing while every API call works fine. The symptom gets reported as "the front end cannot read the login state". The actual cause is one missing attribute on the server.

Gate four: Secure cookies get stored and never sent

Send a Secure cookie over plain http and the standard library accepts it: secure is True in the jar, with discard=True and expires=None. Send another http request from the same jar and the cookie never appears.

No exception. No log line. It sits in the jar waiting for an https request that may never come.

Browsers are stricter here. The MDN Set-Cookie page states: Insecure sites (http:) cannot set cookies with the Secure attribute. A Secure cookie handed over plain http is dropped entirely, never stored. So the library keeps it and never sends it, the browser throws it away, and both end up with a missing cookie through different paths.

One related misconception: RFC 6265 section 4.1.2.5 itself notes that Secure protects only confidentiality, not integrity, and an active attacker can overwrite a Secure cookie from an insecure channel. Treating it as tamper-proof reads more into the attribute than it says.

Gate five: one name can exist several times

A cookie's unique key is name plus domain plus path. Change any one of the three and you have a second record. So sid can live at both / and /app:

  • Two entries in the jar: sid=root at path / and sid=app at path /app
  • A request for /app/x goes out as sid=app; sid=root, longer path first
  • dict_from_cookiejar() hands back only {'sid': 'app'}, silently discarding the other
  • Subscripting the jar directly raises TypeError: 'CookieJar' object is not subscriptable, because __getitem__ was never implemented

That ordering is a SHOULD in RFC 6265, not a MUST: longer paths first, earlier creation first for equal lengths. Servers have historically depended on it, so it functions as a de facto standard.

A server reading the first value reads the more specific, longer-path cookie. If the app writes its logout logic at / and blanks sid there, the copy at /app is still alive, and the next visit to /app logs the user straight back in. That is the usual shape of "I logged out, refreshed, and I was logged in again".

Two Set-Cookie headers with the same name and the same path in one response behave differently: only the second survives, and the jar still holds one entry.

Gate six: two-digit years send you into the future

Precedence first. Send Max-Age=3600 together with Expires=Thu, 01 Jan 1970 00:00:00 GMT. RFC 6265 section 4.1.2.2 reads the Max-Age attribute has precedence, and the measured jar keeps the cookie, with expiry set to now plus 3600 seconds. Max-Age=0 deletes immediately, and MDN describes zero or a negative number as expiring the cookie at once.

Parsing failures are the messy part. None of the forms below is a clean HTTP-date, and the outcomes split in two:

  • Expires=garbage and Expires=Thu, 32 Jan 2030 00:00:00 GMT: parse failure, expires=None, discard=True, silently downgraded to a session cookie
  • Expires=Thu, 01 Jan 1970 00:00:00 GMT: parses into the past, deletion works
  • Expires=Thu, 01 Jan 70 00:00:00 GMT: a two-digit year, parses fine, and does not mean 1970

That last line is the most counter-intuitive finding of this round. The docstring of http2time() says that when the year has only two digits, the function selects the century that makes the year closest to the current date. Measured today, 2026-11-27, the boundary falls between 76 and 77:

  • 70 parses to 2070-01-01
  • 76 parses to 2076-01-01
  • 77 parses to 1977-01-01

RFC 6265 section 5.1.1 has a fixed rule instead: 70 through 99 add 1900, 0 through 69 add 2000. By the RFC, 70 is 1970 and the cookie is already expired. By the standard library it lives until 2070.

Seven of the hundred two-digit values, 70 through 76, diverge from the RFC, which is 7% of the space failing on the classic delete-by-expiry trick. Old code uses Expires=Thu, 01 Jan 70 00:00:00 GMT to remove a cookie. I ran exactly that, and the entry in the jar came back with expires set to 3155760000: not deleted, no error.

Worse, the boundary drifts. It is computed as the century nearest the current date, so the divergent band shifts forward as years pass. A conclusion measured today will not hold in a few years.

No public suffix list, so cookies cross into other tenants

Browsers refuse to use a public suffix as Domain. MDN states it plainly: Domain cannot be a public suffix such as com, co.uk, or github.io, and offending cookies are ignored outright.

The standard library has no such list. Searching the source for publicsuffix and public_suffix returns zero hits. The measurements:

  • Setting Domain=.github.io from user.github.io returns True from set_ok
  • That cookie returns True for other.github.io
  • It returns True for evil.github.io as well
  • Setting Domain=.co.uk from shop.example.co.uk also returns True

On shared-domain hosting (*.github.io, *.herokuapp.com, *.netlify.app and friends), one tenant's cookie can be delivered to another tenant's site. The browser blocks this. A script does not.

If you need that block, add blocked_domains to the policy or check the suffix yourself before sending. Do not expect the library to do it.

SameSite and __Host-: the standard library knows neither

The same source counts: samesite zero hits, SameSite zero, __Host- zero, __Secure- zero.

Behaviour matches:

  • A cookie sent with SameSite=Strict lands only in the Cookie object's _rest dict ({'SameSite': 'Strict'}), with no check at request time
  • A request carrying Referer: https://evil.example/ and Sec-Fetch-Site: cross-site still sends it
  • __Host-h=1 without Secure and without Path=/ is accepted and sent back
  • __Secure-s=1 without the Secure attribute is accepted and sent back

MDN requires three things for __Host- at once: Secure, set by an HTTPS page, no Domain attribute, and Path exactly /. Code that relies on the prefix to pin a cookie to the current host gets that guarantee in a browser and nothing at all in a script.

For anyone writing crawlers, API tests or SSO integration scripts, this means the CSRF protection you verified in a browser is absent when the same flow runs from a script.

Troubleshooting: five real errors and two silent rewrites

All five errors below came out of this session, each with its cause.

1. Calling the policy directly: AttributeError: 'DefaultCookiePolicy' object has no attribute '_now'

return_ok() calls cookie.is_expired(self._now), and _now is injected into the policy by CookieJar at construction. Instantiate a policy on its own to test matching and the first line raises. Add policy._now = lambda: 0 and it works.

2. TypeError: 'CookieJar' object is not subscriptable

The standard-library jar does not support jar['sid']. To look up by name, use requests' RequestsCookieJar or iterate yourself.

3. CookieConflictError: There are multiple cookies with name, 'sid'

With a requests Session holding two cookies under one name at different paths, ss.cookies['sid'] raises this. Either specify domain and path, or switch to dict_from_cookiejar(), which silently drops one copy and is reliable only while debugging.

4. UnicodeEncodeError: 'latin-1' codec can't encode characters in position 3-4

A non-ASCII value in the jar, Chinese text for instance, meets http.client encoding headers as latin-1, and the whole request fails. The error fires at send time rather than parse time, so the traceback contains no mention of cookies and reads like a URL encoding problem. Percent-encode on write instead of pushing raw UTF-8 into a cookie value.

5. LoadError: '...' does not look like a Netscape format cookies file

MozillaCookieJar.load() raises this on a file that is not in Netscape format. The header must be # Netscape HTTP Cookie File; hand-built cookie files usually omit that line.

Two silent rewrites, no error but the data changes:

  • A semicolon inside a value: Set-Cookie: v=a;b; Path=/ stores v=a. The semicolon is read as an attribute separator and the rest vanishes.
  • A space inside a name: Set-Cookie: bad name=1 is accepted and sent verbatim as bad name=1, which most server parsers discard as garbage.

Thirty lines to see the whole scope

When a cookie is missing, dump the jar and evaluate each entry against the request path. It beats guessing.

import urllib.request
import http.cookiejar as cj

policy = cj.DefaultCookiePolicy(
    strict_ns_domain=cj.DefaultCookiePolicy.DomainStrictNonDomain,
)
jar = cj.CookieJar(policy)
jar._policy._now = jar._now = 0  # freeze time so expired entries stay visible

def dump(jar):
    for c in jar:
        print(f"{c.name}={c.value}  domain={c.domain} host_only={not c.domain_specified} "
              f"path={c.path} secure={c.secure} expires={c.expires} rest={c._rest}")

def will_send(jar, url):
    req = urllib.request.Request(url)
    return [c.name for c in jar if jar._policy.return_ok(c, req)]

Print dump(jar) first, then call will_send() on the URL that misbehaves. Two lines of output answer three questions: is the cookie in the jar, what scope did it compute, and why was it judged unsendable.

Frequently asked questions

Q: Why do two local ports overwrite each other's sessions?

Because port is not a dimension of cookie scope. The filters in RFC 6265 section 5.4 are domain, path and scheme. Isolate with different host names (127.0.0.1 versus localhost), not different ports.

Q: The server sets a cookie and devtools shows it, so why is the API request missing it?

Check two things first: whether Path landed outside the API directory, and whether Secure was set over http. The first looks like "the page sees it, the request does not"; the second looks like "it was stored but never sent". Neither reports an error.

Q: Why does Expires=Thu, 01 Jan 70 00:00:00 GMT fail to delete a cookie?

The standard library reads two-digit years as the century nearest the current date, so 70 becomes 2070 rather than 1970. Delete with Max-Age=0, or write all four digits.

Q: Is there any difference between Domain=.example.com and Domain=example.com?

Not in the standard library or in browsers; the leading dot is ignored. What matters is presence versus absence of the attribute, which separates host-only from domain cookies.

Conclusion: scope is four attributes, computed

Compress the six gates into one sentence: which request carries a cookie is decided by the domain attribute, the path, the Secure flag and the expiry, plus one sort rule for same-name collisions. What the server wrote is not what the client does; a layer of policy defaults sits in between.

Five places where the standard library disagreed with the RFC or with MDN showed up in this round: host-only cookies going to subdomains by default, no public suffix list, nearest-century two-digit years, Secure cookies accepted over http, and total indifference to SameSite and cookie prefixes. Each is minor alone. Stacked on one login flow they produce "I set it and it never arrived".

Neighbouring layers are already covered on this site: how long a response header lives in HTTP cache control and ETag, whether the connection is still up in TCP socket liveness, and what a certificate chain actually verifies in TLS verification. Cookies sit after all of them: they assume the first two worked, then decide whether this request carries credentials.

If you keep one line, keep this: DefaultCookiePolicy() is not a safe default, it is a compatibility default written for browsers of the 2000s. Fine for API tests. Wrong for imitating a real user.
