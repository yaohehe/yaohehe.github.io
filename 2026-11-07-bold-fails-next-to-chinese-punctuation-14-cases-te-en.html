Why Chinese Markdown Bold Stops Rendering: 14 Cases Tested

MarkdownCommonMarkCJK

TL;DR: when a bold run starts or ends with a full-width comma, colon, or bracket while the asterisks on the outside touch a Chinese character, CommonMark decides that delimiter cannot open or close anything. The asterisks stay on the page as literal text, and nothing warns you: not the editor preview, not the build log, not the lint pass. I actually ran 32 character combinations and 14 real sentences through markdown-it-py 4.2.0, mistune 3.4.0, GitHub's own GFM endpoint, and Python-Markdown 3.11.3. The first three agreed case by case, and 10 of the 14 sentences came out as literal asterisks. Python-Markdown rendered all 14. Nobody has a bug here; two implementations read the same clause differently. Three fixes exist, and moving the punctuation outside the asterisks is the one that survives everywhere.

The Symptom: Bold in Preview, Asterisks in Production

I hit this more than once. The first time was a warning line in a Chinese technical post that began with the words for "note, colon". The split preview in the editor showed bold text. After the commit, the page showed two literal asterisks, a full-width colon, and the sentence. I opened the HTML source: a plain paragraph, no stray markup, nothing in the build log.

My first assumption was that my own renderer was broken. So I pasted the same line into a GitHub comment box, and it was not bold there either. That was the useful clue. If GitHub does not honour it, the problem is not in a particular implementation. It is in the specification.

Following that thread turned up something better than a bug: a rule that is written down, precisely defined, reported upstream years ago, and still unchanged. It governs bold, italics, underscore emphasis, tables, lists, and horizontal rules for the same underlying reason.

The Rule Itself: What Flanking Actually Means

Section 6.2 of CommonMark 0.31.2 splits every run of delimiter characters into "left-flanking" and "right-flanking", then states when each may open or close. Verbatim:

A left-flanking delimiter run is a delimiter run that is
(1) not followed by Unicode whitespace, and either
(2a) not followed by a Unicode punctuation character, or
(2b) followed by a Unicode punctuation character and
preceded by Unicode whitespace or a Unicode punctuation character.
For purposes of this definition, the beginning and the end of
the line count as Unicode whitespace.

A right-flanking delimiter run is a delimiter run that is
(1) not preceded by Unicode whitespace, and either
(2a) not preceded by a Unicode punctuation character, or
(2b) preceded by a Unicode punctuation character and
followed by Unicode whitespace or a Unicode punctuation character.

5. A double asterisk can open strong emphasis
   iff it is part of a left-flanking delimiter run.
7. A double asterisk can close strong emphasis
   iff it is part of a right-flanking delimiter run.

Both definitions carry a 2b branch. Paraphrased: punctuation on the inside is allowed, provided the other side is whitespace or punctuation. That single clause is the whole problem.

One more definition, from section 2.1 of the same spec, decides what counts as punctuation at all:

A Unicode punctuation character is a character in the Unicode P
(puncuation) or S (symbol) general categories.

The misspelling of "punctuation" inside the parentheses is in the spec itself and has never been corrected.

All of them sit in the P tree, so all of them count as Unicode punctuation. Han characters sit in Lo, "Letter, other", and are neither whitespace nor punctuation.

The conclusion is narrower than the folklore: bold in Chinese is fine on its own. When both ends of the bold run are Han characters, every renderer I tested produces strong emphasis, because the opening delimiter is followed by a letter and the closing one is preceded by a letter, so branch 2a applies. What breaks is the case where the content itself starts or ends with Chinese punctuation. The opening delimiter is then followed by punctuation and must take branch 2b, which demands that whatever precedes the delimiter be whitespace or punctuation. In Chinese prose what precedes it is usually a Han character. Branch 2b fails, the opening delimiter is discarded, and the same happens to the closing one.

Chinese does not separate words with spaces, and it does not pad punctuation either. A rule that costs Western prose almost nothing lands on nearly every sentence in Chinese.

Reproducing It in Three Minutes

The snippet below is copy-paste runnable and needs nothing but three pure-Python packages, no API key:

python -m pip install --target ./mdprobe markdown-it-py mistune markdown
import sys
sys.path.insert(0, "./mdprobe")
from markdown_it import MarkdownIt
import markdown as pymd
import mistune

cm = MarkdownIt("commonmark")
mk = mistune.create_markdown()

CASES = [
    "这是**「重要的」**内容。",
    "这是**我想做的事。**所以继续。",
    "这是 **「重要的」** 内容。",
    "这是**重要的**内容。",
]

for src in CASES:
    a = "" in cm.render(src)
    b = "" in pymd.markdown(src)
    c = "" in mk(src)
    print("%-28s mit=%-5s pymd=%-5s mist=%-5s" % (src, a, b, c))

You should see False/True/False for the first case and True everywhere for the last two. If case 3 is true while case 1 is false, your renderer follows strict CommonMark.

To check GitHub's own behaviour, the public rendering endpoint takes a mode of gfm:

curl -s -X POST -H "Content-Type: application/json" -d "{\"text\":\"这是**「重要的」**内容。\",\"mode\":\"gfm\"}" https://api.github.com/markdown

The response is a plain paragraph with the asterisks intact.

Three Fixes, One of Them Needs No Explanation

Fix one: move the punctuation outside the asterisks. Colons, full stops, and brackets that end a bold phrase go after the closing run instead of inside it. Zero side effects, and the typography is more accurate anyway, since the emphasis covers the words rather than the punctuation.

Fix two: put a space on the outside of each run. That works in all four renderers, but two visible spaces in the middle of a Chinese sentence look wrong, and a space on one side only is not enough (case 9 above). If the gap is unacceptable, use a zero-width space, U+200B, on the inside instead. It is category Cf, format character, so it is neither whitespace nor punctuation, which is exactly what branch 2a needs. I tested a zero-width space on the inner side of both delimiters and got bold in markdown-it and on GitHub.

Counter-intuitive but important: do not reach for NBSP, U+00A0. It is category Zs, real Unicode whitespace. Put it inside and the opening delimiter is followed by whitespace, so branches 2a and 2b both fail and the asterisks still leak. The name says "non-breaking space"; the spec still treats it as a space.

Fix three: write the strong tag directly in HTML. Most reliable, identical across renderers, but poor readability and awkward inline. Reasonable for machine-generated content, unpleasant to hand-write.

My own order is fix one first, zero-width space when the punctuation has to stay inside, and the tag only for generated output.

Related Trap One: A List That Does Not Start at 1 Will Not Interrupt a Paragraph

Flanking aside, CommonMark has a few more constructs that look like they should work and quietly do not. The clearest is a numbered list's start value. The spec attaches an exception to the definition of a list item:

1. When the first list item in a list interrupts a paragraph -- that is,
   when it starts on a line that would otherwise count as paragraph
   continuation text -- then (a) the lines Ls must not begin with a blank
   line, and (b) if the list item is ordered, the start number must be 1.

In plain terms: for an ordered list to interrupt an open paragraph, its first number has to be 1. So these two inputs end up in different places:

Body sentence one.
1. First item
Body sentence one.
3. Third item

The first becomes a paragraph plus an ordered list. The second stays a single paragraph, and on GitHub the line break is rendered as a soft break. That matters if you write "steps three and four": starting at 3 gives readers a paragraph containing the text "3.", not a list.

Two escapes: leave a blank line before the list, after which you are starting a new block and any start value is legal, or drop the numbering and use bullets with a hand-written prefix.

Related Trap Two: A Rule Under a Paragraph Becomes a Heading

A line of dashes on its own is meant to be a thematic break, but when a line of text sits directly above it, the spec states the precedence:

If a line of dashes that meets the above conditions for being a
thematic break could also be interpreted as the underline of a
setext heading, the interpretation as a setext heading takes precedence.

A paragraph followed by a line of three dashes is a level-two heading, not a paragraph plus a rule. All four renderers agree here, Python-Markdown included. I lost an afternoon to this in my own generator: I added a rule at the end of an article and the summary sentence above it became the page's heading, while the HTML review pass, which only counted h1 elements, stayed green.

The guard is simple: blank line above and below the rule.

Related Trap Three: Tables Are Not in CommonMark at All

This surprises people. The CommonMark spec has no table syntax. Searching the full spec for the word table returns 26 hits, and every one of them is a tag inside an HTML block example. No pipe-table grammar anywhere.

So whether a pipe table renders depends entirely on extensions:

That is why the same README turns into a paragraph full of vertical bars locally and a real table on GitHub. Also silent.

Troubleshooting: Two Real Exceptions and Two Silent Failures

The cases above are silent. Configuration does throw, though, and I reproduced each of these on Windows 11 with CPython 3.13.14.

Error one: ModuleNotFoundError: No module named 'tabel'

Symptom: a typo in an extension name crashes the process, and the traceback never says the extension name is wrong.

>>> import markdown
>>> markdown.markdown("| a | b |", extensions=["tabel"])
ModuleNotFoundError: No module named 'tabel'

Cause: Python-Markdown imports the extension name as a module. A misspelling becomes an import failure, and the exception type looks exactly like a missing dependency. My first reaction was to install a package called tabel, which of course does not exist.

Fix: use tables, plural, or pass extra to pull in the usual set. To see what is available first:

python -c "import markdown; print(sorted(markdown.__all__))"
python -c "import markdown; print([e.name for e in markdown.Markdown().registeredExtensions])"

Error two: yaml.scanner.ScannerError: mapping values are not allowed here

Symptom: one front matter line with a colon in the description aborts parsing. The message points at a column but does not explain the semantics.

>>> import yaml
>>> yaml.safe_load("description: 三层结构: 前端 后端 数据库\n")
yaml.scanner.ScannerError: mapping values are not allowed here
  in "", line 1, column 18

Cause: YAML separates key from value with a colon followed by a space. A second colon-space inside the value looks like the start of another mapping entry, and a mapping is not allowed at that position. Full-width colons used in Chinese prose never trigger it, but a single ASCII colon plus space will.

Fix: quote the whole value, or switch to the full-width colon, or use a folded block:

description: "三层结构: 前端 后端 数据库"

Silent failure one: linkify is on, and nothing happens

Symptom: linkify is set to true, bare URLs stay plain text, no exception.

>>> from markdown_it import MarkdownIt
>>> md = MarkdownIt("commonmark", {"linkify": True})
>>> print(md.linkify)
None
>>> print(md.render("见 https://example.com 页面"))

见 https://example.com 页面

Cause: linkify needs a separate package to supply the recogniser. Without it the attribute is None and the rule is skipped. Textbook missing optional dependency: no error, no warning, feature quietly off.

Fix: install the dependency, then assert the attribute after construction:

python -m pip install linkify-it-py
python -c "from markdown_it import MarkdownIt; print(MarkdownIt('commonmark', {'linkify': True}).linkify is not None)"

Silent failure two: the delimiter pair is discarded with no log line

The failure from the top of this article. No exception, because what you wrote is valid Markdown; the spec simply reads it as ordinary characters.

Cause: branch 2b fails, the opening or closing run is discarded, and the asterisks degrade to literal text.

Fix: the three approaches above. Then add a post-build assertion for leftover asterisks, which is cheaper than any review rule:

import re, pathlib
for p in pathlib.Path("dist").rglob("*.html"):
    html = p.read_text(encoding="utf-8")
    body = re.sub(r"", "", html, flags=re.S)
    if "**" in body:
        print("literal asterisks left:", p)

A Seven-Point Checklist for Chinese Markdown

  • If the bolded text begins or ends with a quote, bracket, book-title mark, colon, full stop, enumeration comma, exclamation or question mark, ellipsis, or dash, move the punctuation outside the asterisks first; it is cleaner than padding with spaces.
  • A space on one side only does nothing; both sides need to satisfy the rule, so do not half-fix it.
  • Zero-width space is a workaround, NBSP is not. Prefer neither: invisible characters cost you later.
  • An ordered list that starts at anything other than 1 needs a blank line above it, or it will never become a list.
  • Leave a blank line above and below any horizontal rule, or the line above becomes a heading.
  • Treat pipe tables as an extension and confirm the target renderer has table, tables, or extra enabled.
  • Before publishing, scan the output for literal asterisks and paragraphs full of vertical bars. Both are silent.

Closing

The history is worth one paragraph. CommonMark upstream received a report about CJK punctuation and emphasis in May 2020 (issue 650 in the spec repository, still open), and in August 2026 someone opened a pull request to allow CJK adjacency in delimiter runs (839, still unmerged). On the markdown-it side there was a forwarded report in 2017 (410), and issue 1080 in December 2024 described precisely the "bold fails when a list item starts with Chinese punctuation" case. It was closed in May 2026, but the relaxation patch filed the same month, 1145, did not land either. Re-tested against the current markdown-it-py 4.2.0, the behaviour is unchanged.

So do not wait. Moving the punctuation out is the cheapest fix that survives every renderer I tested.
